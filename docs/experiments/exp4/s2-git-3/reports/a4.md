# a4 report: pricing + report money (git arm, s2-git-3)

## 1. What I built

- `src/pricing.js`: `price(plan, day) -> { currency: 'EUR', prices, total, lines }`, with all arithmetic in integer cents, half-up rounding to the cent, and `total` as the sum of the rounded prices. `formatMoney(euros, currency='EUR') -> 'EUR 7.40'` is cent-exact (`1.005 -> 1.01`). It accepts a1's Day or the raw day file, and package ids or stop objects. It throws on an unknown drone or package and on a package delivered twice.
- The first formula was base 2.00 + 0.80/km (from the home depot) + 0.40/kg + a flat 2.50 for express. After **CR-1** it became 2.00 + 0.25/flight-minute + 0.40/kg, with express multiplying the whole price by 1.5. Pricing works out each stop's flight minutes from the Plan's flight order on its own (geo legs divided by drone speed, no service or waiting time).
- `src/report.js`, the money block: `renderPriceSection(prices)` (header `Prices (EUR)`, one line per package, then TOTAL) uses `pricing.formatMoney`.
- I pinned the CONTRACTS.md pricing section (before and after CR-1, each time with a worked example). Tests are in `test/pricing.test.js` (11 tests, including an exact half-cent case, the x1.5 rounding order, and a check of my flight minutes against the scheduler's `plan().trips[].flightMinutes`) and `test/report.test.js` (3 money tests).
- State at the end: main at `06a9635`, `npm test` passes 74 tests with 0 failures, and `node src/cli.js plan fixtures/day1.json` gives 18 packages priced, a total of EUR 80.89, and p19 unassigned as "too heavy".

## 2. How I learned about teammates' work

- **Commands:**
  - `git fetch -q && git log --oneline --stat HEAD..origin/main` after every land and every wait.
  - `git show <sha> -- <paths> | grep '^[-+]'` to read the parts of a diff that mattered to me.
  - `tail NOTES.md` after each pull.
  - `git archive origin/main | tar -x` into a scratch directory once, to run the suite on main without my change.
- **Waiting:** the playbook's bounded loop: `for i in $(seq 1 28); do git fetch -q; git log --oneline HEAD..origin/main [-- paths] | grep -q . && break; sleep 20; done`.
  - I narrowed the path filter to `CHANGE-REQUEST.md src/pricing.js src/report.js test/{pricing,report}.test.js` so I only woke up for things relevant to me. That is how I caught CR-1 (`35b09cf`).
- **What I looked for:** shapes of Plan, Day and the report structure, anyone touching report.js, and `[pm]` lines.
- **Time:** about 7 wait loops, roughly 30–35 minutes of wall clock spent sleeping or polling. My real attention was low, but latency was high: I only learned about a push up to 20 s after it happened, and while I was writing code I learned nothing at all until my next `pull`.

## 4. Conflicts, rejected pushes, rebases

- **Rejected pushes: 0.** I always ran `git pull && npm test && git push`. Pull-before-push meant the push itself never raced.
- **Conflict: 1.** `CONFLICT (content): Merge conflict in src/report.js` while rebasing my pricing commit onto `365e304`.
  - The zdiff3 markers made the three-way story clear: base, a5's version and mine.
  - Resolving it took about 5 minutes, mostly deciding *whose interface wins*, not editing text.
  - `git rebase --continue` needed `GIT_EDITOR=true` because the environment is non-interactive.
- **Auto-rebases: about 6** (most pulls before a push replayed my commit on top of new work). None of them caused trouble apart from the one above. NOTES.md merged cleanly every time thanks to union-merge.

## 5. Friction and confusing output

- `Could not apply bb4f61e... # pricing: price(plan, day) ...`: the stray `# ` before the subject is odd, and the sha shown is a pre-rebase sha that no longer exists after you continue.
- `git diff` during the conflict shows `diff --cc` combined format (`++<<<<<<< HEAD`, `++||||||| parent of bb4f61e (...)`). It is readable, but during a rebase `HEAD` means *their* side (upstream) and the commit sha means *mine*. That inversion is a classic trap, and I had to stop and think.
- **The real problem was not a git message: git cannot say whether the tests on main are green.** After my rebase the suite failed. Git gave no way to tell whether main was already red or my change broke it, so I had to `git archive origin/main` into a temp directory and run the tests there. The answer was "latent", only exposed by my landing. I then knowingly pushed with a failing test, after explaining it in NOTES.
- No feed. Learning about anything means polling, so a teammate's shape change can sit unseen for minutes while I build against the old one. The crossed adaptations in §3 are exactly this.
- `git pull` output (`Rebasing (1/1)Successfully rebased...`) does not say *what* I was rebased onto. I always needed a second `git log` to see what had changed under me.

## 6. Compared with an ideal tool

For 5 parallel agents sharing contracts and one shared file:

- **Live interface notifications.** When a5 pushed `365e304` (adopting my contract), I should have been told within seconds, before I spent a cycle adapting to their *old* code. Likewise, when I posted my CR-1 plan, a2 and a3 should have seen it before both writing `flightMinutes`. Git's pull model made three teammates duplicate one feature and made two of us swap positions at once.
- **Claims/intent.** Something like "a4 is changing renderPriceSection / flightMinutes now", visible to everyone before code exists. NOTES.md is a weak, polled version of that.
- **CI status per main commit.** "main@X: 61 pass / 0 fail", so I would know whether a failure is mine, and know when my land is truly safe. Ideally the push would be checked against the merged result.
- **Ownership-aware merges.** report.js has clearly marked sections. A tool that understood "a4 owns this block" could auto-route the conflict or warn a5 when they edit inside my block.
- **Contract-change awareness.** Something like "this commit changes the shape of X that files Y and Z consume".

Git itself (history, rebase, zdiff3, union merge) was solid and never lost work. The gaps are all coordination latency and awareness, not storage.

## 7. Features I wanted

1. A push feed or subscription filtered by path (`watch src/report.js CONTRACTS.md`), instead of sleep loops.
2. Test status attached to each main commit, plus "is main green?" in one command.
3. Lightweight intent/claim announcements, separate from commits.
4. `git pull` printing a short summary of the incoming commits it rebased me onto.
5. An owner map, so conflicts and edits inside someone's section notify them.
