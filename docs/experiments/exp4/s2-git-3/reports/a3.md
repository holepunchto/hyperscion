# a3 report: scheduler capacity side (git arm)

## 1. What I built

The capacity side of `src/scheduler.js` and the glue that ties it to a2's timing:

- **`buildTrips(day)`** decides which packages share which trip on which drone. It enforces payload and range (using `geo.orderRoute` and `geo.routeLengthKm`), plans express packages first and then by earliest deadline, and lets several trips run per drone. Packages with delivery windows only share a trip when their windows overlap. When a new trip is needed, the drone with the fewest km flown so far gets it.
- **Capacity reasons** for unassigned packages: `too heavy for every drone`, `out of range for every drone`, `no drone can both carry its weight and reach it`, `no drones available`.
- **`scheduleDay` (the glue):**
  - It runs each drone's trips back to back through a2's `timeTrip`.
  - When a trip would have to wait for a late window, later trips that fit in the gap fly first.
  - A trip that fails on timing is split up, and its packages are retried on any drone. A package that still fails goes to unassigned, with `timeTrip`'s error as the reason.
- **`plan(day)` and the pinned Plan shape:** `trips[{drone,depot,start,end,packages,etas,flightMinutes,loadKg,distanceKm}]` and `unassigned[{id,reason}]`. The shape is documented in CONTRACTS.md. For CR-1, `flightMinutes` comes from the timeTrip stops.
- **`test/scheduler.test.js`:** 18 tests, covering edge cases plus a randomized invariant test over 30 generated days.

Final state of main is 287f411. `npm test` gives 74 passing and 0 failing, and the CLI exits 0 on every fixture (1 on `edge-invalid`, as intended).

## 2. How I learned about teammates' work

- **Every cycle:**
  - `git fetch -q && git log --oneline --stat HEAD..origin/main`, to see who touched which files.
  - `git diff HEAD origin/main -- NOTES.md | grep '^+'`, to read only the new notes lines. This was my real "feed".
  - `git show <sha> -- NOTES.md CONTRACTS.md src/scheduler.js`, for anything touching my file or a contract.
- **For the integration test:** I read the test file directly after pulling.
- **Waiting:** I used the playbook's bounded loop (`for i in $(seq 1 15); do git fetch -q; git log HEAD..origin/main | grep -q . && break; sleep 20; done`), about 7 times. Polling and waiting took roughly 25–30% of wall-clock time, but very little attention.

## 5. Friction and confusing output

- **Pull says "up to date", then push is rejected.** `git pull` reported `Current branch main is up to date.`, yet the next `git push` was rejected. That is technically correct (the race happened during the test run), but it reads as a contradiction. The playbook line `git pull && npm test && git push` has a window of a few seconds in which this happens.
- **The rejection text is truncated.** With `| tail -1` I only saw `hint: See the 'Note about fast-forwards' in 'git push --help' for details.` That is not the line that says it was rejected.
- **No sign of in-flight work.** Nothing shows that a teammate is working on, or replying to, the same thing. This caused the crossed scheduler-split replies, the duplicated rounding fix, and the quadruple `flightMinutes`.
- **Hard to tell what is new since I last looked.** NOTES.md is the only coordination channel, and seeing what is new in it needs a hand-made `git diff HEAD origin/main -- NOTES.md | grep '^+'`.
- **`ORIG_HEAD` is the wrong reference point after a pull.** To see "what came in with that pull" I tried `git log ORIG_HEAD..origin/main`. After a rebase `ORIG_HEAD` points at my pre-rebase commit, which was confusing. I went back to using explicit shas.

## 6. Compared with an ideal tool

For 5 agents working in parallel on shared files, an ideal tool would:

- **Show intent and in-progress work.** For example, "a2 is editing CONTRACTS.md scheduler section" or "a4 is responding to CR-1". That alone would have prevented the crossed split proposal and the 3–4x duplicate `flightMinutes` work.
- **Make landing atomic and test-gated.** It would rebase, test and land in one step, retrying itself, so the gap between pull and push could not reject a push.
- **Push notifications filtered by relevance.** Something like "a commit touched src/scheduler.js or the scheduler section of CONTRACTS.md, or mentioned @a3", instead of me running fetch loops.
- **Structured contract ownership.** A comment like "a2 proposes X for a3, needs ack" should be a first-class item with a state, rather than lines in an append-only file that I have to grep.

Git itself was solid. Rebases on a shared file were painless, thanks to the clear section layout and union-merged NOTES. The failures were all about awareness, not merging.

## 7. Features I wanted

- A `git watch`-style feed: new commits and NOTES lines filtered by path or mention.
- An "I'm working on X" claim or lock that teammates can see.
- An atomic `land` (rebase, test, push, retry).
- `git log --since-last-pull`, a reliable "what came in with my last pull".
- First-class requests and acks for contract proposals.
