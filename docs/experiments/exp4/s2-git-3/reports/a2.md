## 2. How I learned about teammates' work

- `git fetch -q && git log --oneline --stat HEAD..origin/main` before every commit, and `git show <sha>` / `git show origin/main:src/scheduler.js` when a commit touched scheduler, CONTRACTS or NOTES. Reading the NOTES.md diff (`git diff HEAD origin/main -- NOTES.md`) was the most useful single view, because it worked as the team's chat.
- About 8 fetch/log rounds. Five were bounded wait loops (`for i in $(seq 1 N); do git fetch -q; git log ... -- <paths> | grep -q . && break; sleep 20; done`), filtered to CHANGE-REQUEST.md and my files. Roughly 15–20 wall-clock minutes went into waiting/polling, but very little attention. I had to pick the path filter by hand: a too-narrow filter could have missed a NOTES.md line addressed to me.

4. Clean auto-rebases ("Successfully rebased and updated refs/heads/main") on most other pushes, with no trouble. NOTES.md union merge never conflicted.

## 5. Friction and confusing output

- During the conflict, the rebase made "HEAD" mean *origin's* side (`<<<<<<< HEAD` = a3's code) and the commit label meant *mine*. I know this, but it is backwards from intuition every time.
- `git rebase --continue` wanted an editor. I had to set `GIT_EDITOR=true` for a non-interactive agent. The output then said `[detached HEAD 6c3e858] ...` before "Successfully rebased", and that briefly looked alarming.
- My own command chain `git add -A && git rebase --continue && npm test && git push` did not refetch, so the push was rejected. The conflict resolution window is exactly when someone else pushes.
- The conflict output says *what* conflicts but not *why*. Seeing the a3 commit (eea8ef5) that rewrote the whole section needed a separate `git log ORIG_HEAD..origin/main`. Also, during a rebase `ORIG_HEAD` is not the obvious thing to reach for.
- `hint: Disable this message with "git config set advice.mergeConflict false"` and similar hints are noise for agents.
- The bigger problem is not output text. git tells you nothing about *in-flight* work: a3 and I both rewrote the same section twice, and both added `flightMinutes` at the same time, because neither could see the other's uncommitted intent.

## 6. Compared with an ideal tool

An ideal tool here would have:
- **Shown intent/claims before code**: "a3 is editing scheduler.js TIMING/plan() now" or "a3 is implementing CR-1 flightMinutes". That would have prevented both duplicate-work episodes (crossed split proposals, double flightMinutes), which together were my biggest waste.
- **Pushed notifications** instead of polling: a feed of "new commit touching a file you own / NOTES line mentioning @a2 / CHANGE-REQUEST". My fetch loops worked but needed a hand-picked path filter and sleep interval.
- **Section-aware ownership**: scheduler.js has CAPACITY/TIMING/GLUE regions. A tool that knew region owners could flag "your commit touches a3's region" before the push, and merge non-overlapping region edits.
- **Atomic "rebase + test + push" with retry**, so a push rejected after a long conflict resolution re-runs itself rather than failing.
- **Threaded replies attached to a commit**: the NOTES.md log works, but conversations (a3's bug report, my correction) are interleaved lines with no threading or ack state.

## 7. Features I wanted

1. A watch/feed: `notify me when origin/main touches <paths> or NOTES mentions @a2`.
2. Work-in-progress claims visible to the team (lightweight locks or "I'm on X" markers).
3. A one-shot `sync-and-land` (fetch, rebase, run tests, push, retry on reject).
4. Conflict context: show the upstream commit(s) and authors that caused each conflict hunk.
