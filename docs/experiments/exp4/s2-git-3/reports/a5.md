# a5 report (git arm, s2-git-3)

## 1. What I built

- `src/cli.js`: `plan <dayfile> [--json]`, `main(argv, io)` and `runPipeline(json)`. Exit codes: 0 on success, 1 for an unreadable file or `EINVALIDDAY`, 2 for bad usage, 3 for internal errors (with the stack).
- `src/report.js` (shared with a4): input adapters, `toJSON` (the pinned `--json` shape plus extra fields `end`, `distanceKm` and `flightMinutes[]`), and the `renderReport` layout: a summary line, trips grouped by drone with per-stop ETA and flight minutes, unassigned packages with reasons, then a4's `renderPriceSection`. I wrote placeholder money functions that a4 then rewired to `pricing.formatMoney`.
- `test/integration.test.js`: property checks run through the real CLI. Every package appears exactly once (delivered, or unassigned with a reason). Payload, range, day length, no overlapping trips per drone, and windows are checked by re-simulating each flight. p19 must be unassigned for being too heavy. Prices must cover exactly the delivered set, and the total must equal their sum. Each price is recomputed independently with the CR-1 formula, and the plan's `flightMinutes` are cross-checked. The in-process pipeline must match the CLI output. Invalid and missing files and bad usage must exit non-zero.
- `test/report-layout.test.js` and four fixtures: `edge-tight` (exact capacity, too heavy, out of range, window outside the day), `edge-busy` (multi-trip, the day runs out), `edge-empty` and `edge-invalid`.

## 2. How I learned about teammates' work

- `git fetch -q && git log --oneline --stat HEAD..origin/main` before every pull, around 12 times.
- `git show <sha> -- src/report.js` once, when a4 touched my shared file.
- I read `CONTRACTS.md` and `tail NOTES.md` after pulls. Most of the useful information was in NOTES.md and CONTRACTS.md, not in diffs.
- I ran the playbook's bounded wait loop (`for i in $(seq 1 25); do git fetch -q; git log HEAD..origin/main [-- file] | grep -q . && break; sleep 20; done`) 6 times. Total waiting was roughly 25 to 30 minutes of wall clock, two loops of which timed out empty (about 8 minutes each). It cost very few tokens, but it is blind polling.

## 5. Friction and confusing output

- My own pipeline `git pull && npm test 2>&1 | grep -E "^# (pass|fail)" && git push` silently skipped the push: node 26 prints `ℹ pass`, so grep failed. This is my bug, but nothing told me the push had not happened. I only noticed because the output had no `To ...` line.
- The rejected-push hint text is 5 lines of generic advice. The useful part is one line.
- `git log HEAD..origin/main` shows *that* something landed, not *whether it affects me*. To learn "a4 changed my file" I had to scan `--stat`. And a commit message (f14a593) told me my test was now failing on main. Git has no signal that main is red.
- No way to know whether main was green except pulling and running the tests myself.
- No real confusing messages. The output was clear.

## 6. Compared with an ideal tool

With 5 agents working in parallel, git's merge machinery was fine: 0 conflicts and 1 cheap rejection. The gaps were all about awareness:

- **A push feed instead of a sleep-20 loop.** I would like a "wake me when X touches path Y, or when a line mentions @a5" subscription. About 25 minutes went to blind polling.
- **CI on main.** An ideal tool would run `npm test` on every land and tell everyone "main is red since f14a593, failing test: integration overlap". Here a teammate had to write that by hand in a commit message and NOTES.
- **Gated or pending lands.** For CR-1 I wanted to land my integration check as "required once pricing lands". I had to keep it in my working tree instead.
- **Structured asks and replies.** NOTES.md worked, but replies crossed (a2 and a3 each adopted the other's scheduler split, a9759f0). A threaded or acknowledged channel would avoid that.
- **File and section ownership**, so the tool could tell me when someone touched my section of report.js.

## 7. Features I wanted

1. Notification or subscription on paths and mentions (no polling).
2. Shared CI status for main, plus "tested on top of sha X" metadata on each land.
3. Conditional or queued lands ("land when main has a commit touching src/pricing.js and tests pass").
4. Threaded, acknowledged notes instead of an append-only file.
