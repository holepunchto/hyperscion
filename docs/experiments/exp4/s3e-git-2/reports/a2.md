## 5. Friction and confusing output
- The outage message "does not appear to be a git repository ... check access rights" reads like a misconfiguration, not "server down"; without the playbook table I would have started checking remotes. Nothing tells you when it's back; you poll.
- `git pull && ...` chained with `&&`: the failed pull correctly stopped the chain, but my commit was done, so state was "ahead 1" silently; fine, but easy to forget to push later.
- `Current branch main is up to date.` followed by a push of `bcd0eeb..7388833` looked odd for a second (an earlier `pull -q` had already brought things in).
- No way to know a teammate's in-flight state (a3 had a plan WIP locally while I designed my API); you only see what was pushed.
- Discovering "who uses my functions" needs grepping teammates' diffs by hand.

## 6. Compared with an ideal tool
- A push-based feed ("a3b landed scheduler.js; it now calls geo.improveRoute") instead of 20-second fetch loops, filterable by file/owner/contract section.
- Contract-aware notifications: when CONTRACTS.md "model" changed I wanted a ping, not to diff the whole file.
- Clear availability state for origin ("origin offline since 02:04, your 1 commit is queued; will push when back") with automatic retry, instead of a misleading fatal error.
- Notes/requests as first-class threaded items addressed to an owner (my "a4 FYI" line was effectively an issue; union-merged NOTES works but is unthreaded and needs `diff | grep '^+-'` to read).
- Honestly, for this team git was adequate: small owned files + union-merged NOTES meant zero conflicts, and the pull-rebase-test-push line just worked.

## 7. Features I wanted
- `git log` with "only new NOTES lines since my last look" built in.
- Wait-for-change primitive (`git fetch --wait -- src/scheduler.js`).
- Queue-and-retry push when the remote is down.
- A "who calls my exports" view across the team's latest main.
