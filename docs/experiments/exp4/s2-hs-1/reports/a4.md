# a4 report: pricing + report money

## 1. What I built
- `src/pricing.js` + `test/pricing.test.js`. First formula (#3): EUR, 2.50 base + 0.80/km (home depot to destination) + 0.50/kg + 3.00 express. After CR-1 (#26): `(2.00 + 0.25*flightMinutes + 0.40*kg) * 1.5 if express`, rounded once per package (half up), `total` = sum of rounded cents. Pricing works out flight minutes itself: cumulative `geo.distanceKm` along `trip.packages` at the drone's speed. It throws on an unknown drone or package, and on a package that appears in two trips. `breakdown[id]` = `{flightMinutes, kg, base, time, weight, express, total}`. `formatMoney`.
- The money part of `src/report.js`: `moneyColumn`, `moneyDetail`, `tripSubtotal` (trip subtotal lines), `ratesLine`, and `moneyTotalLine` (`Total: €81.31 (18 deliveries)`). I also wrote the a4 tests in `test/report.test.js`.
- I pinned the pricing section in CONTRACTS.md twice (original formula, then CR-1).
- One test checks that pricing's flight minutes match the scheduler's timing on day1 (`arrive - start - earlier stops' (depart - arrive)`, within 0.02).

Lands: #3, #6, #7, #13, #14, #26 (6 landed, plus 1 attempt rejected by a real conflict). When I left, main was at #28: 69 tests passing, 0 failing, 0 skipped, and `node src/cli.js plan fixtures/day1.json` prints the report with total €81.31.

## 2. How I learned about teammates' work
- A background `hs watch --json >> .hs/feed.jsonl` ran the whole time. I read it with `tail` or grep a few times early on to see who had landed what.
- Mostly I used blocking waits: `hs watch --path /src/report.js --path /src/pricing.js --path /CHANGE-REQUEST.md ... --count 1 --timeout 600`. These were the main tool. They woke me exactly for a5's report skeleton (#8), a5's `breakdown` in `--json` (#17), the PM's CR-1 (#20) and a5's integration test (#27).
- The `incoming from teammates` list from `hs sync`/`hs land` was the second biggest source. It told me about #2, #4, #5, #9, #22–#25 without me asking.
- `hs show 11 --path src/report.js` to understand the conflict. NOTES.md for intent, CONTRACTS.md for shapes. I used `hs log <file>` once.
- Yes, watch replaced polling completely. I never ran a sync loop.

## 5. Friction, bugs, confusing output
- On the real conflict, `hs land` printed **only** that one line. It did not say that my other 4 files were committed but not landed. I learned that from `hs status` (`5 committed path(s) not landed`). It also did not say whether the conflict happened before or after the `--check` ran. A line like "nothing landed; your changes are committed locally" would help.
- `hs log src/pricing.js -n 5 --oneline` printed `main is at #22 or later (from your feed); this shows #20. hs fetch to update`. That is useful, but the playbook says to use `sync`, not `fetch`. I had to stop and work out whether `fetch` would rebase my working files. (I didn't run it.)
- `hs watch --timeout` returning exit 2 with `watch: timed out after 480s with 0 matching changeset(s)` is clear. But exit 2 also means "done, read the !! lines" elsewhere, which is a small overload.
- Shared ownership (`src/report.js a4 a5`): my land of report.js went straight to `final` with no Show to a5. That's reasonable because I'm a co-owner, but a5 got no review request for a significant change to their layout function. I told them in NOTES instead.
- `hs show 11 --path src/report.js` printed `(3 other path(s) not shown, drop --path for all)` *above* the diff, between the message and the patch. That's fine but a little noisy.

## 6. Compared with git
- **Better:** `land --check` re-runs tests on the merged tree and retries when main moves, a "rebase, test, push, retry" loop that git doesn't give you. With five agents on one main, git would have meant several `push rejected / pull --rebase / rerun tests` cycles. The path-filtered blocking `watch` let me sleep until exactly the files I care about changed. With git I'd poll `git fetch && git log origin/main -- src/report.js`. NOTES.md union merge made concurrent appends free; in git that file would conflict constantly. The `incoming from teammates` list is a nicer digest than `git log HEAD..origin/main`.
- **Same:** the one real conflict looked and resolved exactly like a git conflict (markers, fix, land). Per-file lands didn't help there, because a5 and I really did edit the same function.
- **Worse/unknown:** no branches or PRs for a shared file. a5 and I coordinated report.js purely via NOTES. With git a PR would have given a5 a review gate on my edit to their layout function. hs's shared ownership skipped that. Git tooling (blame, bisect, editors) is far more mature. I didn't need it here, but `hs log <file>` is the only history tool I saw.
- Net for this setup: modestly better than a shared git repo, mainly because of `--check` with retry and path watches.

## 7. Features I wanted
- On a real conflict, a summary of what did and didn't land, plus an `hs land --continue` or a hint like "after fixing, run: hs land -m ... --check ...". The check command isn't remembered.
- `hs watch --path` that also matches NOTES.md lines mentioning `@a4` (mentions in the union file are how people asked me things).
- An option for a co-owner to request a Show from the other co-owner on shared files (or a default to Show when you edit a function region another co-owner landed recently).
- `hs show N --stat` to list files without the diff.
