# a3 report: scheduler capacity side

## 1. What I built

The capacity side of `src/scheduler.js` and most of `test/scheduler.test.js`:

- `plan(day) -> Plan` glue.
- Express-first and deadline-first package ordering.
- Unassigned reasons for packages that can't go at all (`staticReason`): too heavy, out of range, or every drone's direct-window check fails.
- Payload and range checks per trip (`fitsCapacity`).
- Greedy insertion. Each package either joins an existing trip or opens a new one, on any drone. Every candidate grouping is validated by a2's `scheduleDrone`.
- An insertion cost that spreads work over the drones: extra km + 0.05 × the drone's finish minute + 0.03 × the package's ETA, with express counted double. On day1 the last drone now gets back at minute 132 instead of 171 (the landed #15 baseline; pure km-minimising would give 214), and d1 no longer carries 13 of 18 packages. That costs about 8% more km.
- Clear "fleet full" reasons (`no drone has capacity left: ...`).
- `trips[].flightMinutes` for CR-1.

I pinned the Plan shape in CONTRACTS.md in my first land (#5). By the end there were 28 scheduler tests and 69 in the whole suite, all passing on main #28.

## 2. How I learned about teammates' work

- **Background feed:** I ran `hs watch --json >> .hs/feed.jsonl` in the background and read it with `grep -v settled | tail` about 8 times, at the start of each step. I looked at author, files and message to decide what to open.
- **Blocking waits:** `hs watch --path /src/scheduler.js [--path /CHANGE-REQUEST.md ...] --count 1 --timeout 600` did the waiting. It returned exactly when a2's TIMING land (#15) and pm's CR-1 (#20) arrived.
- **Reading the changes:** `hs show 15 --path /src/scheduler.js`, `hs show 16`, `hs show 22 --path ...` and `hs show 23` for diffs. I read NOTES.md after every sync, and the `incoming from teammates` list from sync and land.

The watch feed fully replaced polling. I never ran a sync just to look; every sync had a reason.

## 4. Conflicts, rebases, flips

- **Silent auto-merges (4):** #5 (over #2–#4), #9 (over #6–#8), #18 (over #17) and #25 (over #24) all merged teammates' CONTRACTS.md and NOTES.md changes. Every one ended in `landed #n` / `#n final`. The output never printed the playbook's `main moved: ... rebasing ... (this is normal)` line; I only saw `checking main #N + your changes`. It worked, but I couldn't tell that a merge had happened.
- **Real conflict 1 (#16 a2):** `test/scheduler.test.js`. a2 and I had both appended tests at the end of the file. The markers were `<<<<<<< ours` / `>>>>>>> theirs`, and the fix was to keep both sides. Cost: about 2 minutes. An append-aware merge for test files would have avoided it.
- **Real conflicts 2 and 3 (#22, then #23, a2):** `src/scheduler.js` and `test/scheduler.test.js`, the CR-1 flight-minutes duplication. I resolved #22 by keeping both field names. Re-landing then hit #23, a2's rename on the same lines, so I resolved again on a2's version. Cost: about 8 minutes, plus the duplicated work.
- **Flips / undone lands:** none. Every land settled and went final within the 10 s wait.

## 5. Friction, bugs and confusing output in hs

- **Conflict exits with code 2:** `hs land ... --check "npm test"` → `real conflicts in /test/scheduler.test.js (#16 a2): fix the <<<<<<< markers, then land again`, exit code **2**. The playbook defines 2 as "done, but read the !! lines", yet nothing was landed and there was no `!!` prefix. A failed land should be exit 1, or at least a distinct code.
- **Markers don't name the change:** the markers say only `ours` / `theirs`. The error line names `#16 a2`, but the file doesn't; `theirs (#16 a2)` would help.
- **No sign of a merge:** see section 4; the `main moved` / `rebasing` line never appeared even when files were merged.
- **Status doesn't say why there are unlanded commits:** after a rejected land, `hs status` shows `3 committed path(s) not landed` (correct) but doesn't mention the pending conflict.
- **Minor:** `hs status` said `main is at #26 or later (from your feed); this shows #25. hs fetch to update`. That was clear and nice. It suggests `hs fetch`, though `hs sync` is what I actually wanted.
- **I never used review:** I never ran `hs propose`, not even for the Plan contract, which the playbook classes as an Ask. Ship was always faster and nothing pushed back, which is why the review fields in the JSON are 0.
- **Nothing stops two people doing the same work:** a2 and I both implemented CR-1 flight minutes within about a minute of each other. hs has no claim or intent signal. A NOTES line only becomes visible after a land, so it races just like code does.

## 6. Compared with git

**Better than a shared git repo here:**
- The live feed and the blocking `watch --path` wait. With git I'd have polled `git fetch` in a loop, or someone would have had to ping me.
- `land --check` runs the tests on main + my change and retries if main moves. With git that is a pull/rebase/test/push loop that fails on non-fast-forward over and over with 5 agents pushing to one branch.
- Per-file lands plus union merge on NOTES.md meant the many concurrent CONTRACTS/NOTES edits never needed my attention. With git, every NOTES.md append would have been a rebase conflict risk.
- `hs show n --path` is equivalent to `git show`, so no gain there, but the numbered `#n` sequence is easier to cite in messages than hashes.

**Same as git:**
- Real conflicts on the same lines. Resolution is identical to git (markers, edit, re-land), and git's markers carry more context (commit subject in diff3).
- The duplicated CR-1 work would have happened with git too. Neither tool helps with intent.

**Worse:**
- Less transparency about merges (silent rebases).
- The exit-code inconsistency on conflict.
- For a human, missing familiar tooling (blame, bisect, diff3).

Overall it's somewhat better than git for this setup, mainly because of the feed, the waits and `--check`.

## 7. Features I wanted

- A lightweight claim / intent broadcast ("a3 is editing scheduler.js:plan stops mapping for CR-1") that shows up in teammates' feeds without a land.
- Append-aware or union merge for test files where both sides only add new `test(...)` blocks at the end.
- Conflict markers that name the changeset and author.
- An explicit `merged with #n (a2) in /CONTRACTS.md` line whenever land or sync auto-merges a file.
- Exit code 1 (or a dedicated code) when a land is rejected.
