# a4 report: pricing + report money (Skyhop, hs run s2-hs-2)

## 1. What I built

- `src/pricing.js`: `price(plan, day) -> { currency, prices, lines, totalCents, total }`. It also exports `priceCents`, `formatMoney` ("EUR 1,234.50"), `flightMinutesByPackage` and `TARIFF`. All money is in integer cents, with half-up rounding once per package, and `total` is the exact sum of the rounded prices.
  - Original formula (#3): 2.50 + 0.80/km (home depot to destination) + 0.50/kg, with express x1.5.
  - After CR-1 (#34, #39): 2.00 + 0.25/flight-minute + 0.40/kg, with express x1.5. Flight minutes are cumulative along the trip's flight order, with no service or waiting time, computed by a2's `geo.flightMinutesAlong`.
- Money section of the shared `src/report.js`: `formatMoney` delegates to pricing, plus `sumMoney` (cents-exact; used for the `--json` total), `moneyCell` (a right-aligned price column) and `moneyLines` (a footer with the standard/express split and the total).
- `test/pricing.test.js` covers:
  - the formula and rounding;
  - flight minutes (order-dependent, speed-dependent, service time not counted);
  - errors;
  - the real `loadDay(day1)`;
  - the real `plan(day1)`;
  - a cross-check against the scheduler's `trip.flightMinutes`.
- The money tests in `test/report.test.js`.
- The pricing section of CONTRACTS.md was pinned in the same changeset as the code, both times.
- The final state of main is #39: 90 tests pass, 0 fail, 0 skipped. On day1, `node src/cli.js plan fixtures/day1.json` totals EUR 81.99, and that equals the sum of the `--json` prices.

## 2. How I learned about teammates' work

- **`hs watch --path <file> --count 1 --timeout N`** was my main tool. I used it to wait for `/src/scheduler.js` (it returned #11, then #15), for `/CHANGE-REQUEST.md` (it returned #17, and later #28, which was CR-1), and for a final idle wait that timed out.
  - This replaced polling completely. It returns immediately if the change already landed, and the matching line it prints is enough to decide what to do next.
- The **background feed** (`hs watch --json >> .hs/feed.jsonl`) worked and recorded 38 changesets with no reorgs. I only read it a couple of times with `tail`. In practice, two outputs were better live summaries:
  - the `incoming from teammates (n): #x author files :: message` block that `sync` and `land --check` print;
  - the blocking `watch --path`.
- I used **`hs show N` / `hs show N --path X`** to read diffs: #2 (a5's report skeleton), #4 (geo), #10 (report layout) and #17. `hs show` with a diff was the most useful learning tool.
- **NOTES.md** (union merge) carried the intent behind the shapes. I also read CONTRACTS.md sections after each sync.
- `hs log -n N --oneline` was a good sanity check, and its `[final]` tags are clear.

## 4. Conflicts, rebases, flips

- **Auto-rebases**: none of my lands printed `main moved ... rebasing`. Every `land --check` simply synced first and listed the incoming changesets, for example "checking main #33 + your changes" with #30–#33 incoming, and then landed. That included report.js, which a5 changed in #10, #17, #31 and #33 while I was also editing it; 3-way merges were silent and correct every time.
- **Real conflicts**: 0 for me. a2 reported one in NOTES with a3's #30 on scheduler.js while implementing CR-1 ("resolved the conflict by taking a3's line").
- **Flips / undone lands / reorgs**: 0. Every land ended `#n final` within the 10 s wait. The feed had no `reorg` lines.
- **Check failure (1)**: my first `moneyCell` land failed `--check` because a5's layout test pinned `EUR 3.50`. The output was clear: `!! check failed (exit 1, 0.4s) on main #11 + your changes: not landed. Your files now include main; fix and land again`. I fixed it and landed #13.

## 5. Friction, bugs, confusing output

- **No Show or review was ever triggered for shared files**, because I'm a co-owner of `report.js` and `report.test.js`. That's correct per `.hsowners`, but it means I edited a5's layout lines (the `formatMoney` → `moneyCell` call and two test regexes) without hs telling a5. The only notice was my NOTES line. For a co-owned file you can't express "the a5 half" vs "the a4 half". Section-level ownership would have made this a Show.
- **CR-1 triple implementation**: three agents built flight minutes at the same time (a3 #30, a2 #35, me #34), and a2 hit a real conflict with a3. hs did nothing wrong here, but nothing in it helps you claim or announce in-progress work either. A NOTES line is only visible after a land, which takes about 3 s, and by then others were already coding.
- **Path spelling is inconsistent**: `watch --path /src/scheduler.js` and the feed use a leading slash, while `show N --path src/geo.js` worked without one. Both forms seemed to work, but I wasn't sure which was canonical.
- **`watch --timeout` exits 2 on timeout** ("watch: timed out after 480s with 0 matching changeset(s)"). That's documented, but 2 is also the code for "done, read the `!!` lines" elsewhere, so a script can't tell the two cases apart by exit code alone.
- **The feed file was less useful than expected**: `settled` lines are interleaved and the messages are long and unwrapped. `hs log --oneline` is the better human view.
- Nothing broke. I had no stalls, no unavailable files and no provisional states.

## 6. Compared with git

Better than a shared git repo here:

- **Landing is one command that rebases, runs tests on the merged tree and pushes.** With git, five agents pushing to one branch would mean repeated `git pull --rebase && npm test && git push` loops, with rejected pushes whenever someone got in first. I never had a rejected land or a retry loop.
  - `--check` running on "main + your changes" is exactly the guarantee I wanted. It caught the regex break before it reached main.
- **`watch --path X --count 1`** has no git equivalent short of polling `git fetch`. Blocking on "scheduler.js landed" was very effective.
- **The `incoming from teammates` summary on every sync/land** is a much better catch-up view than `git log ORIG_HEAD..`.
- The settled/final status was always immediate and unambiguous.

Same or worse:

- Union merge on NOTES.md is possible in git with `.gitattributes merge=union`, so that is not a unique advantage.
- Git's `git diff`/`git log -p` are as good as `hs show`, and more familiar.
- Coordination waste (the CR-1 duplication) would have happened identically with git. hs's speed didn't prevent it, because nothing in either tool announces intent.
- Shared-file ownership: git has CODEOWNERS plus PRs, which is heavier but would have flagged my edits to a5's half more visibly.

Overall, for 5 parallel agents on overlapping files, hs was noticeably smoother than a shared git branch, mainly through the land loop and blocking waits. The hard coordination problem (who does what after a change request) is unchanged.

## 7. Features I wanted

- **An intent/claim broadcast**, such as `hs claim "CR-1 flight minutes in pricing"` or a WIP announcement that shows in teammates' feeds before you land. This would have prevented the CR-1 triple work.
- **Section-level ownership or Show** inside a shared file, such as `report.js#money a4` and `report.js#layout a5`.
- `watch --path` with the incoming diff inline (`--show`), to save the `hs show` round-trip.
- A human-readable `watch` feed mode that drops `settled` lines.
- A distinct exit code for a `watch` timeout.
