# a2 evaluation report (geo + scheduler timing)

## 1. What I built

- `src/geo.js` (#4, #35): `distanceKm` (haversine, R=6371), `travelMinutes`, `routeLengthKm` (closed trip),
  `orderRoute(depot, items, pointOf?)` (nearest neighbour + 2-opt, deterministic), and for CR-1
  `flightMinutesAlong(depot, points, speedKmh)`. Tests: `test/geo.test.js` (incl. brute-force comparison
  and a 2-opt local-optimality check).
- Timing section of `src/scheduler.js` (#11, #22, #24, #27, #35): `buildTrip(day, drone, pkgs, startMin)`
  (route order with geo/EDF/earliest-open candidates, keeps the earliest-return feasible one; range check;
  windows with waiting, first-stop wait moved to the ground; day-length check; `etas`, `waitMinutes`,
  `flightMinutes`; human-readable failure reasons such as `impossible window [5, 4] for w0`),
  `nextStart(trips)`, `placeTrip(day, drone, pkgs, trips)` (earliest non-overlapping slot, gap filling).
  Tests: `test/scheduler-timing.test.js` (kept apart from a3's `scheduler.test.js` to avoid merges).
- CONTRACTS.md sections "geo" and "scheduler timing (a2)" pinned in the same changesets as the code.
- Final state: main #39, `npm test` 90/90 pass, `node src/cli.js plan fixtures/day1.json` prints 18 delivered on
  13 trips, p19 unassigned (too heavy), EUR 81.99 under the CR-1 tariff.

## 5. Friction, bugs, confusing output

- After the real conflict, `hs status` said `6 committed path(s) not landed ... commit /src/scheduler.js` with no
  hint that scheduler.js still contained conflict markers; I had to grep for `<<<<<<<` myself. A "conflicted" state
  in status would help (git shows "both modified").
- The conflict exit was code 2 with only one line on stderr; the playbook says 2 = "done, read !! lines", but
  nothing was done (not landed). Mildly confusing.
- The rebase on a shared file is invisible in `land --check` output (see 4). I'd like an explicit
  `merged with #19 a3 (3-way, clean)` line per file.
- `hs review '#25' comment -m ...` needed quoting in fish/bash (`#` starts a comment unquoted). Accepting `25`
  without `#` would avoid this footgun.
- Background `hs watch --json` exited cleanly when I ran `hs watch --stop` — good.

## 6. Compared with git

Better than a shared git repo here:
- No push races: in git, five agents pushing to one branch would get many `non-fast-forward` rejections and
  `pull --rebase` loops; here `land --check` did fetch + 3-way merge + test + publish in one step, and four of my
  lands rebased over a3's concurrent scheduler.js edits without me doing anything.
- The feed and `watch --path X --count 1` are a real improvement over polling `git fetch`/`git log` — waiting for
  a3's plan() or for the CR was one blocking command.
- `--check` on the merged tree is effectively a pre-merge CI per land; with git you'd need a CI + merge queue.
- union merge for NOTES.md was painless (git supports `merge=union` too, but few set it up).

Same or worse:
- The real conflict experience is roughly git's (markers, fix, re-land), minus git's tooling around it
  (`git status` conflicted state, `mergetool`, `git diff --cc`).
- Coordination failure on CR-1 (three agents doing flight minutes) is not something either tool solves; hs's
  feed made the duplication visible faster (I saw #29/#30 in the conflict message), but didn't prevent it.
- Invisible merges on a shared file make me slightly less sure what I actually landed than a `git log --graph`.
- With git + PRs per agent this would be slower but more reviewable; with git trunk-only it would be noticeably
  more friction.
