# a3 report: scheduler, capacity side

## 1. What I built

The capacity half of `src/scheduler.js`, plus `test/scheduler.test.js` (17 tests) and the
`scheduler (a3)` section of CONTRACTS.md, where the `Plan` shape is pinned.

- `plan(day) -> { trips: [{ drone, depot, start, end, packages, etas, flightMinutes, km, loadKg }], unassigned: [{ id, reason }] }`.
- `capacityReason`: for packages no drone can ever fly. Reasons: too heavy for every drone,
  out of range for every drone that can carry it, or no drones available.
- `groupTrips`: groups packages into trips that fit payload and range. Express packages are
  placed first and never share a trip with standard ones. Packages are added by cheapest
  insertion (extra km). Packages whose windows would make a trip hover more than 15 min are
  kept apart, using a2's `waitMinutes`.
- The `plan()` loop: for each drone it flies the trip that can leave soonest, with express
  first on ties. A standard trip may fill an idle gap before a late express window, but
  only if it doesn't delay the express trip. A group that timing rejects is split into
  single trips. Any single that still fails is retried on every other capable drone through
  a2's `placeTrip`, which can use idle gaps. Only after all that does it go to `unassigned`,
  with the timing reason.
- I consume a2's `buildTrip`, `nextStart`, `placeTrip`, `waitMinutes` and `flightMinutes`
  (CR-1) unchanged.

Final main (#39): `npm test` passes all 90 tests. The CLI on day1 delivers 18 packages on
13 trips, and p19 is unassigned as too heavy.

## 2. How I learned about teammates' work

- **Feed.** I ran a background `hs watch --json >> .hs/feed.jsonl` and read it with `tail`
  every few minutes, usually just before landing.
- **Incoming lists.** The `incoming from teammates` list printed by `hs sync` and `hs land`
  was the most useful single output: one line per changeset, with its files and message.
- **Diffs.** I used `hs show <n> --path <file>` for the diffs I depended on (#11, #22, #35)
  and `hs cat` to get a2's clean version of the file during the conflict.
- **NOTES.md.** It carried the intent: a2's split proposal, a1's frozen Day, and the
  CR-1 ownership calls.
- **Waiting.** For waiting I used `hs watch --path /CHANGE-REQUEST.md --count 1 --timeout 300`
  and `hs watch --path /src/pricing.js --count 1`. These returned the moment the land
  happened, which was nicer than polling.

Yes, the watch feed fully replaced polling for me. I never ran a sync just to look.

## 4. Conflicts, rebases, flips

- **Real conflict (one).** My first land after #11 stopped with `real conflicts in
  /CONTRACTS.md (#11 a2), /src/scheduler.js (#11 a2)`. Both of us had written a whole new
  file from the 2-line stub, so a 3-way merge could not help. The markers left in the
  worktree were whole-file `<<<<<<< ours` / `>>>>>>> theirs` blocks. I rebuilt the file
  from `hs cat /src/scheduler.js` plus my capacity block, in about 5 minutes. This was
  avoidable: a2 and I could have landed the empty section skeleton first.
- **Check failure (one).** The first `--check` failed on main #9 because a5's new

- **Auto-rebases.**
  - Two were real same-file merges with a2 on scheduler.js: #23 over #22 and #25 over #24.
    Both were silent and clean, because we each kept to our own block.
  - Four other lands rebased over unrelated teammate lands (#15, #19, #30, #36), also

## 5. Friction, bugs, confusing output

- **Conflict markers.** `real conflicts in ...: fix the <<<<<<< markers, then land again`
  doesn't tell you that the markers can span the whole file when both sides replaced it.
  My merged CONTRACTS.md also kept a stray `<<<<<<< ours` inside a section I had already
  replaced. I had to grep for markers myself. hs could refuse to land a file that still
  has markers in it, or list them.
- **`status` behind the feed.** `hs status` printed `main is at #38 or later (from your
  feed); this shows #37. hs fetch to update`. That is clear, but it's odd that status says
  "fetch" when the playbook's verb for this is `sync`. I wasn't sure which one to run.
  `sync` worked.
- **Feed lines are long.** Every changeset line carries a 52-char hash, which I had to cut
  away to read the feed with `tail`.
- **No sign of a missed NOTES line.** hs had no way to tell me that a4's #29 NOTES line
  (sent about 10 s before my land) answered the exact thing I was about to land. The
  incoming list showed `#29 a4 /NOTES.md :: NOTES: CR-1 plan — ... a2/a3 no change
  needed`, but only after my land had already gone through.
- **Watch exit codes.** `hs watch ... --timeout` exits 2 on a timeout. That's documented,
  but in a shell `&&` chain it looks like a failure.

## 6. Compared with git

**Better than git:**

- `land --check` checks main plus my changes and retries when main moves. That is a merge
  queue with a pre-merge CI run for free. With git, 5 agents pushing to one branch would
  mean `git pull --rebase && npm test && git push` loops and rejected pushes. I never saw a
  rejected push.
- The incoming list and the watch feed are much better awareness than `git fetch && git
  log`. I learned about teammates' work within seconds, with their messages. Blocking on
  `watch --path` is something git simply doesn't have.
- `merge=union` on NOTES.md worked flawlessly with 5 writers. Git can do this too with a
  `.gitattributes` `merge=union`, but here it was set up already.

**About the same as git:**

- Same-file 3-way merges: clean when we kept to separate blocks, a manual conflict when we
  didn't. Git would behave identically.

**Worse than git:**

- I can't run `git diff`/`blame`/`log -p` style archaeology with the same depth or
  familiarity, though `hs show`/`hs log <file>` covered what I needed.
- The conflict UX is coarser than git's.
- Provisional/settled/final is extra mental load, though in practice everything was final
  within seconds, so it never mattered.

**Overall:** for this setup (5 agents, parallel, shared files, frequent small lands), hs was
moderately better than a shared git repo. The win is mainly coordination speed and the
`--check` landing, not the merging itself.
