# a5 report: Skyhop (hs run s2-hs-2)

## 1. What I built

- `src/cli.js`: `plan <dayfile> [--json]`, plus an in-process `run(argv, io) -> exitCode`. It runs loadDay -> plan -> price -> report. It exits 2 with usage on bad arguments and 1 with `error: <file>: ...` on an unreadable file or a DayError.
- `src/report.js`, layout and JSON half: `toJson` keeps the four pinned keys and passes through depot/end/km/loadKg/etas/flightMinutes/waitMinutes. `renderReport` prints per-drone trips, then one row per stop (kg, priority, eta, flight minutes, price), then unassigned with reasons, then a4's money footer. I proposed the a4/a5 split in #2 and a4 adopted it in #5.
- `test/integration.test.js`: runs the CLI on day1 and every `edge-*.json`. It checks these invariants:
  - every package appears exactly once, either in a trip or unassigned with a reason;
  - each trip is within payload and range, using its own haversine over the flight order;
  - no trip of a drone overlaps the next one (service minutes included);
  - every eta falls inside its window, and every trip ends before the day does;
  - every delivered package is priced above 0, and total equals the sum of prices;
  - p19 is unassigned as too heavy;
  - the output is deterministic, and in-process `run()` gives the same JSON as the binary.

  It also has an **independent CR-1 price check** (my own flight-minute formula), which turned itself on when a4's pricing landed.
- Fixtures:
  - `edge-unreachable`: cases out of range, too heavy, and a window after the day ends;
  - `edge-empty`;
  - `edge-invalid`: 4 fatal errors;
  - `edge-busy`: 1 drone, 9 trips, express first, an empty window.
- Layout tests in `test/report.test.js`. The CLI section of CONTRACTS.md is pinned (#18).
- End state: main #39, `npm test` passes 90 of 90, CLI exits 0 on day1 (18 delivered, 13 trips, p19 unassigned, EUR 81.99 under CR-1).

## 2. How I learned about teammates' work

- A background `hs watch --json >> .hs/feed.jsonl` feed, which I read with `tail`.
- `hs watch --path /src/scheduler.js --count 1` and `--path /CHANGE-REQUEST.md --count 1` to block on a dependency or a CR. This was the main tool, and it worked very well: no polling loops at all.
- The "incoming from teammates" lists printed by `hs land --check` and `hs sync`. These were the best single summary.
- `hs show 5 --path src/report.js` to see what a4 did to my file.
- NOTES.md, which carried the real coordination: shapes, who does what. `hs log --oneline` and `hs status` near the end.

The watch feed fully replaced polling. In practice I used the blocking `watch --path ... --count 1` more than the background feed file.

## 5. Friction, bugs, confusing output

- `hs watch --count 2 --timeout 600` with only 1 match prints `watch: timed out after 600s with 1 matching changeset(s)` and exits 2. That is clear. The friction was that my tool harness killed or backgrounded the 600 s call, so a full-length timeout is awkward for agents. A `--timeout` a bit under the harness limit would be wise to document.
- The `watch --path X --count 1` semantics ("counts everything after your synced base") bit me once. I waited for scheduler.js and got a2's timing-only #11 instead of a3's plan(), so I had to `sync` and wait again. That is expected behaviour, but a `--message`/`--author` filter would have let me wait for "a3's plan()" directly.
- Review targets need the `#`: `hs review '#34' comment`. In fish/zsh scripts, a bare `#34` is a comment, so it must be quoted. Easy to trip on.
- I was never asked to review a4's Show-style edits to the co-owned `report.js` / `report.test.js`; `hs status` showed nothing waiting. I suspect co-owners count as owners, so a4's edits were Ships. That is reasonable, but it means co-owned files never generate reviews.
- No confusing output otherwise. `land --check` output (checking main #N + your changes, incoming list, landed, pushed, final) is very readable.

## 6. Compared with git

**Better with hs here:**
- `land --check "npm test"` ran my tests on *latest main + my change* and landed atomically. With git, five agents pushing to one branch would have meant fetch, rebase, test, and push-rejected retries. That is the biggest win.
- The blocking `watch --path` is a real primitive git lacks. With git I would have polled `git fetch` in a loop.
- Per-file landing with union-merged NOTES.md meant zero conflicts on the coordination log, which every agent appended to constantly. In git, NOTES.md would have conflicted on nearly every push without a custom merge driver.
- Changeset numbers (#n) in messages made cross-referencing easy in NOTES.

**Same or worse:**
- I lost nothing to hs, but git's tooling (blame, bisect, branches for experiments) was not needed in this short run, so I can't judge those gaps.
- Settled/final added little for me since everything finalized in seconds.

## 7. Features I wanted

- `hs watch --author a3` / `--grep plan` filters, so I can wait for a specific teammate's work rather than any change to a path.
- A short `hs show N --stat`-like summary in feed lines of how many lines changed.
- Let co-owners request each other's review on shared files (or make it optional), so edits to `report.js` show up for the other owner.
