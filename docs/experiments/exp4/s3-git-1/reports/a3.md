# a3 report: scheduler (git arm, s3-git-1)

## 1. What I built

`src/scheduler.js` with `plan(day) -> { trips, deliveries, unassigned }`, plus `test/scheduler.test.js` (15 tests, including an independent invariant checker that re-derives distance, payload, range, windows, day end, no double delivery and full accounting). The scheduler is greedy. Packages are sorted express first, then by earliest deadline, then by id. The drone that is free earliest builds its next trip. Each trip is seeded with the most urgent package that drone can serve, and the start is delayed so the drone does not hover at the first stop. The trip then grows by cheapest feasible insertion, with at most 15 minutes of total hover per trip. Drones can make several trips. Unassigned reasons start with stable keywords: `too heavy`, `out of range`, `window impossible`, `no capacity`, `invalid`. Timing uses a2's `geo.tripTimeline`, and the scheduler accepts a1's frozen `Day` as well as a raw day file. I pinned the Plan shape in CONTRACTS.md in the very first push (4c10e65), before any code.

Final main is 1b560de: 69/69 tests pass, and `node src/cli.js plan fixtures/day1.json` delivers 18 of 19 packages in 13 trips. The one unassigned package is p19 (11.5 kg, too heavy for every drone).

## 2. How I learned about teammates' work

- `git fetch -q && git log --oneline --stat HEAD..origin/main` before every pull: about 8 times. The `--stat` output was the most useful signal, because it showed which modules had landed and whether CONTRACTS.md and NOTES.md had changed.
- `git show <sha>` and `git show <sha> -- CONTRACTS.md | grep '^[+-]'` to read contract changes (e.g. 5dbf240, the geo window-aware tripTimeline).
- `git diff HEAD origin/main -- NOTES.md | grep '^+-'` to read new NOTES lines before pulling. In practice, NOTES.md was the real communication channel. I also read NOTES.md and CONTRACTS.md in full after pulls.
- The playbook's bounded fetch loop (20 s sleep) twice near the end, about 5 minutes total waiting. Otherwise I never had to wait: model and geo had landed before my first code push, so polling cost me very little.

## 4. Conflicts, rejected pushes, rebases

- 7 push attempts, 6 successful. Every pull before a push rebased my single commit (`Rebasing (1/1)Successfully rebased and updated refs/heads/main.`): 6 times in total, with no conflicts. NOTES.md union-merge worked, even though everyone appended to it constantly.
- 1 rejected push (on the a0cf71a change). Someone pushed between my `git pull && npm test` and my `git push`. Rerunning the same line worked first try. That window is about the length of the test run (now about 1 s), so the race is real but cheap.
- 0 real conflicts. Module ownership was clean, and the only shared files were NOTES.md (union) and CONTRACTS.md (separate sections).

## 5. Friction and confusing output

- The rejected push: I piped through `tail -1` and saw only `hint: See the 'Note about fast-forwards' in 'git push --help' for details.`. That line does not say the push failed. I had to infer it from the missing `main -> main` line. That is one confusing message, and the cause was partly my own truncation.
- `git pull` output when only my commit was rebased mixes the fetch lines (`eb09110..6f2cd37 main -> origin/main`) with the rebase line. It is fine once you know the format.
- Nothing tells you who is mid-change on what. I learned that a2 was reading my simulate() only after a2 had pushed a note about it.
- Polling: there was no way to say "wake me when NOTES mentions a3 or when CONTRACTS changes". I used `sleep 20` loops instead.
- `git pull && npm test && git push` is not atomic. "Tests passed on top of main" is only true at the moment of the pull, and main can move before the push lands.

## 6. Compared with an ideal tool

For five agents with clean module ownership, git was adequate, closer to good than bad. An ideal tool would have done these things better:
- **Push notifications or a feed** filtered by path or mention (CONTRACTS.md scheduler section, NOTES lines naming a3, `src/geo.js`) instead of fetch loops.
- **An atomic "rebase, test, land" step** (a merge queue) so the pull/push race cannot happen and "tested on latest main" is guaranteed.
- **First-class contracts or interfaces.** CONTRACTS.md worked socially, but nothing checks that code matches it. A tool that flags "you changed an exported function's shape that a3 consumes" would help.
- **Addressed messages** separate from the code history. NOTES.md as a union-merged log works, but it pollutes diffs, and you must diff it by hand to find lines meant for you.
- **Presence and intent**: "a2 is editing geo.js tripTimeline" would have avoided a race between a2 changing tripTimeline and me starting to depend on it (it worked out, and a2 froze it after the fact).

## 7. Features I wanted

1. `git watch` / subscribe to paths or mentions, blocking until a match (replacing sleep loops).
2. An atomic land: rebase onto the latest main, run tests, and push only if main hasn't moved (or retry automatically).
3. Clearer rejection text in the last line of `git push` output.
4. A structured team message channel (with addressees) that is not a merged file.
