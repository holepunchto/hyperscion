# a5 report (integrator, git arm)

## 1. What I built

- `src/cli.js`: `plan <dayfile> [--json]`. It runs loadDay → plan → price → renderReport, with `runPipeline`, `toOutput` and `main(argv, io)` exported. Exit codes: 0 ok; 1 for an unreadable file, bad JSON or `DayValidationError`; 2 for usage errors or unknown options; 3 for internal errors. `--json` follows the pinned contract and adds `currency`, `deliveries` and `report` (a4's `reportData`). `--help` prints the usage.
- `test/integration.test.js` (13 tests). Every check is computed independently with my own haversine: each package appears exactly once, every unassigned package has a reason, payload and range are within limits, a drone's trips don't overlap, arrive times are recomputed from `trip.start` and match windows, trips end before the day ends, the reason keywords are right, and each reason is actually true. It also checks that prices follow a4's formula, that totals add up, that p19 is unassigned as too heavy, that express packages are delivered, that the human report is complete and agrees with `--json`, and that output is deterministic. On top of that it runs 60 seeded random days through the whole pipeline, plus a day with no drones.
- `test/cli.test.js`: unit tests with stub modules.
- Fixtures: `edge-unassignable.json`, `edge-empty.json`, `edge-invalid.json`, `edge-capacity.json`.
- I pinned the cli section of CONTRACTS.md.
- Final state: main at 5e820f4, `npm test` passes 77/77 and the CLI exits 0 on day1.

## 2. How I learned about teammates' work

- After every pull I ran `git log --oneline --stat HEAD..origin/main` (the pull output alone shows only a sha range).
- I used `git show <sha> -- CONTRACTS.md NOTES.md` to read the contract changes. Mostly I read CONTRACTS.md and `tail NOTES.md` after pulling rather than the code diffs.
- For idle waiting I used the playbook's bounded loop (`fetch -q` every 20 s, break on new commits), 5 loops of up to 9 min each.
- Polling time: about 35 min of wall-clock waiting, but little attention, because it ran as a blocking command. The `minutes_lost_to_hs` figure below (8) counts only active attention, not this blocking wait.
- The fetch-loop output gives only one-line subjects. NOTES.md carried the real meaning.

## 4. Conflicts, rejected pushes, rebases

- 12 push attempts and 10 landed. 2 were rejected with `! [rejected] main -> main (fetch first)`: someone pushed between my `pull && npm test` and my `push`, roughly a 1–2 s window while tests ran. I re-ran the same line and it worked both times.
- 7 pulls rebased my commits (`Successfully rebased and updated refs/heads/main.`). All were clean.
- 0 real conflicts, because NOTES.md is union-merged and each file has one owner.
- Origin outage: at about 00:00–00:03 every fetch failed with `fatal: '.../origin.git' does not appear to be a git repository`. I had nothing unpushed, so the loop just kept retrying. The cost was only that my loop printed 9 copies of a 4-line error.

## 5. Friction and confusing output

- When a push is rejected inside `pull && npm test && git push 2>&1 | tail -1`, the tail shows only `hint: See the 'Note about fast-forwards' in 'git push --help' for details.`, which is the least informative line. I had to infer the rejection. (That's partly my own fault for using `tail`.)
- The outage message reads like a configuration error ("does not appear to be a git repository ... correct access rights"). It doesn't say "server unreachable, try later". I only knew it was transient because the playbook's table told me.
- `git pull` output (`From ... d5d9f26..bb451bf main -> origin/main`) doesn't say what landed. I always needed a second `git log --stat` command, run before the pull, because afterwards `HEAD..origin/main` is empty and I had to remember the old sha.
- Nothing tells me whether a teammate's push was tested, or whether main is currently green. I re-ran the full suite on every pull to find out.
- There's no way to wait for a push. The polling loop is a workaround.

## 6. Compared with an ideal tool

- The ideal tool would push events: "a3 landed 418c052 touching src/scheduler.js; CONTRACTS scheduler section changed". With that I'd react within seconds, with no sleep loops and no 9-minute idle waits.
- Landing would be atomic: test against the exact tip and land, or rebase automatically and re-test, all in one step. That would remove the pull/test/push race that caused both of my rejections.
- It would track contracts: show me "CONTRACTS.md section 'scheduler' changed" as a structured diff and know who depends on it. Instead I grepped CONTRACTS.md by hand.
- It would show presence and ownership. a3's machine dying was visible only through a NOTES line from a3b. The tool should have shown "a3 offline since X; last state pushed = 418c052; no unpushed work known".
- It would show CI status per commit, so I could know main was green without running the tests myself.
- Overall, git was adequate here because ownership was clean and NOTES.md was union-merged. The coordination layer (NOTES.md plus polling) was hand-built on top of it, though.

## 7. Features I wanted

- A blocking `git wait origin/main [-- paths]` that returns when something lands.
- `git pull --summary`, showing a stat of what came in.
- An atomic test-and-push.
- Status of the remote (up/down) and of teammates (alive/offline).
- Contract or section-level change notifications.
- Green/red status per commit on main.
