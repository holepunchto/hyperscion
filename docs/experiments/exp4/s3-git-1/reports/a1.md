# a1 report (git arm): src/model.js

## 1. What I built
`src/model.js`: `loadDay(json|string)` and `loadDayFile(path)` return a deep-frozen `Day`. It keeps the raw field names and arrays in file order, passes unknown extra fields through, and adds derived fields: `drone.home {lat,lon}`, `pkg.express`, `pkg.earliest/latest` (window or 0/dayLength), and `depotsById/dronesById/packagesById`. It also exports `DayValidationError` with `.errors[]`, which collects every fatal problem (bad JSON, missing or duplicate ids, unknown depot with the list of known depots, non-positive numbers, bad lat/lon, unknown priority, malformed window). Impossible windows and too-heavy packages are deliberately not fatal. `test/model.test.js` has 13 tests, including one that runs over every fixture: `edge-invalid*` must throw, and must report all 5 problems. The CONTRACTS.md "model" section was pinned in my first land.

## 2. How I learned about teammates' work
- After every land: `git log --stat --format='%h %an %s' <old>..HEAD~1` to see what my pull had brought in, plus `tail NOTES.md`.
- `git show <sha> -- CONTRACTS.md NOTES.md` once, for a5's first push.
- I grepped teammates' source (`grep -n "day\." src/pricing.js src/cli.js ...`) to see how they actually used `Day`.
- I used the playbook's bounded fetch loop twice (`git fetch -q; git log HEAD..origin/main | grep -q . && break; sleep 20`). Both times it exited within about 1 to 2 iterations because teammates push often.
- Polling time was small, about 1 to 2 minutes total. The whole run took about 3 minutes of wall clock.

## 4. Conflicts, rejected pushes, rebases
- 4 lands (4929915, 6a53e8f, a4fc48b, 7a3860f). Each `git pull` rebased my single commit onto new teammate commits ("Rebasing (1/1)Successfully rebased"), so there were 4 auto-rebases.
- 0 rejected pushes and 0 conflicts. NOTES.md union merge worked silently, and CONTRACTS.md edits from different owners touched separate sections.
- No outages or "things going wrong" were observed in my run.

## 5. Friction and confusing output
- `Rebasing (1/1)Successfully rebased and updated refs/heads/main.` has no newline between the two parts. That is cosmetic, but it doesn't say *what* I was rebased onto. I had to diff `<old>..HEAD~1` myself to see the teammates' commits that came in.
- `git pull && npm test && git push` is a race window. Nothing tells me whether someone pushed between my test and my push, except the push being rejected. It wasn't rejected this run.
- To know "what changed since I last looked" I had to remember old shas myself (`a4fc48b..HEAD~1`). There is no per-reader "unread" marker.
- `git log --stat` tells me which files changed, but not whether a change touched *my* interface (e.g. a call to `loadDay`). I grepped for that by hand.
- I had no git-level signal that a teammate had read or adopted my contract change. I only inferred it later from their commit messages.

## 6. Compared with an ideal tool
With 5 parallel agents and shared CONTRACTS/NOTES, an ideal tool would:
- push a feed of landed changes to me, filtered to "touches my module or calls my API", instead of me running a fetch/sleep loop;
- run the full test suite on the merged result at land time and atomically refuse it if the suite fails. That closes the pull-test-push race;
- after each rebase, show "you were rebased onto: a3 9508642, a5 b0925bc", with their messages;
- track interface (contract) changes as first-class objects, with acknowledgements from dependents.

Here git was adequate because ownership was clean (one owner per file), the union merge on NOTES.md removed the main conflict source, and the team pushed small and often.

## 7. Features I wanted
- `git log --since-last-pull`, or an "unread" marker per clone.
- Dependency-aware notifications ("someone changed code calling `model.loadDay`").
- Server-side test gate on push.
- Rebase output that lists the upstream commits I was rebased onto.
