## 1. What I built

`src/geo.js` and `test/geo.test.js` (13 tests), plus the geo section of CONTRACTS.md.
- `distanceKm` (haversine, R = 6371), `travelMinutes`, `routeLengthKm` (closed trip).
- `orderRoute`: nearest-neighbour, then 2-opt. Deterministic, never mutates its input.

- Every function takes depots, `drone.home` or packages directly.

## 5. Friction and confusing output

- `git pull -q && ... && git push -q` hides whether a rebase happened and whether the push went through. I had to run `git status -sb` to confirm `## main...origin/main`. That was my fault for using `-q`, but quiet mode drops exactly the signal you need.
- The git output itself: `Rebasing (1/1)Successfully rebased...` has no newline between the two messages. That's cosmetic but sloppy.
- `git log --stat HEAD..origin/main` shows files touched but not intent. Whether a commit affects me depends on whether the commit message names an interface, and NOTES.md lines do that better than the log. So I read two channels for one question.
- To see only the new NOTES lines I used `git diff HEAD origin/main -- NOTES.md` or `git show <sha> -- NOTES.md`. That's a workable idiom, but you have to know it.
- Nothing tells you that someone started depending on your function. I found out a3 adopted `tripTimeline` only because I happened to diff a0cf71a.
- Waiting needs a hand-written fetch/sleep loop.

## 6. Compared with an ideal tool

- An ideal tool would **push notifications** to me ("a3 landed scheduler.js, which now imports geo.tripTimeline") instead of me polling `fetch` every 20 s.
- It would **link contracts to code**. With one map of which exported symbols each module consumes, it could tell me when a consumer starts using an export and warn me before I change one. Under git, CONTRACTS.md is prose and nothing enforces it.
- It would **run the tests on the would-be-merged state server side** and reject a red push. Under git each agent has to remember `pull && npm test && push`, and a test run on a stale pull is still racy.
- It would **put the team log in the tool** as structured messages, not an append-only markdown file. Git does handle the file itself well enough, thanks to the union merge.

To be fair: for this run git was adequate. Ownership was split by file, so conflicts never happened and rebases were trivial. The costs were in awareness (polling, two channels to read), not in merging.

## 7. Features I wanted
