# a4 report: pricing + report

## 1. What I built
- `src/pricing.js`: `price(plan, day) -> { currency:'EUR', prices, total, lines }` and `pricePackage(pkg, km)`. The formula is 2.50 + 0.40/km + 0.30/kg + 3.00 for express. Each price is rounded half-up to cents, and the total is the sum of the rounded prices. It was pinned in CONTRACTS.md in my first land (#3). km was first measured from the delivering drone's home depot. After review (P1 -> #27) it is measured from the nearest depot.
- `src/report.js`: `renderReport(plan, prices, day)` prints a text report. It lists every drone (idle ones too), its trips with depart/back times, km and load, and its stops with ETA, weight, price and EXPRESS/window/EARLY/LATE flags. It also lists unassigned packages with their reasons and the totals. `reportData(...)` returns the same content in a form that serializes to JSON. The report uses the scheduler's `stops[].arrive`/`end` when they are present. Otherwise it computes them with `geo.tripTimeline`.
- I made a small Show change to a5's `src/cli.js` (#23): `--json` now includes `report`.
- `test/pricing.test.js` and `test/report.test.js`: unit tests, plus a real scheduler→price→report run on day1. On main #27, 70/70 tests pass and the CLI report on day1 looks right (18/19 delivered, p19 too heavy).

## 2. How I learned about teammates' work
- I ran a background `hs watch --json >> .hs/feed.jsonl` and checked it with `tail`. I also read the `incoming from teammates` lists from `sync`/`land`. The other sources were `hs show <n>` (and `--path`), CONTRACTS.md and NOTES.md (where a1 and a5 left me @a4 notes), and `hs watch --path /src/scheduler.js --count 1` to wait for the scheduler.

The second one printed `watch: no peers yet, waiting...` and never wrote anything again, even after the hub came back. I only noticed because `status` said `main is at #16 or later` while my feed was stuck. I had to run `hs watch --stop` and restart it. a5 reported the same thing in NOTES.

## 4. Conflicts, rebases, flips
- **Undone land:** while the hub was down, `land --check` printed `landed #12` and `!! no peers online: landed locally only` (exit 2). But #12 already existed on main (a1's NOTES change). When the hub came back, `hs sync` said `restored your land that a concurrent land undid (conflict); land it again`. I re-landed it as #21 with no problems. The word "(conflict)" worried me, but there was no file conflict.
- **Auto-merge:** my NOTES.md change was union-merged during sync (`1 merged with theirs`). That was fine.
- **Approval reset:** P1 rev 0 was approved by a5. `hs land --check` then merged main #25/#26 into my files and refused: `not landed, needs review: content changed since P1 was reviewed: propose again`. I re-proposed as rev 1, a5 re-approved, and it landed as #27.
- No real conflict markers.

## 5. Friction, bugs, confusing output
1. The watch feed died or hung across the hub outage (see 2). It was silent: no error, and it never reconnected.
2. `hs sync` with the hub down printed `no peers found, using local state` / `up to date with main #11` with exit 0, while my feed already showed #16. "up to date" is wrong there.
3. `hs push` with no peers printed a raw stack trace: `hs: Error: no peers found\n at file:///.../lib/cli.js:1384:46 ...` (exit 1). Later it printed `push timed out`.
4. Offline `land` reuses a seq number (`landed #12`) that already exists on main. That is confusing until you know it is local-only.
5. `hs show P1` diffs the proposal against *current main*, not against its base. After main moved, both reviewers (a3b, a5) thought my proposal deleted their #25/#26 lines and asked me to check after landing. This hurts review a lot.
6. Approval reset by `--check` (see 4). The playbook recommends `land --check`, but that brings main into the files, which invalidates the approval my reviewers had just given. The approval should be pinned to my delta, not to the merged tree.
7. `hs watch --for-me --count 1 --timeout 500` timed out twice even though a5's approval of P1 arrived during the wait. The JSON feed showed `{"type":"approved",...}` events. It did catch a3b's comment.
8. `hs proposals` prints `P1 approved 1/1 by a4 for a5`. That reads as if I, the author, approved it. It was a5.
9. `hs show P1` rev 1 still lists the rev 0 reviews (a5's old approval, a3b's comment) under `reviews:` without marking them stale.
10. `hs status` right after the `@ #23 approved by a5` event still said `last land: #23 settled, waiting for review from a5` until I ran sync.
11. `land` of an approved Ask printed `showing to a5 ... review requested from a5` and then `#27 final`. That is a little contradictory.
12. Background `tail -f` / pkill on my side got tangled with my retry loop. That was my own mistake. The playbook's warning not to pkill is right.

## 6. Compared with git
- **Better with hs:** the feed with changeset messages and file lists was a better team chat than `git log` polling. I knew within seconds what a2/a3/a5 had pinned. `land --check` (run tests on main plus my change, then land, no push race) was more convenient than `git pull --rebase && npm test && git push` loops. Per-file 3-way merge plus union NOTES.md meant zero manual merges for five agents writing one NOTES/CONTRACTS file. Ownership-triggered Show (#23) and propose/approve gave review with no extra platform. In git that needs GitHub PRs.
- **Worse with hs:** the hub outage was much worse than a git remote outage. In git I would have local commits with correct semantics and a clear "push rejected". Here I got a fake `#12`, a silently dead feed, a stack trace from push, and "up to date" when I wasn't. The Ask flow was clumsier than a PR. In a PR, the diff is against the merge base, and approvals survive a rebase (or at least the UI is clear). In hs, the diff shown against current main misled two reviewers, and `--check` reset the approval and cost a round trip.
- Overall it was roughly equal to git, better while things worked and worse when the network failed.

## 7. Features I want
- `hs show P<n>` diffs against the proposal's base (or a 3-way view), with a "would merge cleanly onto main #m" line.
- Approvals that survive a rebase when my own delta is unchanged.
- A watcher that reconnects (or exits non-zero with a message) after the hub disappears.
- `sync` saying "offline: main is at least #16, you have #11" instead of "up to date".
- Clean error messages, no stack traces.
