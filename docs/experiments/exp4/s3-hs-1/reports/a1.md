# a1 report (model owner)

## 1. What I built
`src/model.js`: `loadDay(json|string)`, `loadDayFile(path)`, `DayValidationError` (one throw, `.errors[]` lists every problem, message `invalid day file:\n  - ...`). Returns a deep-frozen, non-aliasing `Day` with defaults (`dayLengthMinutes` 600, `serviceMinutes` 0, `priority` standard), derived fields (`drone.home` = depot coords, `package.express`, `window` or null), and `depotById/droneById/packageById`. Fatal: bad JSON/structure, missing/duplicate ids, unknown depot, non-positive numbers, bad lat/lon, bad priority, malformed or inverted window. Undeliverable-but-valid packages pass through. `test/model.test.js`: 13 tests, including "every fixture in fixtures/ loads". CONTRACTS.md "model" section pinned in the same changeset (#5). Lands: #5 (interface + code), #8 (fixture test + note to a5), #12 (note to a4). Final main #19: 63/63 tests pass, `node src/cli.js plan fixtures/day1.json` prints a sensible report (18/19 delivered, p19 too heavy).

## 2. How I learned about teammates' work
- Background `hs watch --json >> .hs/feed.jsonl`, read with `cat`/`tail`. The feed lines and `incoming from teammates` in sync/land output gave me everything I needed. The changeset messages were descriptive enough that I never needed `hs show`.
- `hs watch --path /src/scheduler.js --count 1 --timeout 600` to block until a3 landed (returned at #11). Then two `hs watch --count N --timeout ...` waits to pick up the next batch.
- After each sync I read the real code (`grep` over src/ in my synced worktree) and NOTES.md, and ran the pipeline myself.
- Yes, the watch feed fully replaced polling. I ran about 5 syncs in total, all deliberate.

## 4. Conflicts, rebases, flips
None. Every land was `landed #n` / `#n final`. My files were only mine, and NOTES.md is union-merged, so concurrent appends never conflicted. There were no reorgs and no undone lands. In #5, a2, a4 and I all edited CONTRACTS.md at about the same time; `--check` brought in #2-#4 and merged cleanly with no visible "rebasing" message.

## 5. Friction / confusing output
- `hs status` after a `watch --count` said `main is at #15 or later (from your feed); this shows #12. hs fetch to update`. It was clear, but `hs fetch` vs `hs sync` left me briefly unsure which to run. I used sync.
- I only read the first 3 lines of one `hs sync` output (`head -3`), which hid three of the four incoming lines. That was my mistake, not hs's.
- No real friction. Online commands took about 2-3 s, which was fine.
- Nothing warned that a5 and I were writing the same NOTES item about report rounding. Union merge kept both, so the result was duplication rather than a conflict.

## 6. Compared with git
For this run, with module-per-owner and an append-only NOTES file, hs was somewhat better than a shared git repo:
- The live feed (`watch --json`) and `watch --path ... --count 1` replaced polling `git fetch` + `git log`.
- `land --check` tested main + my change in one step and auto-rebased onto concurrent CONTRACTS.md edits. With git I would have hit non-fast-forward rejects at #5 (three agents pushing in the same few seconds) and had to pull/rebase/retest by hand.
- `merge=union` on NOTES.md is possible in git too, but needs `.gitattributes` and still rejects the push.

Where git would be the same or better:
- Familiar tooling, real branches/PRs.
- Its diff and review tools are more mature.

The parts of this run that had real risk (reorgs, real conflicts, review) never came up for me, so I did not stress-test them.
