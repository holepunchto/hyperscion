# a2 report: geo (Skyhop)

## 1. What I built

`src/geo.js` + `test/geo.test.js`, with the "geo" section of CONTRACTS.md pinned in the same changeset as the code:

- `distanceKm` (haversine, R=6371), `travelMinutes`, `routeLengthKm`, `orderStops` (nearest neighbour, then 2-opt), `tripTimeline` (ETA per stop, service minutes, optional `waitForWindows` hover), `withinRange`, `windowMisses`, `homeOf`, and `planTrip(drone, stops, opts)`, a helper for the scheduler that works on a model drone.
- Unit tests, including a brute-force optimum check for 2-opt. There is also a cross-module test that replays every scheduler trip on every fixture through `geo.planTrip` and checks distance, ETAs, end time, range, windows and day length against a3's output.

Lands: #4 (API + contract), #9 (planTrip/homeOf/waitForWindows), #14 (cross-check test + rounding note to a3), #18 (strict window check after a3's fix). All ended `#n final` within seconds. When I left, main was at #19: 63 tests pass, 0 fail. `node src/cli.js plan fixtures/day1.json` gives 18/19 delivered in 13 trips, and p19 is reported as too heavy.

## 2. How I learned about teammates' work

- I started `hs watch --json >> .hs/feed.jsonl` once in the background and read it with `tail`/`grep` between steps. It replaced polling completely.
- Blocking waits did most of the work: `hs watch --path /src/scheduler.js --path /src/model.js --count 1 --timeout 600` returned when a1 landed #5. The `--path /src/scheduler.js` wait returned when a3 landed #11, and again when a3 landed #17 in reply to my note. A final 240 s wait timed out cleanly with exit 2.
- I used `hs sync` to see the `incoming from teammates` lists (I read those every time) and `hs show 4 --path CONTRACTS.md`. I mostly read code from my synced files rather than through `hs show`/`hs cat`, because the sync already brought it in. `hs log CONTRACTS.md --oneline` was handy.
- I found that a4's pricing calls `geo.distanceKm` with a fallback (#3/#10) by grepping my synced files. hs did not surface that dependency.

## 3. Moments where others' landed work changed what I did

- **#5 (a1, model):** the Day shape has `drone.home`, `depotById`, `package.window`/`destination`. I added `homeOf` and `planTrip` (#9) to work directly on model drones, and made points accept either `{lat,lon}` or `.destination`.
- **#11 (a3, scheduler):** a3 built its own incremental nearest-append routing with window/range checks. It uses only `geo.distanceKm` and `travelMinutes`, not `orderStops`/`planTrip`. I checked: on day1 every trip has at most 2 stops, so 2-opt would gain 0 km (95.44 vs 95.44). So I did not push 2-opt into the scheduler. I wrote a cross-check test instead. That test found a real inconsistency: a delayed `start` is rounded to 2 dp, so recomputed ETAs landed about 0.003 min before `window[0]` (t7/p18, t10/p08, t12/p06).
- **#17 (a3):** a3 fixed it ("delayed starts rounded up so ETAs never precede window[0]") after my NOTES line in #14. I then tightened my test to a strict `window[0]` check (#18).
- **#13/#15 (a5):** new fixtures (edge-crowded) were picked up automatically by my cross-check, because it iterates over `fixtures/`.

Candidly, `orderStops`/`planTrip` ended up unused by the scheduler. The API I pinned early was more than a3 needed.

## 5. Friction, bugs, confusing output

- **Hub outage / misleading sync:** at the end, `hs sync` printed `no peers found, using local state` / `up to date with main #18`. Meanwhile `hs status` said `main is at #19 or later (from your feed)`. "Up to date" is wrong when hs itself knows main is ahead. It should say "could not reach peers; main is at least #19 per your feed". `hs doctor` showed `peers 0 (none found)` and the verdict `offline: no peers. no online peer holds it. Every team needs a holder: run hs seed ...`. That advice is wrong for an agent told never to run `hs seed`. A `hs watch --count 1 --timeout 150` then returned #19 and the next sync worked, so the outage was transient (about 1–2 minutes).
- `hs status` says `main is at #16 or later (from your feed); this shows #14. hs fetch to update`. The pointer to `hs fetch` is fine, but `hs sync` is what you actually want there.
- Minor: when `--check` re-runs because main moved, it doesn't say which files of yours the new changeset overlapped.

## 6. Compared with git

- **Better:** `hs land --check "npm test"` is a one-shot fetch + rebase + test-on-merged-tree + push + "final" confirmation. With 5 agents on one git remote, I'd have hit `git push` rejections and run fetch/rebase/test/push loops, especially on CONTRACTS.md and NOTES.md, which everyone appended to. `merge=union` on NOTES.md handled the concurrent appends; in git that needs a .gitattributes merge driver too, and it's less discoverable. `hs watch --path X --count 1` is a real improvement: "block until a3 lands scheduler.js" has no git equivalent short of polling `git fetch`. The per-land messages in the feed served as a team chat.
- **Same:** the actual coordination happened in NOTES.md and code, as it would in git. Reading teammates' code after sync is the same as `git pull`.
- **Worse:** the dependency on a holder. During the outage, sync quietly reported "up to date". With a hosted git remote, I'd get a clear network error. I also lacked the familiar tools (blame, grep across history). I didn't need them in this short run.
- Overall, for this parallel, many-small-lands situation, hs was somewhat better than git, mostly because of `land --check` and `watch --path`.

## 7. Features I wanted

- When a teammate's landed file starts requiring one of mine (or calling my functions), show it in the feed. For example: "#10 a4 pricing now requires /src/geo.js".
- `hs sync` should never print "up to date" when the feed knows main is ahead and peers are unreachable.
- `hs doctor` advice should fit the role: "holder unreachable; tell the team owner", not "run hs seed".
- `land --check` re-runs should name the overlapping files and say explicitly whether a 3-way merge happened.
