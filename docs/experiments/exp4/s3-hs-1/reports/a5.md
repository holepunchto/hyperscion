# a5 report: integrator (src/cli.js, test/integration.test.js, fixtures)

## 1. What I built

- `src/cli.js`: `plan <dayfile> [--json]`. Pipeline loadDay → plan → price → renderReport. `toJson` maps the output to the pinned `--json` shape and adds `currency`. Exit codes: 0 ok, 1 DayValidationError (message printed as is), 2 file unreadable or not JSON, 64 usage, 70 internal error. All pinned in CONTRACTS.md (#16).
- `test/integration.test.js` runs the real CLI on 3 fixtures and checks these properties:
  - every package appears exactly once, either on a trip or unassigned with a reason
  - payload and range per trip, using my own haversine
  - arrival times are no earlier than flight time allows
  - windows are met
  - one drone's trips never overlap, and every trip is back before the day ends
  - prices follow the pinned formula (independent check); total = sum of prices
  - `report.totals` agree with `--json`
  - p19 is unassigned as too heavy
  - the human report exits 0
  - an invalid file exits 1 with a message on stderr
  - usage errors and missing files are rejected
- Fixtures:
  - `fixtures/edge-unreachable.json`: too heavy, out of range, impossible window
  - `fixtures/edge-crowded.json`: one drone, a 45-minute day, overflow, and two packages with tight windows that compete
- 9 lands: #2, #6, #7, #13, #15, #16, #19, #25, #28. Final main is #28: `npm test` passes 70/70 and `node src/cli.js plan fixtures/day1.json` exits 0 (18/19 delivered, 12 trips, €90.90).

- Mostly blocking `hs watch --path /src [--path /CONTRACTS.md --path /test] --count 1 --timeout 540-600`, then `hs sync`. I did this about 8 times. Blocking waits replaced polling well.
- The `incoming from teammates` lines from `sync` and `land` were the most useful summary.
- `hs show 23` and `hs show P1` to read diffs. NOTES.md (union-merged) carried the conversation, and it worked well.
- Gap: the path-filtered `watch` does not fire on proposals or review requests. P1 sat waiting for my review for about 9 minutes, and I found it only through `hs status` and the feed file. I should have run `watch --for-me` in parallel; one combined wait would be better.

## 5. Friction, bugs, confusing output

1. **The background feed died silently during the hub outage.** `hs watch --json >> .hs/feed.jsonl`:
   - It stopped writing after `#19 settled`, and the process stayed alive.
   - #20, #21 and #22 landed and it never wrote them.
   - My blocking `hs watch --path /src --path /CONTRACTS.md --count 1 --timeout 600` also printed `watch: timed out after 600s with 0 matching changeset(s)` even though #21 (src/report.js) landed at 05:08:17, before the timeout of about 05:08:40.
   - Only `hs sync` showed the new changesets. After `hs watch --stop` and a restart, the feed caught up correctly.
   - No hs output ever said the hub had been down. I learned it from a4's message "re-land after hub outage" and the note "a3 is gone (machine died)".
2. **`hs show P1` showed the diff against current main (#26), not against the proposal's base (#24).** It looked as if P1 deleted my #25 assertions, my NOTES line and a3b's #26 CONTRACTS line. Both a3b and I stopped to puzzle over it, and a3b left a cautionary comment. Rev 1 (rebased) showed the real diff.
3. **#27 landed with an empty message.** The feed has `"message":null`, `incoming` shows `... :: ` and `hs status` shows `review requested: #27 by a4 ::  `. Landing an approved proposal with `hs land` and no `-m` did not reuse the proposal's message.
4. **Reviewing twice.** #27 sent me a Show review request (because it touched my file) after I had already approved the same content as P1 rev 1.
5. `--timeout 600` on `watch` together with my tool's 600 s limit pushed the command into the background. That is my own setup, not an hs bug; afterwards I used 540.

## 6. Compared with git

**Better with hs:**
- Per-file auto-rebase plus `land --check` against the merged tree let 5 agents push to one trunk with no rejected pushes and no manual rebase. With git, every landing would have been `fetch` / `rebase` / `push`, retried on non-fast-forward.
- Blocking `watch --path` is a real primitive git lacks. With git I would poll `git fetch` in a loop.
- Union merge for NOTES.md meant append-only coordination never conflicted. Git can do this with `.gitattributes merge=union`, but almost nobody sets it up.
- `incoming from teammates` after each sync works as a ready-made changelog.

**Worse, or no better:**
- The outage was invisible: the feed and watch failed silently, which a git push or fetch error would not.
- Proposal diffs against main instead of the base were misleading, and approvals reset on a pure rebase.
- With a GitHub-style PR flow, reviews and "approval dismissed on push" are mature and familiar.
- For this small, mostly disjoint-file team, git trunk-based development with a shared remote would have been nearly as smooth: conflicts were zero either way.

**Overall:** a bit better than git for the moment-to-moment loop (wait, sync, land), and worse on review and failure visibility.

## 7. Features I wanted

- One wait that combines `--path` changesets and `--for-me` review events.
- The feed or watch saying loudly when it loses the hub, then reconnecting by itself.
- `hs show P<n>` diffing against the proposal's base, or offering both views.
- Approvals that survive a clean rebase whose 3-way merge leaves the proposal's own hunks unchanged.
- `land` of a proposal reusing the proposal's message.
- No duplicate Show request for content already approved as an Ask.
