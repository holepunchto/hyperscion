# a2 report: geo (Skyhop)

## 1. What I built

`src/geo.js` + `test/geo.test.js` (13 tests), with the CONTRACTS.md "geo" section pinned in the same changeset:
`distanceKm` (haversine, R = 6371; accepts points or anything with `.destination`), `travelMinutes`,
`routeLengthKm`, `orderRoute` (nearest neighbour + 2-opt, deterministic, never mutates), `tripTimeline`
(ETAs that include service minutes), `withinRange`, `reachable`, `planTrip` (order + timeline; `depot = null` uses
`drone.home`), `windowMisses`, and `improveRoute(depot, stops, { feasible })`, a 2-opt pass that only takes a move
when the caller's feasibility check accepts it. Lands: #4, #6, #10. All three were `final` on the first try.

## 2. How I learned about teammates' work

- I ran `hs watch --json >> .hs/feed.jsonl` in the background for the whole session and read it with `cat`/`tail`.
- For waiting I used `hs watch --path /src/scheduler.js [--path ...] --count 1 --timeout 600`, 4 times. This was the
  most useful pattern: it blocked until a3 landed and printed the changeset line, so I never had to poll.
- `hs sync` output ("incoming from teammates (n): #x author files :: message") was my main summary of new work.
  Together with NOTES.md (a3 replied there) it covered almost everything.
- I used `hs show 14 --path /src/scheduler.js` once, to check how a3 called my API.
- Yes, the watch feed replaced polling completely. The blocking `--path` wait was better than the jsonl feed for me.
  I mostly read the feed file to confirm `settled`.

## 3. Moments where others' landed work changed what I did

- **#3 (a1 model)**: the Day is deep-frozen, drones carry `home`, and packages always have `window`. Because of
  this I made `planTrip(null, …)` default to `drone.home`, added `windowMisses` (it reads `stop.window` directly) and
  added a test that runs over day1 through the real `loadDay`. Landed as #6.
- **#2 / #7 (a4)**: pricing fell back to its own haversine when geo was missing. #7 says it switched to
  `geo.distanceKm`, so I kept `distanceKm` stable and did not rename anything.
- **#9 (a3 scheduler)**: a3 wrote its own window-aware insertion and did not use `orderRoute`. Its `simulate()`
  delays departure to fit windows, so unconstrained 2-opt would break windows. Instead of changing the scheduler, I
  added `improveRoute` with a `feasible` callback that a3 could wrap around `simulate()` (#10), and suggested it in
  NOTES.md. a3 adopted it in **#14** and added `.destination` to its internal stops so geo accepts them. The plan for
  day1 changed (fewer km). This was the clearest win from seeing exact code instead of a contract.
- **#14**: I read the diff to check the integration and found nothing to fix.

## 4. Conflicts, rebases, flips

None that affected me. #4 had to merge CONTRACTS.md and NOTES.md, which #2 and #3 had just changed. That happened
quietly inside `land --check` ("checking main #3 + your changes") with no "rebasing" line, because I had no prior
local commit. NOTES.md union merges worked every time. I saw no reorgs, no undone lands and no real conflicts.

## 5. Friction, bugs, confusing output

- `hs status` said `main is at #13 or later (from your feed); this shows #10. `hs fetch` to update`. The
  playbook tells you to `hs sync` to bring work in, so the suggestion to run `fetch` was a small puzzle: should I run
  fetch or sync? I ran sync and it worked. (1 confusing message.)
- When `land` merges teammates' edits to the same file (CONTRACTS.md in #4), nothing says that a 3-way merge
  happened to a file I had edited. It only lists the incoming changesets. I had to look at the file to confirm my
  section and a1/a4's sections were all there. They were.
- `hs watch --path` prints only the first matching changeset. When I synced afterwards I found 3–4 changesets had
  landed. That is fine, but `--count 1` means "1 matching", which is easy to misread.
- I hit no bugs. Online commands took roughly 2–3 s each, which is acceptable.

## 6. Compared with git

- **Better**: `land --check` combines "fetch, rebase, test the combination, push, retry if main moved" in one
  command, with no merge commits and no push rejections. With 5 agents landing into CONTRACTS.md/NOTES.md within
  seconds of each other, git would have produced several `! [rejected] (fetch first)` → pull → re-run tests cycles,
  and NOTES.md would have conflicted without a union merge driver set up.
  - With git, `watch --path X --count 1` would have to be a polling loop over `git fetch` plus `git log origin/main -- X`.
  - The feed lines carrying the files plus the author's message work as a free team chat.
- **Same**: `hs show n --path` is `git show`; `hs log` is `git log`. Nothing new there.
- **Worse / unknown**: there are no branches and no PR-style discussion in one place. Coordination went through
  NOTES.md, which works but is unstructured. I did not exercise the provisional/undo model because nothing raced on my
  files. In a git hub-and-spoke setup that risk does not exist at all, so I'm trusting that the extra state machine is
  worth it here.
  - Honestly, for this run (separate files per owner, few overlaps) a shared git repo plus a good `pull --rebase`
  habit would have worked too. The difference is mostly ergonomics and fewer retries, not capability.

## 7. Features wanted

- An explicit note in `land`/`sync` output when one of *my* edited files was 3-way merged ("merged /CONTRACTS.md with
  #2, #3"). I'd like this most.
- `hs watch --path ... --count 1` could print "(+3 other changesets since your base)" so you know to sync.
- A way to mention someone (`@a3`) in a land message, with `--for-me` delivering it, instead of using NOTES.md for
  requests.
- `hs status` should suggest `hs sync` rather than `hs fetch` when the worktree is clean.
