# a4 report: pricing + report

## 1. What I built

- `src/pricing.js`: `price(plan, day) -> { currency: 'EUR', prices, total, lines }`, `pricePackage`, `roundCents`, `RATES`. Formula pinned in CONTRACTS.md in my first land (#2): 3.00 + 0.80/km (haversine from the carrying drone's depot to the destination) + 0.50/kg + 4.00 express, rounded half-up to cents once; `total` = sum of the rounded prices.
- `src/report.js`: `renderReport(plan, prices, day) -> string` and `reportData(...)`, a JSON-friendly object that a5 now puts into `--json` as `report`. Per drone (idle drones included): trips with depart/back clock, km, load and stops (ETA, id, kg, price, EXPRESS, window); then unassigned packages with their reasons; then totals. It uses the scheduler's ETAs when the plan has them and falls back to `geo.tripTimeline`.
- `test/pricing.test.js` and `test/report.test.js`: 12 tests, including a day1 run against the real scheduler and a regression test for clock double rounding.
- Lands: #2, #7, #11, #18. All went through `--check "npm test"` and all are final. On main #20: 66/66 tests pass and the CLI renders day1 and all four edge fixtures correctly.

## 2. How I learned about teammates' work

- I started `hs watch --json >> .hs/feed.jsonl` in the background once and `tail`/`grep`ped it about 5 times. Most of what I learned came from the `incoming from teammates (n): #n author files :: message` block that `hs sync` and `hs land` print. Teammates wrote very informative land messages, so that block was often enough.
- I blocked on a3 with `hs watch --path /src/scheduler.js --count 1 --timeout 600`. It returned the moment #9 landed, so there was no polling. Near the end I waited with `hs watch --count 2 --timeout 300`.
- I used `hs show 17 --path src/report.js` and `hs show 18 --path src/report.js` to see exactly what a5 changed in my file. I also read `NOTES.md` and `CONTRACTS.md` after each sync.
- Did the watch feed replace polling? Yes. The blocking `watch --path` was the most useful single feature. The background JSON feed was useful but noisy: half of its lines are `settled` lines.
- I missed one thing: a1 commented on my #2 at seq 2 ("simpler now if you like: day.droneById[...]"). It was only in the JSON feed as a `review` line. I grepped for changesets, and `hs status` never showed comments on my own lands, so I only found it at the very end.

## 3. Moments where others' landed work changed what I did

- **#3 (a1, model)**: the Day shape came with `depotById/droneById/packageById`, `hasWindow` and windows always set. My report's `lookups()` prefers the byId maps, and I show a window only when `hasWindow` is true, which hides the synthetic `[0, 600]`.
- **#4/#6 (a2, geo)**: I deleted my own haversine and pricing now uses `geo.distanceKm`. The report computes fallback ETAs with `geo.tripTimeline`, so I didn't write my own timeline.
- **#5 (a5, cli)**: the CLI writes `renderReport(...) + '\n'` and reads `prices.prices`/`prices.total`. I dropped my trailing newline and kept `price()` returning exactly those fields.
- **#9 (a3, scheduler)**: the Plan carries `stops[].arrive`, `end` and `distanceKm`. I made sure the report uses them instead of recomputing (no waiting at windows). I added a day1 test with the real scheduler and changed load to 2 decimals.
- **#16 (a3, a NOTES-only land)**: a3 reported a double-rounding bug in my report ("back 00:09" followed by "depart 00:08"). I fixed it in #18: clocks are now computed from the raw minutes.

## 4. Conflicts, rebases, flips

- There were no real conflicts, no undone lands and no reorg lines in my feed.
- I had one concurrent edit of my own file. a5's #17 (a Show to me) changed one line of `src/report.js` (`start: round1(...)`) while I was editing the same function for #18. My `land --check` brought #17 in, merged it cleanly (the hunks were 2 lines apart), ran the tests and landed #18. The output only said `incoming from teammates (1): #17 ...`. It never told me that /src/report.js had been 3-way merged with someone else's edit. I only found out through `hs show 17`. That is a silent merge into my own module.
- **Duplicated work**: a3 (#16) and a5 (#17) found the same rounding bug independently. a5 fixed it in my file (by rounding `start`) at the same moment that I fixed it differently (by using raw clocks). The two fixes merged fine, but this is exactly the "three people fix the same thing" waste the playbook warns about. a3 did it right: a note, plus "I won't touch report.js".
- I counted 0 auto-rebases in the "main moved ... rebasing" sense, and 1 merge-on-check.

## 5. Friction, bugs, confusing output

- `hs land ... --check` prints `checking main #10 + your changes: npm test` and only then `incoming from teammates (1): #10 ...`. You learn that main moved after the check has already run against it, so the order reads backwards. The same happened with #17.
- `hs status` said `main is at #15 or later (from your feed); this shows #11. `hs fetch` to update`. The playbook says to use `hs sync` to bring work in. Should I run fetch or sync? I ran sync and it worked, but the hint pointed me at the wrong command.
- No message in the land output says "your file X was merged with a teammate's edit". `incoming` lists the files, but nothing marks the overlap. Compare the playbook's `main moved: /X ... rebasing` message, which I never saw in this path.
- `hs status` did not surface a1's comment on my #2. Comments on my own lands are only in the JSON feed.
- `hs review '#17' approve -m ...` worked, but in fish the bare `#17` is a comment, so it has to be quoted. A plain `17` form would be nicer (I didn't test whether it's accepted).
- Minor: the feed's `settled` lines double its size.

## 6. Compared with git

- **Better**: I didn't need a branch/PR/merge dance. `land --check` meant "test on top of current main and publish" in one step, which in git is `git pull --rebase && npm test && git push`, retried whenever someone else pushes. With 5 agents landing every minute or two, git pushes would often be rejected as non-fast-forward. hs absorbed that.
- **Better**: `watch --path /src/scheduler.js --count 1` beats polling `git fetch`. The incoming summary with messages is better than `git log HEAD..origin/main`.
- **Better**: `hsowners` with automatic Show review requests gave me a clear "someone touched your file" signal (`review requested: #17 by a5` in `hs status`). Git has no equivalent without a forge.
- **About the same**: the content merging. Concurrent edits to `CONTRACTS.md` (5 sections, 5 authors) and `report.js` merged cleanly. git's 3-way merge would also have handled them, because the hunks didn't overlap. The NOTES.md union merge is something git can do too (`merge=union` in .gitattributes), just rarely set up.
- **Worse/unknown**: no local history tooling (blame, bisect). Merges into my own file happened silently. I also have no feel for the robustness of the P2P layer, because nothing went wrong in this run, so I can't credit or blame it.
- For this exact setup (one shared main, many small lands, independent modules), hs was somewhat better than a shared git repo, mostly because of the land/check/retry loop and the watch feed.

## 7. Features I wanted

- A `merged with #n (author)` marker on any file in my land that a teammate also changed, especially files I own.
- `hs status` / `watch --for-me` should show comments on my lands, not only review requests.
- A filter for the JSON feed that drops `settled` lines (or an `--events changeset,review` option).
- Print `incoming` before `checking ...`.
- A way to claim a fix ("a4 is fixing X") so that people don't fix the same bug twice.
