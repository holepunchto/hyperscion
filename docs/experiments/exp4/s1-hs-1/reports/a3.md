# a3 report: scheduler

## 1. What I built

`src/scheduler.js`: `plan(day) -> { trips, unassigned }`. It uses a greedy window-aware
cheapest insertion. Packages go in priority order (express first, then tightest deadline, then
file order). Each package is inserted at the cheapest feasible position of any existing trip of
any drone, or opens a new trip in any idle gap of a drone's day. After each insertion, geo's
`improveRoute` runs as a feasibility-checked 2-opt post-pass. The rules enforced are payload and
range per trip, service minutes, day length and windows; drones wait at the depot rather than
hovering, and one drone's trips never overlap. Unassigned packages get one of seven reasons:
too heavy, out of range, inverted window, window outside the day, window unreachable, no time
left, and no drone free within its window. The Plan shape is pinned in CONTRACTS.md.
`test/scheduler.test.js` has 16 tests, including an independent rule checker that is run on
every plan. The whole suite (66 tests, including a5's integration tests over 4 fixtures)
passes on #21.

My lands were #9, #12, #14, #15, #16 (NOTES only), #19 and #21 (NOTES only).

## 2. How I learned about teammates' work

- `hs watch --json >> .hs/feed.jsonl` ran in the background for the whole session. I read it
  with `tail` about 5 times, mostly to see which files a changeset touched (CONTRACTS.md, my
  module) and what its message said.
- The `incoming from teammates (n): #x author files :: message` block printed by every
  `sync`/`land` was the most useful single output. Because it is attached to the action I was
  already doing, I usually didn't need the feed.
- `hs show 10 --path /CONTRACTS.md` and `--path /NOTES.md` gave a precise view of what a2 added
  for me. `hs log -n 25 --oneline` at the end gave the overview, with [final] tags.
- `hs watch --count 1 --timeout 300` once, to wait for the next land instead of polling. It
  returned on #17 with a clear line.
- NOTES.md (read after sync) carried the intent behind changes: who needs what.
- Did the feed replace polling? Yes. I never ran a sync loop. Blocking `watch --count 1` plus
  the incoming list at sync/land was enough.

## 4. Conflicts, rebases, flips

- No real conflicts, no undone lands, no `reorg` lines in my feed (43 lines, 0 reorgs).
- **Silent merges of shared files.** #9 was based on #4, while #5, #6, #7 and #8 had landed in
  between; #6 and #7 also edited CONTRACTS.md. hs merged my CONTRACTS.md section into theirs
  without any "main moved ... rebasing" line; I only saw the `incoming from teammates (4)`
  list. The same happened for #19 after #17/#18 touched CONTRACTS.md and NOTES.md. It worked
  and the result was correct, but I was never told that my file had been 3-way merged. I
  count these as 2 auto-rebases; hs did not label them as such.
- `--check` race handling was visible once, on #9: `main moved to #8 while checking; checking
  again`, followed by a second passing check. That was clear and reassuring.
- **Duplicate fix (coordination gap, not a VCS conflict).** I reported the report rounding bug
  in NOTES (#16) and said I would not touch report.js. a5 then made a partial fix in report.js
  as a Show to a4 (#17), and a4 fixed it properly (#18). Three agents spent effort on one
  bug, which is the waste the playbook warns about. NOTES plus Show did not prevent it,
  because nothing marks a reported issue as "owner is on it".

## 5. Friction, bugs, confusing output

- Feed noise: `{"type":"review","n":7,...,"actor":"a1","verdict":"commented",...}` (a1
  commenting on a4's #2) and `{"type":"request",...,"reviewers":["a4"]}` appeared in my feed
  although neither involved me. This is minor and I could filter it, but the line was cryptic
  at first: `seq:2` and `n:7` are two different numbering schemes in one object.
- I never saw an explicit message that a file I changed was merged with a teammate's version
  (see section 4). `sync` printed `your unlanded changes: 1 untouched by others, 0 merged with
  theirs, 0 in conflict`, which is good, but `land`'s output doesn't give the same breakdown.
- `hs watch --stop` → `stopped watcher 212490`. That was clear.
- Otherwise the output was clear. Every land ended with `#n final` within a couple of seconds,
  so I always knew my land was safe.
- Time lost to the tool: about 3 minutes, mostly reading the playbook.

## 6. Compared with git

In this exact setup (5 parallel agents, disjoint modules, shared CONTRACTS.md/NOTES.md),
hs was better than a shared git repo in several concrete ways:

- `land --check "npm test"` = fetch + rebase + test the merged tree + push, with an automatic
  retry when main moves, in one command. In git that is `git pull --rebase && npm test && git
  push`, with a race at push time and manual retries. With 5 agents landing every minute, git
  would have produced several rejected pushes.
- The union merge for NOTES.md meant zero conflicts on a file that all five of us appended to
  constantly. In git, every NOTES append would conflict with every other.
- The incoming list on every sync/land, and the push-based feed, gave me "what did my
  teammates just do" for free. In git I would have run `git log -p origin/main` by hand.
- `#n` sequential numbers are easier to cite in NOTES and messages than hashes.

Where git would have been equal or better:

- Git has richer history tools (blame, bisect, branches for experiments). I didn't need them
  here.
- Git is a familiar mental model. hs's provisional/settled/final states never mattered to me,
  because every land was final immediately; with a slow hub they could add confusion.
- The duplicate rounding fix would have happened under git too: it is a coordination problem,
  and hs's Show didn't solve it.

Net: for this workload hs was noticeably smoother, mostly because of `--check` with
auto-retry, union merges and the incoming feed. Git with good discipline would work, but with
more friction and more races.

## 7. Features I wanted

- A `land` output line naming files that were 3-way merged with teammates' changes, for
  example `merged: /CONTRACTS.md with #6 a2, #7 a4`.
- A lightweight "claim/ack" on a NOTES item or issue ("a4 is fixing this"), so that two others
  don't fix it in parallel.
- `hs watch --json --mine-or-paths src/scheduler.js,CONTRACTS.md` style filtering, so review
  events for others stay out of my feed.
- `hs show <n> --stat`, to see files and line counts without the full diff.
