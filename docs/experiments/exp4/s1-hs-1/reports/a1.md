# a1 report — model.js

## 1. What I built

`src/model.js`: `loadDay(objOrJsonString) -> Day`. The returned Day is deep-frozen, keeps file order and has `depotById/droneById/packageById` lookups, `drone.home {lat,lon}` derived from the depot, and `package.window` always set (`[0, dayLengthMinutes]` by default, with `hasWindow` and `express` flags). Fatal problems throw `DayError`, whose `err.errors[]` lists every problem with a path (`drones[0] (d1): unknown depot "east"`). Bad JSON gives the same error type. Undeliverable but well-formed packages pass through: too heavy, out of range, or with an odd or inverted window. `loadDay` is idempotent (`loadDay(day) === day`), and the module also exports `isDay`. `test/model.test.js` has 13 tests, including all five fixtures. The CONTRACTS.md model section is pinned and matches the code. I landed 3 changesets: #3, #8 and #13.

## 2. How I learned about teammates' work

- I ran a background `hs watch --json >> .hs/feed.jsonl` and read it with `tail`.
- I blocked with `hs watch --path /src/scheduler.js ... --count 1 --timeout 600` and with plain `hs watch --count N`.
- I used `hs sync` to see the "incoming from teammates" list, and `hs show 2 --path src/pricing.js`.
- I read NOTES.md after each sync and grepped consumers for `loadDay/home/window/hasWindow/.sort`.

What I looked for: how each consumer used the Day (`drone.home`, `p.window`, whether they re-loaded a Day, mutation of frozen arrays).

The blocking `watch --path/--count` fully replaced polling. I never ran sync in a loop. In practice the blocking watch was more useful than the JSON feed file, because it prints the same lines and returns when there is something to act on. I used the feed file mostly to look back over history.

## 3. Moments where teammates' landed work changed what I did

- **#9 (a3 scheduler)** and its NOTES line "plan() takes a loaded Day or the raw file". I saw a subtle hazard: re-loading an already-loaded Day would flip `hasWindow` to true for every package, because `window` is always set. I made `loadDay` idempotent and added `isDay` in **#13**. a3 then simplified to "always go through loadDay (idempotent since a1 #13)" in **#15**. It was a clean two-way loop that went entirely through hs.
- **#5 (a5 cli)** parsed JSON itself, so bad JSON surfaced as a bare SyntaxError. I did not touch cli.js. I left a NOTES tip in #8, and a5 adopted it in **#17** (cli now passes the raw text and gets a DayError).
- **#5** added `fixtures/edge-limits.json`, and later #17 and #20 added edge-empty, edge-crowded and edge-windows. These drove my edge tests in **#8** (x03 `[0,2]`, x04 5.01 kg must pass validation) and my final check that every fixture loads.
- **#2 (a4 pricing)** wrote a defensive `finder()` that accepts arrays, objects or Maps, because they wrote it before my shape existed. I left a review comment on #2 pointing at `droneById[..].home`. That was not needed for correctness.
- Influence also went the other way: **#6 (a2)** switched `planTrip(null, ...)` to use `drone.home`, citing "a1 Day shape".

## 5. Friction, bugs, confusing output

Honestly, very little:

- `hs watch --count 3` printed a review event (`@ #17 approved by a4 ...`) in addition to 3 changesets. It was not obvious whether `--count` counts review events without `--for-me`. Apparently it does not (I got 3 changesets plus the review line), but the line printed anyway. Minor.
- `hs watch --for-me --count 1 --timeout 5` → `watch: timed out after 5s with 0 event(s) for you`, exit 2. This is fine and documented, but exit 2 on "nothing for you" looks like an error in a shell `&&` chain.
- `hs review '#2' comment` needs the `#` quoted in fish/bash scripts. `hs review 2` would be nicer. I didn't test whether it works without the `#`.
- After stopping, `hs status` still said `last land: #13 final` while base was #21. That is correct, but it would help to say whether my files have changed on main since then.
- On the first wait, `watch` reported #4, which was already on main before I started waiting (it counts from the synced base). This is documented, but on first contact it looked like a new event.
- Each online command took 2–3 s. Not a problem at this scale.

## 6. Compared with git

In this exact setup (one module per agent, shared CONTRACTS.md and NOTES.md, five agents landing every minute or two), a shared git repo would have meant:

- `git pull --rebase` before each push, and a retry on push rejection.
- Real textual conflicts in NOTES.md and in CONTRACTS.md, since everyone appended at the end and edited adjacent sections. hs handled NOTES.md with merge=union and CONTRACTS.md with a per-file 3-way merge, without me noticing.
- No built-in "run the tests on main + my change and land only if green, rechecking if main moved". `--check` is the real win. With git, I would have pushed code tested only against my stale base.
- Polling (`git fetch` in a loop) instead of `hs watch --path X --count 1`. The blocking wait for a specific file landing is something git simply doesn't have.

What git does as well or better:

- `git log -p`/`git show` cover `hs show` and `hs log`.
- Git is mature, and every agent knows it without reading a playbook.

My task had low contention (I owned one file), so I didn't stress hs's race handling (flips, reorgs). Overall, for this workflow hs was clearly smoother than git. I'd put most of the difference down to `--check` with auto-recheck, the watch/wait primitive and the union merge for notes, rather than the P2P aspect, which was invisible to me.
