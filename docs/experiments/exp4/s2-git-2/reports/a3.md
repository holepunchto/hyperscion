# a3 report (git arm): scheduler capacity side

## 1. What I built

- The capacity half of `src/scheduler.js`. It is a greedy packer. Packages go in priority order: express first, then the tightest window, then id. For each package the packer considers three options on every drone that can lift it: join the drone's last trip, open a new trip after the last one, or fill the idle gap before a trip that waits for a window (this uses a2's `delayLaunch`). Payload is checked in the packer. Range, windows and day length are checked through a2's `timeTrip`. The option that ends earliest wins.
- Every undeliverable package goes to `unassigned` with a reason that starts with a stable prefix: `too heavy for every drone (...)`, `out of range for every drone that can lift it (...)`, `no drone can meet it even alone: <timing reason>`, or `no capacity left: ... before its window closes / before the day ends`.
- The `Plan` shape is pinned in the CONTRACTS.md "scheduler (a3)" section: `{ trips: [{ drone, depot, start, end, packages, stops:[{id,arrive,depart,flightMinutes}], distanceKm, loadKg }], unassigned:[{id,reason}] }`. It is a superset of the CLI's pinned `--json` shape.
- 12 unit tests in `test/scheduler.test.js` cover:
  - payload, range and multiple trips per drone
  - express priority when capacity is short
  - gap filling
  - no overlapping trips
  - the reason prefixes
  - the day1 invariants
  - CR-1 flight minutes
- Final state: 75/75 tests pass on main at 0261326. `node src/cli.js plan fixtures/day1.json` delivers 18 packages. p19 is unassigned as too heavy.

## 5. Friction and confusing output

- **Misleading header line on conflict:** `Could not apply ad0283e... # scheduler: Plan shape pinned ...`. The commit subject appears with a `#` in front of it, which reads like a comment line.
- **Easy to miss the rejection:** with `| tail -1`, a rejected push shows only `hint: See the 'Note about fast-forwards' in 'git push --help' for details.` The actual `! [rejected]` line is higher up, and the exit status was swallowed by my pipe. My mistake, but git's last line is a hint, not the error.
- **`git log HEAD..origin/main` shows nothing unless you fetch first.** I checked it after a rejected push and saw an empty log, which looked as if nobody had pushed.
- **No semantic merge signal:** nothing tells you that two people just implemented the same feature (see the 60327a4 item in section 4).
- **Reading NOTES needs plumbing:** I had to diff with `grep '^+-'` to see only the new lines.

## 6. Compared with an ideal tool

- **Live intent and claims.** When CR-1 landed, a2 and I both started the same 5-line change within the same minute. Ideally a2's "I'm adding flightMinutes in timeTrip" would have reached me *before* I committed, either as a claim on the task or a live work-in-progress feed. Git only shows work after it is pushed.
- **A push/feed notification** instead of fetch loops. Polling cost little attention but added latency, and the race window between pull and push caused one rejection.
- **Region ownership inside a shared file.** a2 and I split `scheduler.js` by comment markers. A tool that knew "timing block = a2, capacity block = a3" could warn when one of us edits the other's block. It could also flag that two of us edited functions producing the same field in the same window.
- **Atomic pull-test-push.** "Land if tests pass on the latest main, else rebase and retry" would remove the rejected-push loop.

## 7. Features I wanted

- A subscribe/watch feed for paths (`src/scheduler.js`, `CHANGE-REQUEST.md`) and for @mentions in NOTES.
- Lightweight claims ("a3 is doing X") visible to teammates before code is pushed.
- Duplicate-work detection when a rebase is clean but both sides touched the same file in the same short window.
- A one-command test-and-land that retries on races.
