## 2. How I learned about teammates' work

- `git fetch -q && git log --oneline --stat HEAD..origin/main` after every push and at the end of every wait loop. That was about 12 times.
- `git show <sha> -- <file>` to read the diffs that mattered to me: a5's report skeleton b6ff91f, a1's Day shape f6935e9, a3's Plan shape e09a427, a5's layout a237bd4, and a2's and a3's flightMinutes commits.
- `tail NOTES.md` after each pull. It was the most useful channel because it explains intent; the log only shows what changed.
- To wait, I used the playbook's bounded loop (`for i in $(seq 1 28); do git fetch -q; git log HEAD..origin/main | grep -q . && break; sleep 20; done`), 7 times. Roughly 25–30 minutes of wall-clock time went into waiting, though it was not my effort. Most loops ended after 1–5 minutes with a single commit, so I had to restart the loop again and again.

## 4. Conflicts, rejected pushes, rebases

- 0 rejected pushes and 0 textual conflicts.
- 3 visible auto-rebases (`Rebasing (1/1)Successfully rebased and updated refs/heads/main.`) on my pushes of 9ca0768, e1211e6 and 98f63cb. All went cleanly.
- The real problem was a **semantic** collision that git could not see. a2 and a3 implemented the same CR-1 field in two places in scheduler.js, a3's rebase applied cleanly, and both ran, with a3's overwriting a2's. a2 spotted it later from NOTES (a98c16e) and a3 removed one copy (256c634). Four agents wrote the same flight-minutes computation within about 10 minutes of the change request.

## 5. Friction and confusing output

- No feed. Learning that something had landed always meant `git fetch` + `git log HEAD..origin/main` in a sleep loop. The loop wakes on any commit, mostly NOTES-only ones, so I restarted it about 7 times.
- My NOTES "I'm taking this, don't do X" line (aea09b8) was pushed within a minute of reading the CR, yet two teammates had already done X. NOTES only propagates when someone pulls, so claims cannot prevent duplicate work.
- `git pull` printing `Rebasing (1/1)Successfully rebased and updated refs/heads/main.` on one line (no newline after the progress) is a little ugly but clear. `git pull -q` hides whether a rebase happened at all, so my rebase count is a lower bound.
- My own mistake, not git's: a Python slice edit left a stray `}` in integration.test.js. `npm test` caught it before the push, and this is why the `pull && npm test && push` discipline matters.
- Hard to tell whether my push was "safe": tests passed on top of main at the moment of the push, but anyone could land on top seconds later. Nothing confirms that main is green after the fact.

## 6. Compared with an ideal tool

- **Push notifications or a feed filtered by path or interest** (e.g. "tell me when src/scheduler.js or CHANGE-REQUEST.md changes"). This would replace the sleep loops.
- **Claims / intents visible before code lands.** When the change request arrived, an ideal tool would show "a2 is working on stops[].flightMinutes" immediately, which would have prevented the 3–4 duplicate implementations. In git, intent becomes visible only after a commit is pushed and fetched.
- **Semantic overlap detection**: a warning when two commits that rebase cleanly add the same field or function in one file (a2's and a3's flightMinutes). A clean rebase was the wrong signal here.
- **Contract-aware landing**: when I changed the pinned price formula, the tool could have flagged that a5's integration test asserts the old formula. git only tells you once you run the tests.
- **Main health**: a CI-style "main is green at sha X" so I would know my land stayed safe.

## 7. Features I wanted

1. A watch/feed with path filters (`watch src/scheduler.js CONTRACTS.md CHANGE-REQUEST.md`).
2. Lightweight work claims ("a4: implementing CR-1 flightMinutes in pricing") broadcast immediately, without a commit.
3. Post-land green/red status for main.
4. `git log` that hides NOTES-only commits by default when I am scanning for code changes.
