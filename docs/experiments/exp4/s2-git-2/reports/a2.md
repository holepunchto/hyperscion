- `git show <sha> -- src/scheduler.js NOTES.md` for a3's scheduler commits. I read `CONTRACTS.md` and `test/integration.test.js` after pulling, to check my timing model against a5's independent checks.

## 4. Conflicts, rejected pushes, rebases

- 0 rejected pushes and 0 textual conflicts. About 5 pulls rebased my single commit cleanly (`Rebasing (1/1)Successfully rebased and updated refs/heads/main.`).
- The **semantic** collision was the real issue. a3's 60327a4 duplicated my 79128cf in the same file and rebased with no conflict, so both code paths ran (a3's overwrote mine). Neither of us knew until we read the log. Git treated it as a success.
- The block markers in `scheduler.js` (`--- timing (a2) ---` / `--- capacity (a3) ---`) worked well: two people editing one file all session never had a textual conflict.

## 5. Friction and confusing output

- `git pull` printed `Current branch main is up to date.` right after a fetch had already advanced origin. It was correct but made me pause, because I couldn't tell whether my later push included the commits I had just read about.
- `Rebasing (1/1)Successfully rebased...` has no newline between its two parts. It's minor, but it's easy to misread.
- No conflict ≠ no problem: a clean rebase of duplicated logic (60327a4 on 79128cf) gave no warning at all.
- The wait loop is crude. `git log HEAD..origin/main | grep -q .` wakes on anything. Filtering by path (`-- src/pricing.js`) misses NOTES lines addressed to me unless I add NOTES.md, and then it wakes on everything again.
- There's no way to see what a teammate is *working on* before they push. a3's placeholder `timeTrip` and my real one were written in parallel (a3 noted that it kept mine on rebase).

## 6. Compared with an ideal tool

For 5 agents with a shared file, an ideal tool would:

- **Show intent before code exists.** "a3 is editing `toPlanTrip` for CR-1" would have stopped the flightMinutes duplication and the placeholder `timeTrip`.
- **Give a push feed.** Wake me when someone touches my files, mentions me in NOTES, or posts a change request, instead of 20-second fetch polling.
- **Flag semantic overlap.** For example: "two commits in the last N minutes both add a field `flightMinutes` to stops".
- **Tie messages to commits.** NOTES.md worked well as a union-merged chat, but replies are only linked by hand-cited shas.

Git's strengths here were real:

- History is fully inspectable (`show`, `diff A B -- file`).
- Rebases are cheap and clean.
- The union merge on NOTES.md never conflicted.

## 7. Features I wanted

- A blocking `git wait --path X --mention a2` (or a feed) instead of sleep/fetch loops.
- Advisory "claims" or WIP markers per file region, visible to others.
- A post-rebase "these commits touched the same function as yours" notice.
- A way to see whether a NOTES line has been acted on (an ack or thread).
