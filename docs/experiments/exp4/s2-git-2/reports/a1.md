# a1 report (git arm, s2-git-2)

## 1. What I built

`src/model.js`: `loadDay(json | string) -> Day`, deeply frozen, sharing nothing with the input.
`Day` has `depots/drones/packages` arrays in file order plus `depotById/droneById/packageById`.
Each drone gets `home: {lat, lon}` (its depot's coordinates). Each package gets
`window: [e, l] | null`, `express: boolean` and a default priority of `standard`. On fatal
problems it throws `DayValidationError` with `.errors: string[]`, collecting every problem
first: bad JSON, missing arrays, missing or duplicate ids, unknown depot, non-positive numbers,
bad coordinates, unknown priority, malformed or inverted window. Undeliverable but valid
packages load normally. The CONTRACTS.md "model" section is pinned in the same commit.
`test/model.test.js` has 13 tests, including "every fixture except edge-invalid loads" so new
fixtures from a5 are checked automatically. `fixtures/edge-invalid.json` was added for the CLI's
exit-1 path.

Lands: f6935e9 (model + contract, the first push of my run), 75317e5 (edge-invalid fixture, tests,
CLI nits for a5).

## 2. How I learned about teammates' work

- After each land, I ran a bounded wait loop: `for i in 1..28; git fetch -q; git log --oneline HEAD..origin/main | grep -q . && break; sleep 20`.
  Then `git log --stat --format='%h %an %s' HEAD..origin/main` and
  `git diff HEAD origin/main -- NOTES.md CHANGE-REQUEST.md` to read only the new NOTES lines.
- One `grep` over `src/*.js` and `test/integration.test.js` for `loadDay|depotById|home|window|...`
  showed how others consumed my module. I also ran the CLI against the fixtures. I didn't need `git show` for the diffs.
  The `--stat` output and NOTES lines told me whether anything touched my area.
- That was about 10 wait loops, roughly 11 fetch+log rounds. Polling took most of the wall-clock
  time (about 60+ minutes of sleeping in loops) but little of my attention. Once the model was
  pinned, nobody needed anything from me, so I spent most of the run waiting.

## 4. Conflicts, rejected pushes, rebases

- Both of my pushes went through on the first try. Each `git pull` before pushing rebased 1
  commit onto new upstream work (b45ac0e, then 8aae672) with no conflicts. `NOTES.md`'s union merge did its
  job.
- I had no rejected pushes and no real conflicts.
- I saw one problem in other agents' work: a2 (79128cf) and a3 (60327a4) both implemented
  `stops[].flightMinutes` for CR-1 in different blocks of `scheduler.js`. git rebased one onto the
  other cleanly, so both copies ran, and neither of them was warned. They found it later by reading
  NOTES (a98c16e, 256c634). A clean textual merge hid a semantic duplicate.

## 5. Friction and confusing output

- `git pull` prints `Rebasing (1/1)Successfully rebased and updated refs/heads/main.` with no
  newline between the two messages. It's cosmetic, but it's easy to misread when grepping.
- There's no way to learn "something landed" other than polling. `fetch` + `log HEAD..origin/main` in a
  sleep loop works, but it's crude. A loop either sleeps after a change landed or exits too eagerly.
- To see only the new NOTES lines I had to use `git diff HEAD origin/main -- NOTES.md`. That's fine
  once you know it, but git has no concept of "new messages since I last looked."
- Ownership is a convention in README/NOTES. git doesn't know a5 owns `cli.js`, so nothing
  stopped me (or warned anyone) from editing it. The crossed flightMinutes work above shows git can't
  tell when two people are working on the same thing.
- I had to puzzle over no git messages. Everything was the standard, well-known output.

## 6. Compared with an ideal tool

With 5 parallel agents and shared files, an ideal tool would:
- push a feed of landed changes (or block until one arrives) so I wouldn't sleep-poll;
- show who is currently working on which file or section before they push. That would have
  stopped the a2/a3 duplicate, since textual merges cleanly hide semantic overlap;
- know module ownership and route Show/Ask notices to the owner automatically, instead of
  `@a5` lines in a shared file;
- let me subscribe to "consumers of my module": tell me when someone pushes code that calls
  `loadDay` or reads `Day` fields I might change.
Honestly, for my role (one owner, one file, a stable interface pinned early), plain git was enough. Nothing went wrong
for me. The gaps showed up in shared-file and change-request coordination between other agents.

## 7. Features I wanted

- A blocking `wait for next land` (or `--since-last-seen` log) instead of a fetch/sleep loop.
- "Who's working on X right now" or intent announcements.
- Ownership-aware notifications (someone touched your file / your interface's consumers changed).
- A structured "new NOTES lines since my last read" view.
