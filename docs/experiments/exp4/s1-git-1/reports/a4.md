# a4 report (git arm): pricing + report

## 1. What I built

- `src/pricing.js`: `price(plan, day) -> { currency: 'EUR', prices, total, lines }`.
  Formula pinned in CONTRACTS.md in my first push (dbc2900): `2.50 + 0.60*km + 0.40*kg + 3.00 if express`,
  with km = great-circle distance from home depot to destination (so it doesn't depend on route
  order), half-up rounding to cents, and total = sum of the rounded prices. It uses
  `geo.distanceKm` when that exists and falls back to a local haversine otherwise.
- `src/report.js`: `renderReport(plan, prices, day)` gives a text report (per drone, including
  idle ones: trips with depart/return/km/load; stops with ETA, weight, price and express/window
  flags; unassigned with reasons; totals). `reportJson(...)` is a superset of the cli `--json`
  contract, and a5's cli merges it in. ETAs come from the plan (`stops[].arrive`) when present.
  Otherwise they are computed from speed and service time, with waits for windows.
- Tests: `test/pricing.test.js` and `test/report.test.js`. They cover a hand-made plan plus a
  real-pipeline test (model → scheduler → pricing → report over day1). The full suite has 60
  passing tests on main at bca1c2e.

## 2. How I learned about teammates' work

- `git show <sha> -- CONTRACTS.md NOTES.md` to read the interface parts of commits: a1's c51432c,
  a3's c224c95, a2's 4599d02, and a5's a335679 and 1386ce3 (cli.js diff).

## 4. Conflicts, rejected pushes, rebases

- No content conflicts. NOTES.md union merge worked with 5 people appending.
- Auto-rebases on pull: 3 (before 4804289, before 62061ec, and the retry for 210419b). All clean.
- One rejected push. `git pull` said `Current branch main is up to date.`, the tests passed, and
  then `git push` was rejected (the output I captured ended with `hint: See the 'Note about
  fast-forwards' in 'git push --help' for details.`). Someone landed in the few seconds between
  my pull and my push. I re-ran pull/test/push, which rebased and went through. It cost about 1 minute.

## 5. Friction and confusing output

- The "up to date then rejected" race above. The pull → test → push window isn't atomic, so
  "safe to push" is only probabilistic, and the rejection text talks about fast-forwards rather
  than "someone pushed X just now".
- My own mistake that git doesn't guard against: I piped `npm test | grep ...` inside the
  `pull && test && push` chain, which hides the test exit code. A failing suite could have been
  pushed. Nothing enforces "tests passed on top of latest main" before a push lands.
- `git pull` output (`Rebasing (1/1)Successfully rebased...`) doesn't say *what* came in. I had
  to fetch and log first to know whether the rebase brought changes relevant to me.
- No way to subscribe to "commits touching CONTRACTS.md sections I consume". I grepped diffs in a
  sleep loop instead.

## 6. Compared with an ideal tool

- A push-based feed filtered by what I depend on (CONTRACTS sections, files, NOTES lines with
  `@a4`/`a4:`), instead of polling with a sleep loop.
- An atomic "land if tests pass on top of current main" (a merge queue) so the race and the
  piped-exit-code mistake can't put an untested state on main.
- Contract changes as first-class objects: a3's Plan shape lived in prose in CONTRACTS.md. An
  ideal tool would notify consumers and maybe check that `reportJson` still matches the pinned
  `--json` fields.
- Lightweight addressed messages. NOTES.md worked, but replying to a5 means appending a line
  and hoping they fetch and read the diff.

## 7. Features I wanted

1. `git watch --paths CONTRACTS.md src/scheduler.js --mentions a4` (a blocking wait for a relevant change).
2. Server-side "push only if CI on the rebased result is green" (a merge queue).
3. A pull summary that lists incoming commits with files touched.
4. A per-section owner/consumer map for CONTRACTS.md with notifications.
