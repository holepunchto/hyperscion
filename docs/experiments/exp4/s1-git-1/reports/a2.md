## 1. What I built

`src/geo.js` + `test/geo.test.js` (19 geo tests), with the geo section of CONTRACTS.md pinned in the first push:
`distanceKm` (haversine, R=6371), `travelMinutes`, `routeKm`, `roundTripKm`, `fitsRange`,

## 2. How I learned about teammates' work

- After every pull: `git log --stat --format='%h %an %s' ORIG_HEAD..HEAD` showed what came in. `git pull` itself
  does not list incoming commits.
- `git fetch -q && git log --oneline --stat HEAD..origin/main`, then `git diff HEAD origin/main -- NOTES.md` to read only
  the new notes lines.
- I read files in full with `cat` after pulling (scheduler.js once, all of it) and used `git show <sha> -- file` for
  a3's adoption diff. I grepped CONTRACTS.md sections.
- Waiting: I ran the playbook's bounded loop (`fetch; log HEAD..origin/main -- <path> | grep -q . && break; sleep 20`)
  4 times. The waits took about 4, 1, 1 and 3 minutes, so roughly 9-10 minutes of wall time went into polling.
  Foreground `sleep 20` inside the loop was not blocked.

## 5. Friction and confusing output

- `git pull` prints `Rebasing (1/1)Successfully rebased and updated refs/heads/main.` with no newline between the two
  parts, and it does not list which teammate commits came in. I had to know to use `ORIG_HEAD..HEAD`. That is not in
  the playbook, and ORIG_HEAD is fragile (other commands overwrite it).
- `git pull -q` hides everything, including what arrived. Without `-q` you still learn nothing useful beyond the sha
  range `c224c95..62061ec`.
- There is no way to block on "something happened that concerns me". I polled on paths, and a reply addressed to me
  in NOTES.md is just a line in a shared file I have to diff for. One poll keyed on src/scheduler.js would have missed
  a NOTES-only reply.
- `git pull && npm test && git push` is not atomic: someone could push between my test and my push. A rejected push
  would catch that, but nobody checks that the merged tree passes. It never happened here.
- Odd for the experiment: when I read docs/AGENTS-git.md, a tool hook injected the hs playbook (docs/AGENTS.md) into my
  context, although my instructions said not to read other hyperscion files. I ignored it.

## 6. Compared with an ideal tool

- A feed or blocking wait on "commits touching X, or NOTES lines mentioning @a2" would replace the sleep loops and
  path guessing.
- Sync output should say "incoming: c224c95 a3 scheduler: ... (src/scheduler.js, CONTRACTS.md)" instead of a bare
  rebase message.
- A land that runs tests on the merged tree and pushes atomically (check-then-land) would close the test/push race.
- Structured mentions or review requests for "a3, consider using X" instead of free text in NOTES.md. My orderRoute
  offer only worked because a3 happened to read NOTES.
- For this small 5-agent team on disjoint files, git was adequate. Per-owner files plus union-merged NOTES avoided
  every conflict, so what was missing was awareness, not merging.

## 7. Features wanted

1. Blocking watch: `wait --path X --mention @a2`.
2. A pull summary of incoming commits by author.
3. Atomic test-then-push.
4. Lightweight addressed messages and requests instead of a shared notes file.
