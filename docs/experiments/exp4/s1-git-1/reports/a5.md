# a5 report (git arm, s1-git-1)

## 1. What I built

- `src/cli.js`: `plan <dayfile> [--json]`, wired through `model.loadDay` -> `scheduler.plan` -> `pricing.price` -> `report.renderReport` / `report.reportJson`. Exit codes are 0 for success, 1 for an unreadable file, bad JSON or a ModelError (each problem gets its own line on stderr), and 2 for a usage error. `--json` returns the pinned fields (`toOutput`) merged over a4's `reportJson` extras, merged per stop. Exports `run/toOutput/parseArgs`.
- `test/integration.test.js` (13 tests). Shared `checkPlan` property checks use my own haversine: every package appears exactly once (in a trip, or unassigned with a reason). For each trip it checks payload, depot->stops->depot range, delivery windows (waiting allowed) and that the trip ends within the day. It also checks that one drone's trips don't overlap, that prices cover exactly the delivered packages, and that the total equals the sum. Further tests: p19 is unassigned as too heavy, the human report prints, `--json` is deterministic and matches the report total, there's a usage/missing-file/bad-JSON test, and a seeded random-day property test runs 40 generated days through `cli.run` in-process.
- Fixtures: `edge-unreachable.json` (heavy, far and late packages), `edge-invalid.json` (ModelError with 5 problems), `edge-crowded.json` (1 drone, 30-minute day, the express package must win), `edge-empty.json`.
- CONTRACTS.md cli section pinned (368d0f9).
- Final state: main at 96399cf. 62/62 tests pass, the CLI on day1 delivers 18 packages, p19 is unassigned, EUR 120.70, exit 0.

## 2. How I learned about teammates' work

- After every push: `git log --oneline -n 3..6 origin/main` (sometimes with `--stat`), then `git show <sha> -- CONTRACTS.md NOTES.md` for the interface parts. I read NOTES.md / CONTRACTS.md after each pull.
- The `pull` inside my `commit && pull && npm test && push` line acted as the "feed": the fetch summary line (`a335679..4804289 main -> origin/main`) told me something arrived, and then I ran log on it.
- Two bounded fetch loops: one waiting for `src/scheduler.js` (it was there on iteration 2, about 20 s), and one generic "anything new?" loop at the end that ran its full 15x20 s (5 min) with nothing new, plus a final 3-minute one. About 8-9 minutes of wall-clock polling in total, nearly all of it at the end, spent confirming the team had gone quiet. Git has no way to say "everyone is done".

## 4. Conflicts, rejected pushes, rebases

- 7 pushes, 0 rejected, 0 conflicts. Pull-before-push rebased my single commit 6 times (`Rebasing (1/1)Successfully rebased and updated refs/heads/main.`). Every rebase was clean because I only touched my own files plus NOTES.md (union merge) and my own CONTRACTS.md section.
- There's still a race window between `pull`/`npm test` and `push`. I never lost it, so I never saw `! [rejected]`.

## 5. Friction and confusing output

- My own pipeline bug: `git pull && npm test 2>&1 | grep ... && git push`. The grep's exit status masks `npm test`, so a failing suite would still have been pushed. I caught it after one push and switched to `npm test >log && git push`. Git and the playbook give no guard here. Nothing ties "tested" to "pushed", and the tested tree isn't recorded anywhere.
- `git show 210419b | cat; tail -6 NOTES.md`: the diff's context lines ran straight into the tail output. I briefly thought union merge had duplicated NOTES lines and spent a minute on `git blame --line-porcelain` to rule it out. That one is on me, but NOTES as a flat log is hard to scan for "lines addressed to me".
- `Rebasing (1/1)Successfully rebased...` has no newline between the progress text and the result. It's fine, just noisy.
- There's no way to know whether teammates were done or just thinking. 5+ minutes of empty fetch loops is the price.
- No signal of which commit a teammate's tests ran against. "Passes on 368d0f9" in NOTES was my manual workaround, and it was already stale, since I actually tested on ff9a45d.

## 6. Compared with an ideal tool

- A push-based feed (new commits by path/author, NOTES lines mentioning `@a5`) instead of fetch loops. Mentions in NOTES are effectively the review channel, and git can't route them.
- Atomic "land if tests pass on the merged tree", so the pull/test/push race and my grep-masking bug can't happen.
- Per-module (per-file) landing: everyone touched disjoint files, so rebases were pure ceremony. An ideal tool would do it silently and tell me only about content I depend on.
- A team "quiescent / done" signal, or presence, to end the integrator's wait.
- A dependency-aware nudge: "src/scheduler.js changed; your integration tests depend on it, rerun". I did this by reading the log.

Candidly: with good ownership boundaries and union-merged NOTES, git was adequate here. Coordination cost was low, around 10 minutes, mostly polling.

## 7. Features I wanted

- `git watch`-style blocking wait on a path or author (without the shell loop), and on `@me` mentions in NOTES.
- `push --if-tests-pass` (a server-side check on the merged tree).
- Recording which commit a test run passed on, visible to teammates.
- Presence/"I'm done" status per agent.
