# a3 report: scheduler (git arm)

## 1. What I built

`src/scheduler.js` with `plan(day) -> { trips, unassigned }`. It is a greedy planner. Packages are ranked: express first, then the earliest window close, then the heaviest. Packages no drone can ever deliver are pre-classified with a `code` and a `reason` (`too-heavy`, `out-of-range`, `window`, `day-length`, `no-drones`). After that, whichever drone is free earliest builds its next trip:

- It seeds the trip with the best-ranked package it can leave for right away. Packages whose window opens later are only a fallback, because they would keep the drone idle.
- It then grows the trip by cheapest feasible insertion.
- Every candidate trip is checked against payload, range, the windows (at most 10 min of hovering per trip), the end of the day, and "never delay the trip start".
- Finally it polishes the stop order with a2's `geo.orderRoute({accept})`.

Leftover packages become `no-capacity`. The Plan shape is pinned in the CONTRACTS.md scheduler section (trip `id/drone/depot/start/end/packages/stops[{package,arrive,wait,depart,legKm}]/distanceKm/payloadKg`). `test/scheduler.test.js` has 12 tests: an invariant checker plus edge cases for payload, range, windows, express, day length, multiple drones, the model `loadDay` output, the edge-unreachable fixture and 2-opt optimality. On day1: 13 trips, 18 delivered, p19 unassigned (too heavy).

## 5. Friction and confusing output

- A rejected push after a pull that said `Current branch main is up to date.` The window between pull and push is the length of the test run, and with 5 active agents it was hit 2 of 4 times. The rejection text ends in `hint: 'git pull' before pushing again.`, which I had literally just done. It isn't confusing once you know it, but it is a pure retry loop the tool could do for me.
- My own mistake that git made easy: an early `npm test 2>&1 | grep ... && git push` pipeline would push even if the tests failed, because grep succeeds. "Push only if tests pass on the merged tree" is entirely up to the agent's shell discipline. There is no `--check`.
- `git pull` output (`Rebasing (1/1)Successfully rebased...`, with no newline between the two) does not list *what* came in. I had to run a separate `git log` with the right range, and after the pull `HEAD..origin/main` is empty, so you have to remember the old sha or use `ORIG_HEAD`/the reflog.
- No way to know whether anyone read my NOTES line, except by seeing a reply commit.

## 6. Compared with an ideal tool

- **Atomic "test on latest main + land":** retry on rejection automatically and re-run the check on the merged tree (like `hs land --check`). It would have removed both rejected-push loops and the risk of a pipeline that pushes untested.
- **A push feed with per-file and per-mention filtering:** "tell me when someone touches CONTRACTS.md#scheduler or writes @a3". It would replace both sleep loops and the `grep a3 NOTES.md`.
- **Pull output that summarizes incoming commits** (author, files, message) instead of only "Successfully rebased".
- **Interface-aware review:** a3's Plan shape is a contract for a4 and a5. Git gave me no lightweight Ask. I just pushed it, which worked here only because nobody had built against a conflicting guess. Ideally, consumers would be notified when the contract section changes.
- Honestly, for this small team with disjoint files, git plus a union-merged NOTES.md was adequate. The pain points are latency and ceremony, not correctness.

## 7. Features I wanted

1. `push --check "npm test"` with automatic pull/rebase/retry.
2. A blocking `watch --path` / `--mention a3` instead of sleep loops.
3. `pull` printing the incoming commit list.
4. Owner-aware notifications when someone edits a file or contract section I own.
