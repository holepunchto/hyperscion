# a1 report — model owner

## 1. What I built

`src/model.js`: `loadDay(json|string)`, `loadDayFile(path)`, `DayValidationError`
(`code: 'EINVALIDDAY'`, `errors[]` with every fatal problem). It returns a deeply frozen `Day`
with arrays in file order, `depotsById/dronesById/packagesById`, `drone.home` (the depot's
`{lat, lon}`), `package.window` (`[e, l]` or null), `package.express`, defaults (priority
standard, serviceMinutes 0) and `warnings[]`. Fatal errors: bad shapes, duplicate ids, unknown
depot, bad priority, malformed window, lat/lon out of range. Undeliverable packages
(too heavy, too far, windows that can't be met) are passed through for the scheduler.
`test/model.test.js` has 10 tests, including a5's edge fixtures. The CONTRACTS.md model
section is pinned. I left main at #25: 67/67 tests pass, and `node src/cli.js plan
fixtures/day1.json` prints a full report (18 delivered, p19 unassigned "too heavy").

## 2. How I learned about teammates' work

- A background `hs watch --json >> .hs/feed.jsonl` plus `tail`. It worked for #2–#10. After the
  network outage (see 5) **it silently stopped receiving anything**: the file ends at #10 even
  though main reached #25. I only noticed at the end when I ran `wc -l`. From about #11 on,
  everything I learned came from the `incoming from teammates` lists printed by `sync` and
  `land`, and from blocking waits.
- I used `hs watch --path /src/scheduler.js --count 1 --timeout 600` and
  `--path /src/report.js` to wait for the modules I depended on. This was the best feature: no
  polling, and it returned with the changeset line.
- I used a plain `hs watch --count 2/3 --timeout 300` to idle until teammates landed something.
- I used `hs show 10 --path src/scheduler.js`, `hs show 18/20 --path src/cli.js` and
  `hs log --oneline` to read diffs, and `grep a1 NOTES.md` to find requests aimed at me.
- The feed half-replaced polling. Blocking `watch --path` fully replaced it. The background
  feed can't be trusted because it dies silently.

- **Auto-rebase** on #13 (`main moved: /NOTES.md (#12 a2) ... merged cleanly`). It was smooth.
  The union merge on NOTES.md worked every time.

- **Flip**: my NOTES land `#11` (made offline, `!! no peers online: landed locally only`) was

  land undid (conflict); land it again`. The playbook says "(conflict)" but it merged cleanly. I
  landed it again as #13 with no loss.
- **Rejected check**: one (see 3). The playbook was accurate: "Your files now include main".

## 5. Friction, bugs, confusing output

1. **Network outage, ~3–4 min.** `hs land` printed `No peers found, using local state` /
   `!! no peers online: landed locally only`. `hs doctor` said `peers 0`, `indexer hub has seen
   #10 !! behind`, and `verdict offline: no peers...`. The doctor output was clear. `ps` showed
   teammates' watchers alive, so the problem was the network or discovery, not the hub process.
2. **`hs push` with no peers prints a raw stack trace:**
   `hs: Error: no peers found\n at file:///.../lib/cli.js:1384:46 ...`. On the next try it
   printed `push timed out`. It should print a friendly message the way `land` does.
3. **The background `hs watch --json` died silently.** It exited 0 at some point, as the
   task-completion notice showed only at the end, and it wrote nothing after #10. The feed
   wrote no error line and no reorg line, and gave no hint. This is the most serious issue,
   because the playbook says to rely on the feed.
4. **`hs restore <path>` after a failed `land --check` did nothing useful.** `land` had
   already committed my working copy, so `restore` printed `restored /src/model.js` but left
   my edited content in place. I had to `hs cat /src/model.js > src/model.js` to get main's
   version back. "restored" was misleading. I counted this as a confusing message.
5. `hs diff NOTES.md` gave `hs: UNKNOWN_ARG: NOTES.md`. diff doesn't take a path (or wants
   `/NOTES.md`?), and the error doesn't say which.
6. The `(conflict)` in `restored your land that a concurrent land undid (conflict)` was
   puzzling, because the following merge was clean.

## 6. Compared with git

Better than a shared git repo here:

- `land --check` runs tests on main + my change and re-checks if main moves. This caught a
  real semantic clash (#20 vs my message change) that `git pull --rebase && git push` would
  have let through unless I remembered to run tests after the rebase.
- Auto-rebase and retry on land, plus union merge for NOTES.md. With 5 agents appending to
  NOTES and CONTRACTS, git would have produced many push rejections and manual NOTES conflicts.
- `watch --path X --count 1` is a clean "wait for teammate" primitive that git doesn't have.
- `incoming from teammates` with messages on every sync is a better summary than
  `git pull` output.

Worse or equal:

- The CONTRACTS.md conflict is identical to git, because it's line-adjacent.
- The offline period: with a git server outage I'd simply get a push failure. Here I got a
  local land that later flipped, a feed that died silently, and a stack trace from push. It
  was more states to reason about (provisional, undone, restored), although no work was lost.
- `restore` semantics after a rejected land are surprising. In git I'd know exactly what
  `git checkout origin/main -- file` does.

Overall, for this workload, hs was moderately better than git. The coordination features
(`--check`, blocking watch, union notes) beat its reliability rough edges.

## 7. Features I wanted

- A watcher that reconnects after a network loss, or at least writes an `{"type":"error"}` or
  `offline` line and exits non-zero.
- An `hs restore --from-main <path>` (or `hs checkout main -- path`) to drop a committed but
  unlanded edit.
- `hs diff <path>`.
- A hint when someone lands a change that depends on a message or format I own (e.g. a test
  that pins my error format), like a "touches strings from /src/model.js" heads-up. A simpler
  version: `watch --for-me` could include changes that mention my owned paths in their message.
