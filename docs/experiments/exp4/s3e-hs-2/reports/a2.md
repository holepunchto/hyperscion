## 1. What I built

`src/geo.js`: `distanceKm` (haversine, R=6371, accepts points, depots or packages), `travelMinutes`,
`routeKm`, `roundTripKm`, `withinRange`, `orderStops` (nearest neighbour + 2-opt, non-mutating,
deterministic), `planTrip(depot, stops, {speedKmh, serviceMinutes, start, order, waitForWindow})`
returning km, start/end and per-stop ETAs (`arrive/depart/wait/late`, `onTime`). I pinned the CONTRACTS.md
geo section in my first land. `test/geo.test.js` has unit tests plus a cross-check: for every valid fixture,
`planTrip` reproduces each scheduler trip's km, arrivals and end within 0.02 and checks range.
Lands: #4, #9, #12, #15, #17 (notes only), #26. Main at #27 when I left: 68 pass / 0 fail / 0 skipped.
`node src/cli.js plan fixtures/day1.json` gives 13 trips, 18 delivered, p19 unassigned (too heavy), 100.76 km.

## 2. How I learned about teammates' work

- Background `hs watch --json >> .hs/feed.jsonl` for the whole run (26 changesets, 0 reorgs). I looked at it with `tail` a few times.
- I mostly used **`hs watch --path <file> --count 1 --timeout 600`** as a blocking wait (for /src/model.js and /src/scheduler.js, then also /NOTES.md and /src/geo.js). I used it about 7 times. This replaced polling completely, and it worked well.
- After each wait I ran `hs sync`. Its "incoming from teammates" list, together with reading the synced files directly (scheduler.js, CONTRACTS.md, NOTES.md), was my main source of information. I never needed `hs show <n>`, because reading the synced file was faster for the whole-module changes I was looking at.
- The `--check` lands also listed incoming changesets, which kept me up to date for free.

## 5. Friction, bugs, confusing output

- **Outage of about 2 minutes (after #10).** `hs sync` printed `no peers found, using local state` / `up to date with main #9` while my own feed had already shown `#10` and `settled through #10`. Saying "up to date" is misleading here: hs knew from the feed that main was further ahead. `hs status` did say so correctly: `main is at #10 or later (from your feed); this shows #9. hs fetch to update`.
- During the outage, `hs show 10` printed a raw stack trace (`hs: Error: no changeset #10 at renderShow (.../lib/cli.js:1087:21) ...`). It should have said something like "#10 is known from the feed but not fetched; no peers online".
- During the outage, `hs cat /src/scheduler.js` silently returned the old skeleton, with no warning that it was stale.
- `hs doctor` during the outage gave `verdict offline: no peers. ... run hs seed on an always-on hub worktree`. That advice is wrong for a team member, who is told never to run seed. It also said "indexer hub has seen #9", although the hub had clearly seen #10.
- There was no foreground sleep available, so I used `hs watch --path /nowhere --count 1 --timeout 60` as a timed wait. That printed `watch: no peers yet, waiting...`, and after the timeout the next sync worked.
- A minor point: a land without `--check` (a NOTES-only change) prints `(your land sits on these untested ...)`. That is fine and clear.

## 6. Compared with git

Better than git here:
- Blocking `watch --path` instead of fetch/poll loops was the biggest difference. In git I would have had to poll `git fetch && git log origin/main -- src/scheduler.js`.
- `land --check` rebases, tests the merged tree and pushes in one step. With 5 agents pushing to one branch, git would have meant a lot of non-fast-forward `pull --rebase` retries. NOTES.md union merge would have needed a `.gitattributes merge=union`. git supports that too, but here it was already set up.
- The "incoming from teammates" summary on every sync/land is a nicer commit digest than `git log HEAD..origin/main`.

Worse than git, or no different:
- The outage. With a central git remote down you get a hard error, which at least is honest. hs said "up to date" and served stale `cat` output.
- Per-file module ownership meant there were essentially no conflicts. In this setup git would also have rebased cleanly, so most of the win is ergonomics, not merge capability.
- Review/Show/Ask never came into play for me, because I only touched my own files and NOTES.

## 7. Features I wanted

- `sync`/`cat`/`show` should warn loudly when the feed knows of newer changesets that can't be fetched, and should not say "up to date".
- `hs show <n>` should give a friendly error instead of a stack trace.
- A `hs watch --grep a2` / mention filter, to block until someone mentions me in NOTES or in a land message.
- A built-in `hs wait <seconds>`, or a retry-until-peers option for sync (`hs sync --wait-peers 60`).
