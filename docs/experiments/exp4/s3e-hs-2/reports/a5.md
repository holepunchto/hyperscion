# a5 report: integrator (src/cli.js, test/integration.test.js, fixtures/edge-*)

## 1. What I built
- `src/cli.js`: `plan <dayfile> [--json]` runs model.loadDay → scheduler.plan → pricing.price → report.renderReport. Exports `run`, `toOutput`, `main`. Exit codes: 0 ok, 1 for an unreadable or invalid day file (`skyhop: <file>: invalid day file: N problems: ...` on stderr, nothing on stdout), 2 for usage. The CONTRACTS cli section is pinned.
- `test/integration.test.js` (11 tests). It recomputes everything independently with its own haversine: every package appears exactly once (on a trip, or unassigned with a reason), payload, range per trip, arrival ≤ window end (with waiting), trip back by day end, no overlapping trips per drone, prices recomputed from the pinned formula, total = sum, p19 unassigned as too heavy, deterministic output, the report lists drones/unassigned/reasons, CLI exit codes.
- Fixtures: `edge-unreachable` (heavy/far/late), `edge-empty`, `edge-invalid`, `edge-overbooked` (1 drone, 60-minute day, multi-trip, out of time, express first), `edge-windows` (inverted window, unreachable window, waiting for early windows, range that only one depot's drone covers).
- Final state: main #27, `npm test` 68/68 green. day1: 13 trips, 18 delivered, p19 unassigned, 100.76 km, 124.44 EUR.

## 5. Friction and bugs in hs
- Outage around 02:35: `hs land -m ... --check "npm test"` printed `no peers found, using local state` (twice) and then `landed #11` and `!! no peers online: landed locally only. Run \`hs push\` once a holder is online`, exit 2. That was clear. `hs doctor` was helpful: `indexer hub has seen #10 !! behind`, `verdict offline: no peers`.
- `hs push` while offline printed a raw stack trace instead of a message: `hs: Error: no peers found\n at file:///.../lib/cli.js:1384:46 ...`, exit 1.
- **The background `hs watch --json` silently stalled after the outage.** The process stayed alive but wrote no new lines, not even #11 after the push succeeded. I only noticed because `hs log` showed #11 and the feed didn't. `hs watch --stop` plus a restart resumed correctly from #11, so the resume itself works. A feed that goes quiet with no error is the worst way for it to fail.
- I wrote a retry loop around `hs push`. It succeeded on the 4th try, about 2 minutes later.
- Also confusing: `ps` showed two `bin.mjs watch --json` processes. One was mine; I assume the other belonged to a teammate. Nothing in `hs watch --stop` output says which worktree a watcher belongs to.

## 6. Compared with git
- Better: the push-based `watch --path ... --count 1` is a real improvement over `git fetch` polling for "tell me when the scheduler lands". `land --check` (rebase, test the merged tree, land, retry if main moved) replaces fetch/rebase/test/push races. With 5 agents pushing to one git branch I would have hit non-fast-forward rejections several times. The union-merge NOTES.md, the per-file history and the "incoming from teammates" summaries were also good.
- Worse or equal: during the hub outage, git with a shared bare repo would have failed the same way, but git doesn't leave a background process silently stale. Semantic conflicts (#16 vs #18) are invisible to both, and only tests catch them. The repo had no merge conflicts at all thanks to module ownership, so much of hs's machinery went unexercised. Git with per-agent branches and a single integrator would also have worked, but more slowly.

## 7. Features I wanted
- A watch feed that reports its own health (an `{"type":"offline"}` or heartbeat line) and reconnects after the hub returns.
- Clean errors from `hs push` (no stack trace), and an automatic retry of pending pushes when peers reappear.
- An "also touched recently by" warning when someone lands a change to a *related* file in the same window, for example noting that a1 also changed the error message within the last few minutes.
- `hs watch --stop` should list which watchers belong to me and which to others.
