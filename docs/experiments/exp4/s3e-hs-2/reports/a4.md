# a4 report: pricing + report

## 1. What I built

- `src/pricing.js`: `price(plan, day) -> { currency:'EUR', rates, prices:{id:n}, lines:[breakdown], total }` and `pricePackage(pkg, depot)`. The formula is pinned in CONTRACTS.md: `2.50 + 0.80*km + 0.50*kg + 3.00 express`. `km` is the haversine distance from the delivering drone's home depot to the destination. Each price is rounded to cents once, and `total` is the sum of the rounded prices. Uses `geo.distanceKm`.
- `src/report.js`: `renderReport(plan, priced, day) -> string` and `reportData(...)` (the JSON-friendly form).
  - Per drone, including idle drones: each trip's depart and return times, km and load, then each stop's ETA, weight, EXPRESS flag, window, a LATE flag and the price.
  - Unassigned packages with their reasons, then totals.
  - ETAs, end times and km come straight from the scheduler (`stops[].arrive`, `end`, `distanceKm`). If those are missing, they are computed.
- Tests: `test/pricing.test.js` and `test/report.test.js`, 15 tests in total. They include one that runs the real model and scheduler on day1.
- Lands: #3, #14 (landed offline as a local #4, see §4), #19, #21 and #25.
- Final state on main #27: `npm test` gives 68 pass and 0 fail. `node src/cli.js plan fixtures/day1.json` prints the full report (13 trips, 18 delivered, p19 unassigned "too heavy for every drone", 124.44 EUR). Every edge fixture renders.

## 2. How I learned about teammates' work

- **Feed:** `hs watch --json >> .hs/feed.jsonl`, read with `tail`/`grep`.
- **Waiting:** `hs watch --path /src --path /CONTRACTS.md ... --count 1 --timeout 600` to block until something relevant landed.
- **After each event:** `hs sync`, which prints the "incoming from teammates" list and was the most useful output.
- **Diffs:** `hs show 18 --path src/cli.js` and `hs show 23 --path CONTRACTS.md`.
- **Overview:** `hs log --oneline`.
- **Interfaces:** mostly CONTRACTS.md and NOTES.md, which arrived through sync.

I synced about 10 times. The blocking `watch --path --count 1` did replace polling, and that worked well. The background JSON feed was less reliable for me. My first watcher, started with `nohup ... &` inside a foreground shell, died silently after #5 with an empty stderr. I didn't notice until about #22. I restarted it with a proper background task, and it resumed and backfilled correctly.

## 4. Conflicts, rebases, flips

- **Hub outage, 02:34 to 02:38:** `hs sync` printed `no peers found, using local state` / `up to date with main #3` even though my feed already showed #5. I landed the report anyway, with `--check`: `landed #4`, `!! no peers online: landed locally only. Run hs push once a holder is online`, exit 2.
- **What happened to that land:** a2 had already landed a real #4. When peers came back, my next `hs sync` printed `synced to main #14`, and my land now sits on main as #14 after 9 teammate changesets. It was rebased automatically, with no conflict. I saw no reorg line or "undone" warning. That is fine, but my land number silently changed from #4 to #14. I count it as 1 auto-rebase, not a flip.
- **The rest:** there were no real conflicts. The other `--check` lands brought in 1 to 4 incoming changesets each and passed. NOTES.md union merge worked.

## 5. Friction, bugs, confusing output

1. **`hs show 5` while offline printed a raw stack trace:** `hs: Error: no changeset #5 at renderShow (file:///.../lib/cli.js:1087:21) ...` with **exit 0**. It should be a friendly "not fetched yet / offline" message with a non-zero exit.
2. **`hs sync` while the hub was down said `up to date with main #3`** while my feed knew #5. `hs status` correctly said `main is at #5 or later (from your feed)`, but sync claiming "up to date" is misleading.
3. **The stale hint points to the wrong command.** After #27, sync reported 2 files `could not be fetched: no online peer holds it`. `hs status` said `stale ... (behind main, run hs fetch)`. `hs fetch` then said `main at #27, fetched 2 file(s)`, but `hs status` *still* showed both files stale and they weren't in my worktree. Only a further `hs sync` cleared them. I looped `fetch` 6 times (about 3 minutes) before trying sync. Either fetch should materialize the files, or the hint should say `hs sync`.
4. **`no online peer holds it` appeared while `hs doctor` a moment later said `peers 1 ... verdict ok`.** A transient holder gap is plausible (a5 had just landed), but the message tells you to run `hs seed` / add a blind peer. That is alarming advice for something that cleared up by itself within about 30 s.
5. **The offline land renumbered silently (#4 to #14).** Not wrong, but `hs status` / `hs log` don't tell you "your local #4 is now #14".
6. **The background watcher died silently.** Possibly my fault for how I backgrounded it, but nothing told me the feed was stale. A heartbeat line, or a status warning like "your feed hasn't updated since X", would help.

## 6. Compared with git

- **Better than a shared git repo here:**
  - `land --check` is effectively "pull --rebase, test, push" in one atomic command that retries if main moves. With 5 agents landing every few minutes, git would have given me several rejected pushes and manual `pull --rebase` cycles.
  - Per-file 3-way rebase meant I never saw a conflict, even though CONTRACTS.md was touched by everyone.
  - The `merge=union` NOTES.md removed the most common git conflict in this setup.
  - `watch --path X --count 1` is a really nice primitive that git simply doesn't have (you would poll `git fetch`).
  - The "incoming from teammates" list on every sync and land was better than `git log HEAD..origin`.
- **Worse:**
  - Availability. Twice the "server" (holder) wasn't reachable, and hs degraded to confusing states (stale files, "up to date" lies, a stack trace).
  - With a git remote that is down you get one clear error. Here I got partial states and had to learn the difference between fetch and sync.
  - Offline landing is a plus in principle, but the silent renumbering and the provisional/settled machinery add mental load that git's "push rejected" doesn't.
- **On balance:** somewhat better than git for this parallel, many-small-lands workflow, as long as the holder is up.

## 7. Features I wanted

- `hs status` should warn when the `watch` feed process is dead or behind.
- A notice like `your local #4 landed as #14` after an offline land is pushed.
- `hs fetch` should make stale files current in the worktree, or the hint should say `hs sync`.
- `hs show` and similar commands should print friendly offline errors with no stack traces and a correct exit code.
- `hs log --grep` / `hs notes --since <n>` to see NOTES lines added since my last read, so I don't post duplicates.
