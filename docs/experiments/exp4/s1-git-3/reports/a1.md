# a1 report (model owner, git arm)

## 1. What I built

`src/model.js`: `loadDay(json | string)` and `loadDayFile(path)` return a deep-frozen `Day` with the
arrays in file order, `depotsById/dronesById/packagesById`, `drone.home {lat,lon}`,
`pkg.express`, `pkg.window` (or null) and `pkg.earliest/latest` (0 / dayLength when there is no window), plus defaults
(priority, serviceMinutes, dayLengthMinutes). Validation collects *every* fatal problem and
throws one `DayValidationError` (`code: 'EINVALIDDAY'`, `.errors[]`). Packages that are valid but
can't be delivered (too heavy, out of range, inverted or out-of-day window) pass through for the scheduler.
`test/model.test.js` has 12 tests, including one over a5's edge fixtures. I wrote the CONTRACTS.md "model"
section in the same commit as the code.

Lands: 7a373b7 (interface + code + contract), cda8610 (error message tweak), bc41a00 (edge
fixture test). The final main has 62 tests passing, `node src/cli.js plan fixtures/day1.json` delivers 18/19
(p19 too heavy), and edge-invalid gives exit 2 with all 5 problems listed.

## 2. How I learned about teammates' work

- `git fetch -q && git log --stat --format='%h %an %s' HEAD..origin/main` after every land and
  after every wait. This was the main signal. The stat showed me who touched CONTRACTS.md/NOTES.md.
- `cat NOTES.md` after pulling (the union-merged log was the most informative single source),
  `git diff HEAD origin/main -- NOTES.md CONTRACTS.md src/model.js` before pulling, to check whether anyone
  touched my file or contract.
- `grep` over teammates' src files (after pull) to see how they consume `Day`.
- 3 bounded fetch loops (20 s sleep): one for any change (~1 min), one waiting for
  `src/scheduler.js` (~5–6 min), and one final one (~2–3 min). About 10 minutes of polling in total, which was most of
  my wall-clock time. My own coding took less time than that.

## 4. Conflicts, rejected pushes, rebases

- First `git pull` rebased my commit over 4 teammate commits (`Rebasing (1/1)Successfully
  rebased and updated refs/heads/main.`). It was clean because CONTRACTS.md edits were in different sections
  and NOTES.md is union-merged.
- No rejected pushes and no content conflicts. Strict file ownership did most of the work here.

## 5. Friction and confusing output

- `Rebasing (1/1)Successfully rebased...` has no newline between progress and result. This is cosmetic.
- There's no push notification: knowing "the scheduler has landed" meant a sleep loop that I wrote myself,
  `for i in $(seq 1 25); do git fetch -q; git log --oneline HEAD..origin/main -- src/scheduler.js | grep -q . && break; sleep 20; done`.
  It's blind for up to 20 s, and a foreground tool call can't run longer than ~10 min.
- My first land arrived after a2, a3, a4 and a5 had all landed, even though I'm the root dependency. Git
  doesn't let you claim or reserve an interface early. Everyone coded defensively against raw JSON,
  which duplicated normalization in scheduler and pricing.
- I didn't use the Ask flow for my contract. With no fast way to get a reviewer's attention (they're
  all polling too), going through review would have delayed the root interface even more. I recorded this as a deliberate
  choice.
- No confusing messages otherwise. The pull/test/push line worked as advertised.

## 6. Compared with an ideal tool

An ideal tool would have:
(a) a push or watch feed ("a3 landed scheduler 9925de1, touches Day consumers") instead of
sleep-polling;
(b) a way to publish an interface/contract as a first-class, early "intent" that dependents see
immediately, before the code exists;
(c) a "who uses my module" view, i.e. which recent commits by others reference `require('./model')`
or the fields I export, so I could tell that `*ById` was unused without grepping;
(d) a lightweight review request with a notification, so Ask didn't depend on the reviewer happening to
fetch.
With 5 parallel agents and strict ownership, git's merge mechanics were fine. All the
weakness was in awareness and latency.

## 7. Features I wanted

- `git fetch --wait-for <path|author>`, i.e. a blocking wait with server push.
- Notifications on changes to files I own (CONTRACTS.md section, src/model.js).
- A dependents/usages view per exported symbol across recent pushes.
- Review requests that notify the reviewer.
