# a3 report (scheduler), git arm

## 1. What I built

`src/scheduler.js`: `plan(day) -> Plan`. It's a greedy insertion heuristic. Packages that can never be delivered are filtered out first, each with a reason: too heavy for every drone, out of range for every drone, window impossible (inverted, unreachable in time or outside the day), or no drones at all. The rest are sorted express first, then by earliest deadline. Each package then goes to the cheapest feasible spot: any position in any existing trip of any drone, or a new trip in any gap in a drone's schedule. A spot counts as feasible when payload, range, windows and day length all hold, the drone's next trip isn't pushed back, and no express stop already planned slips by more than 10 minutes. The start of a trip is chosen "just in time" so the drone waits at the depot instead of hovering at the stop. I pinned the Plan shape in CONTRACTS.md first, before any code, at ca3f9f6. It is a superset of the CLI `--json` fields, and its stop fields match geo.tripTimeline. `test/scheduler.test.js` has 17 tests. They include an independent feasibility checker, every unassigned category, multi-trip, consolidation, range-bound trips, day-length exhaustion, express-vs-standard under scarcity, windows, model.loadDay input, all team fixtures and 15 seeded random days. Final main is 26 commits; `npm test` gives 76 pass / 0 fail / 0 skipped. On day1 the CLI shows 18/19 delivered (p19 too heavy), 12 trips, 97.2 km and 116.43 EUR.

## 2. How I learned about teammates' work

- `git fetch -q && git log --oneline --stat HEAD..origin/main`: before every pull, about 8 times. The `--stat` was the most useful part, because it showed at a glance whether someone touched CONTRACTS.md, NOTES.md or anything near my module.
- Reading `CONTRACTS.md` and `NOTES.md` in full after pulling, and `git diff HEAD origin/main -- NOTES.md` to see only the new notes. NOTES.md did most of the coordination; commit messages were second.
- I never needed `git show <sha>` for code diffs. The contracts were pinned well enough that reading CONTRACTS.md was sufficient.
- Polling: two bounded fetch loops (20 s sleep, at most 12–15 iterations) while waiting for feedback. Together they took roughly 3–4 minutes of wall-clock wait. There was no polling while blocked: by the time I had a first version, model, geo, pricing, report and cli had all landed, so I was never actually blocked.

## 4. Conflicts, rejected pushes, rebases

- 6 pushes to main, 0 rejected. `git pull` rebased my commit 5 times ("Rebasing (1/1)Successfully rebased and updated refs/heads/main."), with no conflicts. NOTES.md never conflicted thanks to the union merge. CONTRACTS.md was edited by several people in parallel, but always in different sections, so the rebases were clean.
- I was lucky that no push lost a race: someone pushed between my pull and my push several times, but never within the ~1 s `npm test` window.

## 5. Friction and confusing output

- `git pull -q && git push -q` (my first push) printed nothing at all. I had to run `git log` to confirm the push had happened, because `-q` hides success as well as failure.
- `git pull` output: `Rebasing (1/1)Successfully rebased and updated refs/heads/main.` The progress line and the result share a line. That's cosmetic, but it also doesn't say *what* came in. I still had to run a separate `git log` to see which teammate commits I had just rebased onto, so I tested on top of code I hadn't looked at.
- There's no way to wait for "someone mentioned a3" or "someone changed CONTRACTS.md scheduler section". The fetch loop wakes on *any* commit (it woke on e517088, a cli unit test), so I had to read and filter by hand.
- "Is my push safe?": `npm test` passing locally before the push doesn't prove main is green after it, since someone could push in the gap. In practice it was fine, but nothing confirms it.
- My own slip, not git's, but worth recording: a parameter sweep with `sed` left a tuning value (0.2) in the file, and I committed it as "mild preference" in 266a80a. Git happily landed it. A review step or a diff summary at push time would have caught the mismatch between message and diff. I fixed it explicitly in d709324.

## 6. Compared with an ideal tool

For 5 agents in parallel with one hot shared file (CONTRACTS.md) and an append-only log, git was adequate. The union-merged NOTES.md plus small commits avoided every conflict. An ideal tool would have:

- pushed me a feed of relevant changes instead of me polling: changes to files and sections I depend on, and NOTES lines that mention a3;
- shown "what you just rebased onto" (authors, files, notes added) as part of the pull result;
- made the land atomic with the test run (test on the merged result on the server, or a reject if main moved), so "my land is safe" isn't an assumption;
- treated contract sections as first-class objects with owners, so "a4 consumes scheduler.Plan" is known and a4 gets notified when I change it;
- offered a lightweight review/ack flow for contract changes. I never used `ask/` branches, because pushing a pinned contract straight to main was faster and nobody objected. That only worked because everyone was well-behaved.
