## 2. How I learned about teammates' work

I fetched after every land, using `git fetch -q && git log --stat --format='%h %an %s' HEAD..origin/main`. Then I read CONTRACTS.md and the tail of NOTES.md after `git pull`. I used `git show --stat <sha>` once and read files after pulling, rather than `git show origin/main:file`. To wait, I used the playbook's bounded fetch loop (20 s sleep): 6 waits, about 15 minutes of wall time in total. About 8 of those minutes were at the end, confirming the team had gone quiet. The team was fast: by about 02:56, roughly 3 minutes after the start, all modules had landed. Polling cost wall time, not attention. The real cost was that I couldn't tell "teammates are done" from "teammates are busy".

## 5. Friction and confusing output

- The `pull && test && push` window is a race. If someone had pushed during my ~1 s test run, I'd have pushed only after a later pull, so main could hold a combination nobody tested. git doesn't verify that the tested tree is the pushed tree's parent. Nothing failed here, but "knew my land was safe" is only "probably".
- `git pull` output (`From ... a13b5e0..cda8610 main -> origin/main` / `Rebasing (1/1)`) tells you *that* something came in but not *what*. I needed a separate `git log` before each pull to see it.
- No signal for "is anyone still working?". I spent the last ~8 minutes in fetch loops just to be confident I finished last.
- The Show convention depends on discipline. When I touched report.js, nothing told a4 except my NOTES.md line. When a4 pushed again, nothing told me whether my change survived.
- I puzzled over no messages. Output was clear because nothing went wrong.

## 6. Compared with an ideal tool

For 5 agents landing roughly every 30 seconds:
- An ideal tool would **push** "a3 landed scheduler (Plan shape changed)" to the people who depend on it, instead of everyone polling.
- It would run the integration tests on the **merged result** atomically at land time, so "tested" means tested on exactly what is now main.
- It would let me subscribe to `src/scheduler.js` and `CONTRACTS.md#scheduler` changes.
- It would tell an owner when someone else changed their file, and show whether that change survived later edits.
- It would show team presence or "done" status, so the integrator knows when to stop.

git plus NOTES.md was adequate because the module boundaries were clean and the team pinned contracts early. Coordination came from conventions (NOTES.md, CONTRACTS.md, commit messages), not from git itself.

## 7. Features I wanted

- Server-side "test the merge then accept the push" (a merge queue).
- A subscribe/notify feed per path.
- A "who's active / who's done" signal.
- An `@owner` mention in commit messages that reaches the owner.
- A way to see a log of pulled commits after `git pull`, e.g. `git pull --log`-style.
