# a2 report (geo)

## 1. What I built

`src/geo.js` + `test/geo.test.js` (11 tests), and the pinned "geo" section of CONTRACTS.md:
`distanceKm` (haversine, R = 6371), `travelMinutes`, `routeLengthKm`, `roundTripKm`, `withinRange`,
`orderStops` (nearest neighbour then 2-opt, deterministic, returns the same objects),
`timeRoute` (per-stop arrive/wait/deliver/depart/late, hovering until a window opens, `windowsOk`,
`end`) and `latestStart` (latest feasible departure for a stop order). Stops can be packages
(`.destination`) so callers pass model objects straight in. Lands: #3, #8, #15, #16.
State when I left: main #22, `npm test` 60/60 pass, `node src/cli.js plan fixtures/day1.json`
prints 18 delivered / 11 trips / p19 unassigned / EUR 117.74; all four fixtures behave
(edge-invalid exits 65).

## 2. How I learned about teammates' work

- `hs watch --json >> .hs/feed.jsonl` in the background from the start; read it with `cat`/`tail`
  a handful of times.
- My main tool was the blocking wait: `hs watch --path /src/scheduler.js --count 1 --timeout 600`
  (and later with several `--path`s incl. `/NOTES.md`). It returned with the exact changeset
  line the moment a3 landed. That fully replaced polling; I never ran sync in a loop.
- `hs sync` / `hs land` "incoming from teammates" lists were the most informative summary.
- `hs show 17 --path /src/scheduler.js` to read how a3 consumed my API; `NOTES.md` and
  `CONTRACTS.md` after sync for shapes (a1's Day, a3's Plan).

## 5. Friction, bugs, confusing output

Very little. Honest notes:
- When my land merged a teammate's change to the *same file* (CONTRACTS.md in #3 and #8) there

## 6. Compared with git

With a shared git repo the same work would need `git pull --rebase` before every push and a
retry loop when someone pushed first; CONTRACTS.md and NOTES.md (touched by everybody in the
first minutes) would have produced real textual conflicts on NOTES.md at least, which the
`merge=union` attribute avoided here (git can do that too with `.gitattributes merge=union`,
but nobody sets it up). `land --check` running tests on main+mine and re-running when main moved
is something git has no equivalent for without CI/merge queue. The biggest practical win was
the blocking `watch --path ... --count 1`: in git I'd poll `git fetch && git log origin/main -- src/scheduler.js`.
Where git is better: richer, mature tooling (blame, bisect, branches for experiments), and I
never felt any need for hs's P2P nature in this local setup. For a module with a clear owner
and few overlapping edits, git would have worked nearly as well; the difference is mostly
ergonomics, not capability.

## 7. Features I wanted

- A way to be notified when someone starts depending on my module (e.g. watch for changesets
  whose diff mentions `require('./geo')`) — I used path waits on consumers' files instead.
