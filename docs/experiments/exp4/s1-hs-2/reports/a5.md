# a5 report — integrator (cli, integration tests, fixtures)

## 1. What I built

- `src/cli.js`: `plan <dayfile> [--json]`. Runs model.loadDay → scheduler.plan → pricing.price → report.renderReport, or report.reportJson for `--json`; the four pinned fields are always set again on top of that object. Exit codes are 0, 64 (usage), 65 (invalid day file, prints model's list of problems), 66 (file unreadable or not JSON) and 1 (unexpected error). It exports `run(argv, io)` for in-process tests.
- `test/integration.test.js` (16 tests). They run the full pipeline through the CLI's `--json` and recompute everything from the raw day file with my own haversine:
  - each package appears exactly once, either in a trip or unassigned with a reason;
  - payload and range per trip, in flight order;
  - window, day-length and no-overlap timing, including hovering;
  - the plan's own `distanceKm`, `loadKg` and `end` agree with my recomputation;
  - prices match the pinned formula and the total is their sum;
  - "too heavy" and "out of range" reasons are actually true;
  - p19 is too heavy, the text report mentions every package, and invalid or missing files give a non-zero exit;
  - 40 seeded random days, which reproduce from the seed.
- Fixtures: `edge-unassignable.json`, `edge-short-day.json`, `edge-no-drones.json`, `edge-invalid.json`.
- I pinned the cli section of CONTRACTS.md (exit codes, what `--json` really contains).
- Final state: main #30. 65 of 65 tests pass. day1 gives 18 delivered in 11 trips, 91.73 km, EUR 115.48, with p19 unassigned as too heavy.

## 2. How I learned about teammates' work

- I started `hs watch --json >> .hs/feed.jsonl` in the background once and `tail`ed it before landing.
- Most of what I learned came from the `incoming from teammates (n): ...` block printed by `hs land --check` and `hs sync`. That block is effectively a changelog of everything since my last land, with good messages, and I read it on every land (8 lands).
- To wait, I used `hs watch --path /src/scheduler.js --count 1 --timeout 600` (the scheduler was the last piece I needed) and later `hs watch --count 1 --timeout 300/400`. These blocked cleanly and returned the moment a changeset landed.
- I read NOTES.md and CONTRACTS.md after each sync and used `hs log --oneline` once near the end. I never needed `hs show`: the messages plus NOTES and CONTRACTS were enough because ownership was per file.
- Yes, the feed and blocking watch fully replaced polling. I never ran a sync just to check.

## 5. Friction, bugs, confusing output

- **Order of output in `hs land --check`**: the order is "checking main #18 + your changes … check passed … incoming from teammates (5)". The incoming list comes after the check result even though those changes were already in the tested tree. It is not wrong, but I briefly wondered whether the check had included them (it had, since it said "main #18").
- **NOTES.md tagging (my mistake, not an hs bug)**: I wrote two lines tagged `[a4]` and `[a3]` meaning "addressed to", but the format means "author". a3 called it out.
  - Union-merged notes can't be corrected in place, so I had to append an apology.
  - Some way to attribute or address notes (e.g. `hs note --to a3`) would help.
- **Notes crossing in flight**: I complained about report alignment that a4 had already fixed in #18, which landed concurrently with mine. This is inherent to async work, but hs gave no hint at land time that someone else had just touched the owner's file I was commenting on.
- **No dedicated status call for "is everyone done?"**: I relied on teammates' "final status" NOTES lines plus a 240 s `watch` timeout (`watch: timed out after 240s with 0 matching changeset(s)`, exit 2). That works but is ad hoc.
- Nothing in hs was actually confusing. `hs watch --stop` worked (`stopped watcher 376774`).

## 6. Compared with git

**Where git would have been about the same:** module ownership was strictly per file, so a shared git repo would also have had few code conflicts. Git also supports `merge=union` for NOTES.md via .gitattributes.

**Where hs was better in this exact setup:**

- **Notifications.** `hs watch --path X --count 1` replaced a fetch-and-sleep polling loop. With git I would have polled `git fetch` and diffed logs, and probably found out about #13 minutes later.
- **Testing the merged tree.** `land --check` runs the tests on main plus my changes and retries if main moves. That is a correct-by-default version of `git pull --rebase && npm test && git push`, which with 5 agents landing every minute would often fail the push with non-fast-forward errors and need re-testing.
- **Hot shared files.** For CONTRACTS.md and NOTES.md, which everyone edits, hs's per-file 3-way rebase was invisible. With git, every push race on those files would have been a manual pull/rebase round.

**Where git would have been better:**

- Tooling familiarity, `git blame`, and richer history inspection.
- Branches or PRs for the review flow, though I never needed review here.

**Overall:** for this exact workload, hs was moderately better, mainly through the push-feed and `--check`. It was not dramatically better, because the per-file ownership design kept conflicts rare whatever the tool.

## 7. Features I wanted

- A team-presence or "who's still working" view (e.g. `hs team`: last land per agent and whether their watch is running), to know when to stop as the integrator.
- A `hs land` hint like "#18 a4 touched /src/report.js 30 s ago" when my NOTES diff mentions a file someone just changed. More generally: "your note may be stale".
- Addressed notes: `hs note --to a3 "..."` that shows up in their `--for-me` feed.
- `incoming from teammates` printed before the check line, to make clear what was tested.
