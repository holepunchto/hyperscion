# a1 report: model owner

## 1. What I built

`src/model.js`: `loadDay(json | string)` and `loadDayFile(path)` return a deep-frozen, JSON-serializable `Day`. It keeps the day file's field names and adds `drone.home` (the depot's coordinates), `pkg.express`, `pkg.window` (or `null`), `pkg.earliest`/`pkg.latest` (always numbers) and `depotById`/`droneById`/`packageById` lookups. Validation collects every fatal problem and throws one `DayValidationError` with `.errors[]` and a message of the form `N problems:\n  - ...`. Undeliverable but valid packages (too heavy, out of range, impossible window) pass through to the scheduler. `test/model.test.js` has 10 tests, including a5's edge fixtures. I pinned the model section of CONTRACTS.md in the same changeset as the code (#4). My lands were #4, #7, #9 and #14, all `final`.

At the end, main was at #25: `npm test` passed 63, failed 0 and skipped 0. `node src/cli.js plan fixtures/day1.json` delivered 18 packages in 11 trips, with p19 unassigned (too heavy), 91.73 km and EUR 115.48. `edge-invalid.json` exits 65 and lists all 5 problems.

- The `incoming from teammates (n): ...` list from `sync` and `land` was my main summary. I read the message lines and opened the diffs I cared about:
  - `hs show 5` (a5's cli and fixtures)
  - `hs show 6 --path src/pricing.js`
  - `hs show 21 --path src/cli.js`
- I also read NOTES.md and CONTRACTS.md after syncs, and grepped the synced tree for how others call `model`.
- What I looked for: how each module consumes `Day` (lookups by id or arrays, `drone.home` or a depot lookup, whether anything sorts frozen arrays), and the fixtures a5 expects my loader to accept or reject.

## 6. Compared with git

In this exact situation (5 agents, files that are mostly owned plus shared NOTES and CONTRACTS):

- **Better than git:**
  - `land --check` does fetch, rebase, test and push atomically. It retries itself when main moves. With git I would have had `pull --rebase`, test, push, rejected (non-fast-forward), and repeat, several times, because all 5 agents were landing within seconds of each other.
  - The union merge for NOTES.md removes the most common git conflict in this setup.
  - The JSON feed and `watch --path ... --count 1` give a push-style "tell me when the scheduler lands". Git has no equivalent without polling `git fetch` or a CI hook.
  - The `incoming from teammates` list on every sync is a better default than git's silent fast-forward.
- **Same as git:** `hs show n` and `hs log` are `git show` and `git log`. CONTRACTS.md section edits merged in both tools would have merged the same way with a 3-way merge.
- **Worse, or unproven:** the provisional, settled and final states are extra concepts. I never saw them matter, since everything was final immediately with a healthy hub. I never used review (Ship, Show, Ask), so I can't say whether it beats PRs. Git's tooling (blame, bisect, editor integration) is far richer.
- **Net:** for this tightly parallel, owned-file workflow, hs was moderately better, mainly from automatic rebase-and-retry on land plus the watch feed.

## 7. Features I wanted

- A `hs land --check` shortcut that skips the check when only union-merged files changed. Or simply no "untested" warning for NOTES-only lands.
- `hs who-uses /src/model.js`: which teammates' changesets touched code that calls my module. I approximated it with grep.
