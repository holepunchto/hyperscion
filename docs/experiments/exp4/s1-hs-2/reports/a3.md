# a3 report: scheduler

## 1. What I built

I wrote `src/scheduler.js` with `plan(day) -> Plan` and `test/scheduler.test.js` (16 tests, plus a `checkPlan` invariant checker that every fixture test runs through). The scheduler is greedy:

- The most urgent remaining package (express first, then earliest window end, then heaviest) seeds a trip on whichever drone would deliver it earliest.
- That trip then grows by cheapest insertion, but only while it stays within payload, range, windows, the day length and a 15-minute hover cap.
- A stop is added only if the detour costs less than a dedicated round trip from the best-placed drone.
- An express stop is added only if that makes it at most 20 minutes later than on its own trip.
- A drone can take several trips, and a later trip can fill an idle gap before a trip that is waiting for a delivery window.
- Every undeliverable package gets a reason with a pinned prefix: too heavy / out of range / window / no drone time / invalid package.

The Plan shape is pinned in CONTRACTS.md and was landed first, in #2. On day1 the result is 18 delivered in 11 trips, 91.73 km, EUR 115.48, with p19 too heavy. 6 of my 7 lands were code or contract changes: #2, #13, #17, #20, #23, #26, #28.

## 5. Friction, bugs, confusing output

- **The NOTES.md author tag is just text.** A line `- [a3] cosmetic: reason for an unreachable window says …` appeared in NOTES.md, and I never wrote it. To find the author I had to run `hs show N --path NOTES.md` for several changesets. It was a5's (#19), probably meant as "to a3".
  - hs doesn't help here because union merge hides which changeset added a line. A `hs blame NOTES.md` would have answered it at once.
  - While doing this I also confused myself: a shell loop printed the `show` output before its `== n` label. That was my own scripting error, not hs.
- **`show --path` on an untouched file is unclear.** `hs show 18 --path NOTES.md` (NOTES.md is not in #18) prints the header and `(2 other path(s) not shown, drop --path for all)`. It doesn't say "NOTES.md was not changed in #18". This is minor, but it made me stop and think.
- **Merges are silent.** There's no per-file statement of what was merged during a land (see section 4).
- **Unused features.** Review (Ship/Show/Ask) never came up. I never touched another owner's file, so I can't judge it.
- Otherwise the output was clear. Everything that needs a peer took about 2–3 s.

## 6. Compared with git

**What hs did better in this situation:**

- **Shared files never needed manual merges.** NOTES.md is union-merged, and the auto-rebase on land meant five agents appending to NOTES.md and editing CONTRACTS.md never conflicted. With a shared git repo, NOTES.md appends would have conflicted constantly, unless we had set up `merge=union` in `.gitattributes`, which git supports too. Every agent would also need its own pull/rebase/push retry loop.
- **`land --check`** in one command (rebase onto main, test the combination, land only if green, re-check if main moved) is clearly nicer than `git pull --rebase && npm test && git push` plus retry on a rejected push.
- **The feed and `incoming` summaries** gave me awareness without polling. With git I would `git fetch && git log` periodically.

**Where hs gets too much credit:**

- Ownership was cleanly split by file, so the zero conflicts here are mostly a property of the project layout, not of hs. With git and separate branches merged often, it would have gone almost as smoothly.
- The real differentiators were the union merge on NOTES.md and the landing ergonomics.

**What git would have done better:** blame, mature diff tooling, and familiarity. I missed `git blame`.

## 7. Features I wanted

- `hs blame <file>`, or per-line authorship for union-merged files.
- A per-file merge summary on land, for example `merged /CONTRACTS.md with #8 (a2), #12 (a4)`.
- `hs show N --path X` should say "X not changed in #N".
- A way to address a NOTES line to someone, for example `hs note --to a3 "…"`, so it shows up in their `--for-me` feed. Otherwise "[a3]" is ambiguous: is it the author or the recipient?
