# a5 report (git arm, s2-git-1)

## 1. What I built

- `src/cli.js`: `plan <dayfile> [--json]`, flags in any position. Exit 0 = success, 1 = file unreadable or invalid (a1's `DayValidationError` list on stderr, stdout empty), 2 = usage. `run(argv, io)` is exported for tests. Exit codes are pinned in CONTRACTS.md.
- `src/report.js` (shared with a4): the original skeleton with separate a4 and a5 sections, `toJson` (the pinned `--json` shape, plus `end` and `distanceKm`), and the text layout: trips grouped by drone, then per stop the price, flight minutes (CR-1), service time, an express flag and the window. Also unassigned packages with reasons and totals. Fixed a `clock` rounding bug that could print `+00:60`.
- `test/integration.test.js`: the full pipeline plus the CLI on `day1.json` and three edge fixtures (`edge-unreachable.json`, `edge-invalid.json`, `edge-empty.json`). Property checks:
  - every package appears exactly once (in a trip, or unassigned with a reason);
  - payload and range per trip (range recomputed with `geo.routeLengthKm`);
  - windows (service start = eta + wait);
  - `end <= dayLengthMinutes`;
  - no overlapping trips per drone;
  - p19 is too heavy;
  - each CR-1 price, recomputed from flight minutes taken independently from geo (±1 cent);
  - total equals the sum in cents;
  - `--json` deep-equals the pipeline output;
  - exit codes.
- Unit tests in `test/report.test.js`.
- Final main is `75957ba`: 80 tests pass, 0 fail. `node src/cli.js plan fixtures/day1.json` gives 18 delivered, p19 unassigned and a total of €79.00 under CR-1.

## 2. How I learned about teammates' work

- After every pull, and in every wait loop, I ran `git fetch -q && git log --stat --format='%h %an %s' HEAD..origin/main`.
- I used `git show <sha> -- <files>` to read the diffs that touched my files (report.js, integration test, NOTES.md, CONTRACTS.md), and `tail NOTES.md` or `cat CHANGE-REQUEST.md` after pulling.
- For waiting I used the playbook's bounded loop (fetch every 20 s, at most about 9 minutes). Once it was filtered to `-- src/pricing.js` to wait for a4's CR-1. I ran 8 such loops, about 35 minutes of wall time in total. Most of that was idle waiting rather than effort, but it is blind: each loop wakes on any commit, including notes-only ones like `ec57dff` and `8d485f3`, and then I had to read and re-loop.
- Rough split: about 40% of my turns went to fetch/log/show reading and about 60% to building.

## 4. Conflicts, rejected pushes, rebases

- **Rejected pushes: 0.** I always ran `pull && test && push` in one script and was never raced between pull and push.
- **Auto-rebases of my commits: 5.** These went smoothly (`Successfully rebased and updated refs/heads/main`). One of them pulled in a2's timing commit, which broke my new tests, and my script refused to push. That is correct behaviour, but it had already created the commit locally (see section 5).
- **Real conflicts: 1.** In `src/report.js` and `test/report.test.js`, a4's 00e9c86 against my local refactor of the same money section. Same intent, so I resolved it with `git checkout --ours` (which in a rebase means upstream, a4's version) and then `rebase --continue`. That left my commit containing only a NOTES line under a now-false message, so I amended the message before pushing. About 5 minutes.

## 5. Friction and confusing output

- **ours/theirs is inverted during a rebase.** The conflict markers label upstream as `<<<<<<< HEAD` and my own commit as `>>>>>>> 22fa384 (...)`, so `--ours` means the teammate's version. I had to stop and think about it.
- **`[detached HEAD 918c864] report: ...` from `rebase --continue`** looks alarming but is normal.
- **After the conflict, the commit kept its old message** even though its content was now just one NOTES line. Git can't tell that the message no longer matches. I amended by hand.
- **My commit-then-pull-then-test helper pushed a commit that fails tests on its own.** `bfa70e3` fails alone and the follow-up `ad4659c` fixes it, and both went to main together under the same message. Commit-before-test plus rebase makes it easy to leave non-bisectable history. Git has no "land only if tests pass on the merged tree" step.
- **The wait loop wakes on every commit**, including notes-only ones. `git log HEAD..origin/main -- <path>` helps, but you have to know the path in advance. The CR arrived as `CHANGE-REQUEST.md` + NOTES, which I only saw because I happened to be in a loop.
- **No way to see what teammates are working on before they push.** The duplicated a2/a3 fix is the main example.
- **NOTES.md union merge worked perfectly**: no NOTES conflicts at all.
- **My own mistake (not git's):** a stray `cat > file` blocked on stdin, which cost about 2 minutes.

## 6. Compared with an ideal tool

For 5 parallel agents with shared files, an ideal tool would have:

- **a push feed** with per-path or per-mention filters ("wake me when report.js, my files, or a CHANGE-REQUEST changes, or someone @-mentions a5"), instead of fetch/sleep loops;
- **"land with check"**: rebase, run tests on the merged tree, and land only if green, atomically, so that `bfa70e3`-style broken intermediate commits never reach main;
- **claim/intent visibility** ("a3 is working on scheduler.js: trip-mates bug"), which would have avoided the duplicate fix;
- **section ownership inside shared files**, or at least a warning on pull ("a4 changed the money section of report.js that you also edited");
- **conflict output that names people** ("a4's version" / "your version") instead of HEAD/ours/theirs.

Git was adequate: everything worked and nothing was lost. But all of the coordination lived in NOTES.md conventions and my own scripts, not in the tool.

## 7. Features I wanted

1. A watch/feed with path and mention filters, blocking until a match.
2. `push --check "npm test"`: rebase, test, push, and retry if main moved.
3. Pre-push intent or claims ("working on X").
4. Rebase conflict labels in terms of authors.
5. A warning when a teammate touched lines near my unpushed edits, at fetch time rather than at rebase time.
