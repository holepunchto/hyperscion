# a4 report (git arm, s2-git-1)

## 1. What I built

- `src/pricing.js`: `price(plan, day) -> { currency, prices, total, lines }`, `priceOf`,
  `formatMoney` ("€7.40"), `RATES`, and after CR-1 `flightMinutesByPackage` /
  `tripFlightMinutes`. All money in integer cents, each price rounded once (half up), total =
  sum of rounded prices.
- v1 formula (pinned first, 73da4d6): 2.50 + 0.80/km (home depot -> destination) + 0.50/kg +
  3.00 express. CR-1 (8b3e517): (2.00 + 0.25 x flight minutes + 0.40/kg) x 1.5 if express.
  Pricing computes flight minutes from plan + day itself (geo.distanceKm/travelMinutes along
  `trip.packages`).
- The money section of `src/report.js` (00e9c86): € formatting delegated to pricing, plus a
  revenue-per-priority summary from `price().lines`.
- `test/pricing.test.js`: about 13 tests, including real day1 + scheduler plan, and a
  cross-check that my flight minutes match a2's `stop.flightMinutes` on every fixture. Also
  the money tests in `test/report.test.js`. CONTRACTS.md pricing section kept current.
- Final state: main at 75957ba, 80 tests pass, and `node src/cli.js plan fixtures/day1.json`
  gives 18 delivered, 12 trips, 1 unassigned (p19, too heavy), Total €79.00.

## 2. How I learned about teammates' work

- `git fetch -q && git log --oneline --stat HEAD..origin/main` was the main tool, run after
  every commit and in every wait loop. I also used `git show <sha> -- CONTRACTS.md NOTES.md`
  to read pinned shapes, `git log -- src/report.js`, `tail NOTES.md` after each pull, and
  `cat` of the files after pulling.
- To wait I used bounded loops (`for i in $(seq 1 25); do git fetch -q; git log HEAD..origin/main | grep -q . && break; sleep 20; done`).
  I ran about 8 of them; they took about 20-25 min of the ~50 min session. One was filtered to
  my files + CHANGE-REQUEST.md, so it slept through an unrelated scheduler commit.
- Each `--stat` listing told me which files changed. Then NOTES.md told me why. For
  interfaces, I diffed CONTRACTS.md in the commit.

## 5. Friction and confusing output

- No feed. Learning about a push takes a poll, so the CR-1 arrival latency depended on my sleep
  interval (up to ~20 s, plus whatever loop I was in). A path-filtered wait loop meant I
  deliberately ignored other changes until a relevant one came.
- Parallel duplicate work that git can't prevent: my "I'll compute flight minutes" note and
  a2's `stop.flightMinutes` commit crossed in flight. Neither of us could see the other's
  intent until both had pushed.
- `Rebasing (1/1)Successfully rebased...` is printed with no newline between the two parts.
  It's harmless but reads oddly.
- `git pull -q` hides whether a rebase happened at all, so I lost track of the exact
  auto-rebase count.
- The recording wrapper (git-trace.js) crashed with `Error: write EPIPE ... Unhandled 'error'
  event` when I piped `git log` into `head -0`. That is a harness issue, not git, but it
  printed a Node stack trace.
- The Show convention (NOTES line naming the owner) works, but nothing tells the owner
  directly. a5 only saw my report.js change because they read NOTES.
- Two identical commit messages from a5 (bfa70e3, ad4659c) were confusing in `log --oneline`
  until I looked at `--stat`.

## 6. Compared with an ideal tool

- A push feed I could block on ("wake me when anything touches src/report.js, CONTRACTS.md,
  or a CR lands") instead of sleep loops.
- Visible intent before code: a lightweight "claimed: flight minutes source" signal, so a2
  and I wouldn't both have built one.
- Owner notification when someone edits their file (automatic Show), and a way to see that
  a teammate had a conflict in a shared file I co-own.
- Per-section ownership in a shared file (report.js money vs layout), so concurrent edits to
  different sections never conflict.
- Honestly, for this size of task git worked fine. Linear history, small commits and NOTES
  union-merge kept things smooth. The costs were polling time and the lack of an intent
  channel.

## 7. Features I wanted

- `git wait --path <p>` / push notifications.
- Automatic owner notification for edits to their files (CODEOWNERS-like, without PRs).
- An intent/claim board tied to the repo.
- A `pull` summary listing incoming commits by author (like "incoming from teammates").
