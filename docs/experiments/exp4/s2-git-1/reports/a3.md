# a3 report (git arm, s2-git-1)

## 1. What I built

The capacity side of `src/scheduler.js` + `test/scheduler.test.js` (12 tests):

- `plan(day) -> Plan`, with the Plan shape pinned in CONTRACTS.md in my first push (a09db42).
  The file is split into `buildTrips()` (mine) and `scheduleTimes()` (a2's). I wrote a placeholder
  `scheduleTimes()` so the pipeline worked end to end from the start, and a2 replaced it.
- `buildTrips`: packages are sorted express first, then by earliest deadline. Each package
  either joins the open trip with the smallest extra distance (payload, `rangeKm` via
  `geo.routeLengthKm`, and on time from minute 0 via a2's `timeTrip`), or opens a new trip on
  the least-busy drone that can carry it. A drone can fly several trips. Unassigned reasons:
  too heavy, out of range, or "no drone can make it on time even on a dedicated trip" (a
  prefilter that uses a2's `soloTimingProblem`).
- At first I used local haversine and nearest-neighbour shims. I switched to a2's geo
  (`orderRoute`, `routeLengthKm`, `travelMinutes`) right after seeing it land (01707ba).

At the end, main passes `npm test` (80 tests, 0 fail, 0 todo), and
`node src/cli.js plan fixtures/day1.json` prints a correct report: 12 trips, 18 delivered,
p19 unassigned as too heavy.

## 2. How I learned about teammates' work

- `git fetch -q && git log --stat HEAD..origin/main` and
  `git diff HEAD origin/main -- NOTES.md CHANGE-REQUEST.md`. The NOTES diff was by far the most
  useful single view.
- `git show <sha> -- src/scheduler.js` to read a2's timing code before pulling, and
  `git show <sha> -- CONTRACTS.md`.
- I waited with the playbook's bounded loop (`for i in $(seq 1 N); do git fetch -q; git log
  HEAD..origin/main [-- paths] | grep -q . && break; sleep 20; done`), about 9 times. Most
  of my wall-clock time went into these loops, roughly 25–35 minutes. The loops cost me few
  tokens, but each one wakes on any push, even when it isn't relevant. Path-filtering helped
  (`-- CHANGE-REQUEST.md src/scheduler.js`), but then I could miss NOTES lines addressed to me.

## 5. Friction and confusing output

- `Rebasing (1/1)Successfully rebased and updated refs/heads/main.`: a missing newline makes
  this run together. It's cosmetic, but it looks like garbage at first glance.
- `git pull` after a push said `Current branch main is up to date.` even though a teammate
  had pushed. I had to check whether my earlier `-q` fetch had already brought it in. I
  wasn't sure what "up to date" referred to.
- No feed: every wait is a fetch-sleep loop that cannot tell "a commit that concerns me" from
  "any commit". I had to `git diff HEAD origin/main -- NOTES.md` every time to see whether
  anyone was talking to me.
- Claims ("I'm taking bug X") travel over the same slow channel as the code. A claim pushed
  60 s before a teammate starts the same work doesn't help if they don't fetch in between.
  That caused one double fix.
- Union-merged NOTES.md sometimes puts lines out of time order (a2's CR-1 line landed above
  my earlier ack). That's harmless, but chronology is unreliable.

## 6. Compared with an ideal tool

For 5 agents working in parallel on shared files, an ideal tool would:

- push notifications (a feed) filtered to "touches my files / mentions me / change request",
  instead of me polling;
- have a lightweight **claim/lock-intent** primitive ("a3 is working on bug X / on
  scheduler.js lines N–M") that teammates see immediately and that is checked before they
  start. That would have prevented the double fix and the duplicate flightMinutes source;
- tell me at push time which tests a teammate's concurrent change touched, or run the tests
  on the merged tree automatically (with git, "pull && npm test && push" is a race I just
  happened to win every time);
- treat NOTES-style messages as first-class, addressable messages (to a2), not lines in a
  file whose merge order is arbitrary.

To be fair to git: rebases were silent and correct, nothing was lost, and merge conflicts
never happened, thanks to good module/function ownership.

## 7. Features I wanted

1. A `git wait --path X --mention a3` that blocks until a relevant commit or note lands.
2. Visible work claims / intents.
3. Merge-time test checks ("land only if tests pass on the merged result").
4. Structured messages addressed to an agent, separate from code history.
