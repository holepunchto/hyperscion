## 2. How I learned about teammates' work

- Each cycle: a bounded fetch loop (`for i in $(seq 1 25); do git fetch -q; git log --oneline HEAD..origin/main | grep -q . && break; sleep 20; done`), then `git log --stat --oneline HEAD..origin/main` and `git diff HEAD..origin/main -- NOTES.md | grep '^+-'` to read only the new NOTES lines, then `git pull`.
- Sometimes `git show --stat <sha>` and `grep` on teammates' source after pulling (cli.js, scheduler.js, pricing.js) to see how they used `Day`. Once I grepped `day\.[a-zA-Z]+` across src/test to check that every field consumers read actually exists.
- About 13 fetch-loop waits. Once model was pinned (around cycle 3), nearly all my wall time was polling. I estimate 70–80% of my session was waiting in `sleep 20` loops. It cost few tokens but a lot of time. I also changed the loop filter once (`-- src test CONTRACTS.md`) to skip NOTES-only commits, then realised that could make me miss a `[pm]` change request that arrives as NOTES + CHANGE-REQUEST.md, so I went back to waking on any commit.

## 5. Friction and confusing output

- `git pull` prints `Rebasing (1/1)Successfully rebased and updated refs/heads/main.`, two messages run together on one line. It does not say *what* came in. After the pull, `HEAD..origin/main` is empty, so to review incoming work I had to either check the log *before* pulling or remember the old sha. I settled on fetch → log → pull.
- No way to tell "NOTES-only" commits from code commits without `--stat`. To avoid waking on chatter I'd have to filter by path, and that risks missing the PM's change request.
- a5 pushed two commits with the identical subject "integration: full-pipeline property tests …" (bfa70e3 and ad4659c). The log made me wonder whether something had been amended or duplicated. I had to read `--stat` to see the second was a follow-up.
- There's no signal for work in progress, so I watched duplicate work happen. a5 reported the "impossible window sinks trip-mates" bug. a3 claimed it in NOTES (ec57dff) and fixed it (6fe7e50). a2 also fixed it on the timing side (962b977). Both removed the same `todo`. On CR-1, a4 wrote "a2/a3 nothing needed, pricing computes flight minutes" (00e2c1c), while a2 added `stop.flightMinutes` (d957009). That left two sources of flight minutes, and the integration test ended up with a ±1 cent tolerance plus a 2.85 → 2.9 double-rounding fix (cec3136). Git can only show finished pushes, and claims in NOTES only arrive after fetch + pull.
- Polling: `sleep 20` loops are crude. Wake-ups had high latency, and I spent most of my time idle.

## 6. Compared with an ideal tool

For 5 parallel agents on shared files, an ideal tool would:
- **Push** events (a feed) instead of fetch-and-sleep, with a filter like "changes to files that depend on mine, CONTRACTS.md, or anything from pm".
- On sync, **list what came in** (`incoming: a3 scheduler.js "…"`) instead of just "rebased".
- Show **claims / work in progress** ("a3 is working on scheduler buildTrips for bug X"), so a2 and a3 don't both fix the same bug and a2 and a4 don't both implement flight minutes.
- Know who **consumes** an interface. When I change `Day`, tell a2–a5 directly, or run their tests against my change before it lands. Today it's `git pull && npm test` by hand, and nothing enforces that.
- Treat **change requests** as first-class events routed to the named owners. Today they're a NOTES line I could miss.
- Git did the actual merging fine: zero conflicts, clean auto-rebase, and union-merged NOTES was effective. The gaps are awareness and coordination, not merging.

## 7. Features I wanted

1. A blocking "wait for change" with a path or author filter (`git wait --path src/ --path CHANGE-REQUEST.md`) instead of sleep loops.
2. `pull` printing the incoming commits (oneline, author, files).
3. A lightweight "claim/intent" channel tied to files.
4. A dependency-aware notification ("model.js changed; you import it").
