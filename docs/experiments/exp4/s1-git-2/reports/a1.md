# a1 report: model (git arm, s1-git-2)

## 1. What I built
`src/model.js`: `loadDay(json|string)` and `loadDayFile(path)` return a deep-frozen `Day`
(the file's arrays with their field names kept, plus `drone.home {lat,lon}`, `package.express`,
`package.window` as `[e,l] | null`, defaults for serviceMinutes/dayLengthMinutes/priority, and
`depotsById/dronesById/packagesById`). Both throw `DayValidationError`, whose `.errors[]` lists
**every** fatal problem and whose message is ready for stderr. Undeliverable packages are not
errors. The model section of CONTRACTS.md is pinned. `test/model.test.js` has 9 tests,
including day1 and a5's edge fixture. At the end, main had 52/52 tests passing, and
`node src/cli.js plan fixtures/day1.json` printed a full report (18/19 delivered, p19 unassigned
"too heavy"). An invalid day file exits 1 with the clean list of problems.

## 2. How I learned about teammates' work
- `git fetch -q && git log --oneline --stat HEAD..origin/main` after every land, and in the
  playbook's bounded fetch loop (20 s sleep). I used the loop 3 times: waiting for anything,
  waiting for `src/scheduler.js`, and a final check for anything new.
- `cat NOTES.md` after each pull. It was the most useful channel, because the notes said what
  people *needed* (a3: "keep arrays with day-file field names"; a5: "loadDay should THROW").
- I read files directly after a pull (`src/cli.js`, the fixture, grep on scheduler.js), rather
  than `git show <sha>`.
- Polling: about 6-8 minutes of wall-clock time in the sleep loops, not much attention. The
  loops ended early as soon as anything landed.

## 4. Conflicts, rejected pushes, rebases
- 3 pushes (77abc7f, ee66d3a, fff97a0), all accepted on the first try. There were 0 rejections
  and 0 conflicts.
- 3 pulls rebased my commit onto new work (geo 17c6857; geo d7aa4d8; cli/report b377012). They

- The `git pull && npm test && git push` one-liner made every land safe: tests ran on top of
  the latest main.

## 5. Friction and confusing output
- `git-a1 log --oneline -4 --stat origin/main | head` crashed the recording wrapper with
  `Error: write EPIPE ... at Socket.<anonymous> (.../scripts/experiment/git-trace.js:21:18)`
  and a Node stack trace. It was harmless, but alarming, and it is wrapper friction rather than
  git itself. I worked around it by not piping into head.
- `git pull -q` hides whether a rebase happened. Without `-q` the output
  `Rebasing (1/1)Successfully rebased and updated refs/heads/main.` has no newline between the
  two parts. It is minor.
- Git has no notion of "who depends on my interface". I had to grep teammates' code
  (`grep -n "model\|loadDay" src/*.js`) to see how they used `Day`.
- The playbook says contract changes are "Ask" (an ask/ branch), but my instructions said to
  land the interface first. I shipped directly and announced it in NOTES. With everyone pinning
  contracts in the first minutes, an ask/ round trip would have stalled the team.

## 6. Compared with an ideal tool
- A push feed or subscription ("tell me when someone lands a change that touches CONTRACTS.md
  model, or imports src/model.js") would replace the sleep/fetch loops.
- Structured "needs" and "answers" (a3 needs X from a1) instead of free text in NOTES.md, with
  a way to mark one resolved and link it to the commit that resolved it (a5's 781952a answered
  my note, and only a free-text line said so).
- A consumer view: who reads which fields of my exported types, so I would know which change
  is breaking without grepping.
- In this run, git was adequate. The work split cleanly by file, the union-merged NOTES
  absorbed the shared-file traffic, and the tested rebase-then-push loop never failed.

## 7. Features I wanted
- A blocking `wait-for <path|any>` that returns the new commits.
- Pull output that summarizes "N commits from a2, a5 rebased under your 1 commit; files: ...".
- Machine-readable needs/acks in the log, tied to commits.
