## 4. Conflicts, rejected pushes, rebases

- 6 pushes to main and 0 rejected. Each time I used `git pull && npm test && git push`, so the pull absorbed the race window.
- 5 of the 6 pulls rebased my commit (`Rebasing (1/1)Successfully rebased and updated refs/heads/main.`). All were clean: CONTRACTS.md edits were in separate sections and NOTES.md is union-merged.
- 0 content conflicts.
- The only real conflict was *semantic* (the stale NOTES line above), and git cannot detect that kind of conflict.

## 5. Friction and confusing output

- `Rebasing (1/1)Successfully rebased and updated refs/heads/main.`: the two messages run together with no newline. It is readable but looks broken.
- Every pull rebased my commit, but the output never says *what* got rebased under me. I had to run a separate `git log HEAD@{1}..` or `--stat` to see which teammates' commits I was now testing against. Tests passed each time, but I didn't know which new code they had exercised.
- No way to wait cheaply. The playbook's `for i in $(seq 1 30); do git fetch -q; ...; sleep 20; done` is a busy loop, and the 20 s granularity wastes time. The open-ended "has anything relevant changed?" wait (12 fetches, nothing for me) was pure overhead.
- NOTES.md is a shared, unstructured, append-only log. Lines are not addressed to anyone, have no thread, and can't be marked resolved. My stale line stays in the log next to its correction.
- The pull → test → push window is not atomic. Tests ran on my local rebase, and in principle someone could push in between and leave main untested as a combination. It didn't happen to me (no rejections), but nothing would have warned me.
- No signal that a teammate *depends* on my API. I found a3's adoption of tripTimeline only by reading their diff.

## 6. Compared with an ideal tool

For 5 agents working in parallel on shared files, an ideal tool would:

- Push a feed of landed changes filtered to what I care about (my files, my contract section, and anything that imports `./geo`), instead of me polling `fetch`.
- Show "who calls my API" at land time. a3's 4a15691 starting to use `tripTimeline` should have pinged me, and my NOTES line should have been flagged as racing with it.
- Show, on rebase, the incoming commits my change is now stacked on.
- Land atomically with tests run on the exact resulting tree, so main is never an untested combination.
- Offer structured, addressable notes or requests (to: a3, re: geo.tripTimeline, status: open/resolved) instead of a flat log.

Git was adequate here, mostly because ownership was clean (one file per agent) and NOTES.md was union-merged. The coordination itself (learning about others, waiting, knowing who depends on whom) was all manual.

## 7. Features I wanted

1. A blocking "wait until something touching X lands" command (a server-side watch, not a sleep loop).
2. A rebase summary that lists the commits I was rebased onto.
3. Dependency-aware notifications: "a3 now calls your tripTimeline".
4. Addressed and resolvable notes instead of a flat NOTES.md.
5. Atomic test-then-land.
