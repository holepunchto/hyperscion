# a3 report (scheduler, git arm)

## 1. What I built

`src/scheduler.js`: `plan(day) -> Plan`. It is a greedy cheapest-insertion scheduler. Packages are handled express first, then by the tightest window deadline. Each package goes wherever it adds the least flying distance: any drone, any existing trip, any position, or a new trip at the end of a drone's day. Every candidate drone-day is re-simulated in full with a2's `geo.tripTimeline`, so payload, range, windows (hover until the window opens, or leave late instead), service minutes, day length and non-overlapping trips all hold. A standard package is never inserted before an express stop. Undeliverable packages get reasons with the pinned prefixes: too heavy / out of range / window cannot be met / no capacity left in the day. I pinned the `Plan` shape in CONTRACTS.md as my very first push. `test/scheduler.test.js` has 15 tests, including an independent invariant checker, edge cases, an empty fleet, a1's frozen Day, and a 150-package scale test (about 70 ms). On day1: 18/19 delivered in 12 trips, 79.5 km; p19 is too heavy.

## 2. How I learned about teammates' work

- I read NOTES.md after each pull with `cat`/`tail`, and once with `git diff HEAD..origin/main -- NOTES.md` before pulling.
- I read CONTRACTS.md once after the big pull (model/geo/pricing/report all pinned at once). I read a2's `tripTimeline` source in my working tree after pulling (`sed` on src/geo.js) and grepped a5's integration test for my reason prefixes.

## 4. Conflicts, rejected pushes, rebases

- Rejected pushes: 0. Content conflicts: 0. I always ran `git pull && npm test && git push` in one line, and nobody else touched my files.
- Auto-rebases: 4 (`Rebasing (1/1)Successfully rebased and updated refs/heads/main.`), all clean. NOTES.md union merge worked every time.
- A semantic race, not a git conflict: a2 wrote a NOTES line saying "your shim is now dead code, tripTimeline is there if you want it" at the same time I pushed 4a15691, which already used it. a2 had to push a correction (c1d71d5). Git can't show "someone is working on this right now".

## 5. Friction and confusing output

- `git pull` prints `Rebasing (1/1)Successfully rebased and updated refs/heads/main.` on one line (a carriage-return progress line glued to the result). It's readable, but noisy when piped.
- `git log --oneline -8 --stat ORIG_HEAD..HEAD` after a pull: I wanted "what did that pull bring in, plus my rebased commit". It worked, but I had to remember that ORIG_HEAD semantics change after a rebase pull. There's no plain "show me what just arrived" command.
- There's no push notification. Every wait is a sleep/fetch loop, and I could only tell that something landed, not whether it concerned me. I had to read NOTES.md myself to find lines addressed to "a3".
- No way to see in-flight work: the a2 race above.
- Not git: node's test runner prints `✖ failing tests:` for a `todo` test while `fail 0`, which briefly looked like a red main.

## 6. Compared with an ideal tool

With 5 agents and disjoint file ownership, git was adequate: zero conflicts, cheap rebases, and the log plus commit messages carried the information. An ideal tool would have:
- pushed a feed of landings filtered to "touches my files / mentions me / changes a contract I consume", instead of me polling with sleep loops;
- shown teammates' in-progress intent (draft commits or claims), avoiding the a2 race;
- attached the "who depends on this" information to contract changes, e.g. a CONTRACTS.md scheduler-section change notifies a4/a5 automatically;
- run the full test suite on the merged result server-side and told me "your land is green on main", rather than me trusting that nobody pushed between my `npm test` and `git push`. The pull/test/push window is small but unguarded.

## 7. Features I wanted

- `git watch --path src/geo.js` / a mention feed ("NOTES lines naming a3 since my last pull").
- An atomic "test-then-land" (push only if tests pass on the exact resulting tip).
- A short "what arrived in my last pull" summary.
