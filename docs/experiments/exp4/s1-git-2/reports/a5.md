## 5. Friction and confusing output
- No feed: learning that a teammate was waiting on me, or that a3 had answered, meant polling `fetch` + `log`. The fetch loop is a crude busy-wait (sleep 20, up to 30 times) and burns wall-clock time with no notification. My long 3-round wait loop hit my 600 s tool timeout and had to be stopped.
- `git pull` folds "here is what your teammates did" into rebase output. It lists the fetched range (`ca2bc8b..5c93fa9`) but not the commits, so after each pull I had to run another `git log`/`git show` to see what came in.
- NOTES.md replies are hard to find: `git show <sha> -- NOTES.md | grep '^+-'` worked, but nothing tells you a line is addressed to you (I grepped for `a5`).
- Nothing in git confused me. One non-git item: `node --test` prints `✖ failing tests:` even when the only entry is a `todo` test, with `fail 0`.
- `pull.rebase` + autostash worked without problems; I never needed the conflict path.

## 6. Compared with an ideal tool
- Push notifications/feed scoped to what I depend on ("scheduler.plan landed", "a3 replied to you"), instead of polling.
- A "who is working on what right now" view. I couldn't tell whether a3 was mid-change on scheduler.js before considering a small fix there, so I asked in NOTES instead of fixing it myself.
- Contracts as first-class, machine-checkable objects: my integration test effectively is the contract check, but nothing ties CONTRACTS.md text to code, and nothing flags a contract edit to its consumers.
- Server-side CI on main: each push gated on `npm test` at the merged state, so "safe to land" doesn't depend on everyone honouring `pull && test && push`. There is a small race between my test run and my push.
- A threaded, addressed message channel instead of an append-only NOTES file.

## 7. Features I wanted
Watch/subscribe on paths or contract sections; addressed notes with "unread for me"; land-gated CI on the merged result; a pull summary that lists incoming commits (one line each); presence/intent ("a3 is editing scheduler.js").
